อ่านหน้านี้หน้าเดียวก่อน แล้วค่อยไปคู่มือเล่มอื่น — ตอบว่าไฟล์ไหนคืออะไร ติดตั้งที่เครื่องไหน และสั่งอะไรเรียงตามลำดับไหน

คำสั่งทั้งหมดในหน้านี้พิมพ์บนเครื่อง storage (10.100.1.17) เว้นแต่จะเขียนบอกไว้

มีคู่มือ 3 เล่ม อ่านตอนไหนบ้าง

เล่มอ่านตอนใช้เวลา
infrastructure-setup.html ตั้งเครื่องใหม่ตั้งแต่ศูนย์ หรือมีเครื่องใหม่ join เข้ามาครึ่งวัน อ่านไปทำไป
start-here.html หน้านี้ — อ่านก่อนใช้งานครั้งแรก แล้วเปิดซ้ำเวลาลืมว่าไฟล์ไหนคืออะไร15 นาที
disaster-recovery.html อ่านล่วงหน้าตอนยังไม่มีอะไรเกิด แล้วเปิดซ้ำตอนเครื่อง storage ตาย20 นาที

ถ้าเพิ่งเข้ามาใหม่และระบบตั้งอยู่แล้ว อ่านหน้านี้พอ อีกสองเล่มค่อยเปิดตอนถึงเวลาของมัน

1

ของทั้งหมดมีแค่ 2 ชั้น

สับสนกันตรงนี้บ่อยที่สุด เพราะเห็นโฟลเดอร์ซ้อนกันแล้วนึกว่าเป็นคนละโปรเจกต์ จริงๆ มันคือ repo เดียว clone ครั้งเดียว แล้วข้างในแบ่งเป็นสองชั้นที่หน้าที่ไม่ทับกันเลย

ชั้นอยู่ที่หน้าที่
ketsync/root/ketsync ตัดสินใจ — ใครเป็นตัวหลัก, CT ตัวไหนอยู่เครื่องไหน, เครื่องพังแล้วย้ายไปไหน
tp/root/ketsync/engines/tp ลงมือขน — ย้าย/ก๊อป/เอากลับ ตัว rootfs จริง พร้อม guard ทุกด่าน

กติกาเดียวที่ต้องจำ: ของที่แตะข้อมูลลูกค้าอยู่ใน tp ทั้งหมด ส่วน ketsync ไม่เคยเขียนข้อมูลเอง ถ้าวันไหนเห็น rsync โผล่ในฝั่ง ketsync แปลว่ามีคนวางผิดที่

แต่ไม่ต้องเข้าไปเรียก tp เองในโฟลเดอร์ข้างใน — สั่งจาก ./ketsync ตัวเดียวได้หมด คำสั่งฝั่ง tp ถูกส่งต่อไปแบบไม่แตะอะไรเลย flag เดิม ผลเดิม รหัสออกเดิม

พิมพ์มันไปเรียก
./ketsync migrate <flags>engines/tp/tp migrate
./ketsync replica <flags>engines/tp/tp replica
./ketsync failback <flags>engines/tp/tp failback
./ketsync distribute <flags>อันเดียวที่ไม่ใช่การส่งต่อเฉยๆ — เรียก ct-prepare.sh ให้ก่อน แล้วค่อย tp distribute
./ketsync recall <flags>engines/tp/tp recall
./ketsync isolate <flags>engines/tp/ct-prepare.sh --isolate
./ketsync restore <flags>engines/tp/ct-prepare.sh --restore
./ketsync evacuate <flags>engines/tp/ct-prepare.sh --evacuate
./ketsync statusengines/tp/tp status
./ketsync doctorตรวจฝั่ง ketsync แล้วต่อด้วย tp doctor ให้เลย
./ketsync tp ...ทางลัดตรงไปที่ tp เผื่อมี flag ที่ยังไม่ได้สอน dispatcher

ทุกคำสั่งใช้งานได้จริงแล้วทั้งหมด ไม่มีตัวไหนเป็นโครงเปล่าเหลืออยู่ ชุดล่าสุดคือ isolate restore evacuate ซึ่งเป็นขั้นที่ 1 ของ DR ทั้งขั้น — เมื่อก่อนเป็นคำสั่ง pvesm umount pct สี่ห้าตัวต่อโหนด ที่ต้องทำตามลำดับซึ่งเกือบทุกคนทำสลับ ดูขั้นที่ 1 ใน docs/disaster-recovery.html

2

ไฟล์ไหนคืออะไร ใครแก้ แก้บ่อยแค่ไหน

ตารางนี้คือคำตอบของคำถาม “ทำไม inventory มีหลายที่” — คำตอบสั้นๆ คือมันคนละเรื่องกัน และตอนนี้เปลี่ยนชื่อให้ไม่ชนกันแล้ว

ไฟล์คืออะไรแก้บ่อยแค่ไหน
ketsync.confเครื่องนี้เป็น master หรือ slave, master อยู่ IP ไหนตอนติดตั้ง
nodes.tsvทุกเครื่องที่ระบบนี้จะคุยด้วย — IP กับบทบาท ไม่มีคอลัมน์ชื่อตอนมีเครื่องใหม่
fleet.tsvแผนที่ฟลีต — CT ตัวไหนอยู่บ้านไหน พังแล้วไปไหน (เป็น IP)ตอนรับลูกค้าใหม่
nodes.mapIP → ชื่อ node ของ PVE ระบบสร้างเอง ห้ามแก้มือไม่ต้องแตะ
engines/tp/inventory-migrate.tsvใบงาน migrate — จะย้าย CT ตัวไหนจากเครื่องเก่ามาที่นี่ช่วงย้ายของ แล้วเลิกใช้
engines/tp/inventory-replica.tsvใบงาน replica — จะก๊อป CT ตัวไหนไปเครื่อง backup ทุกคืนแก้บ่อยที่สุด
engines/tp/ctmig.confค่าปรับจูนของ migrate (bandwidth, lane)นานๆ ครั้ง
engines/tp/ctrep.confค่าปรับจูนของ replica + failbackนานๆ ครั้ง

ทุกไฟล์ที่ลงท้าย .sample คือตัวอย่าง ก๊อปแล้วตัดคำว่า sample ออกถึงจะใช้จริง ตัวอย่างจะถูก track ใน git ส่วนตัวจริงไม่ถูก track เพราะมันเป็นข้อมูลของแต่ละไซต์

ชื่อ inventory เปลี่ยนแล้ว ของ migrate เคยชื่อ inventory.tsv เฉยๆ ตอนนี้เป็น inventory-migrate.tsv ถ้าเครื่องไหนยังมีไฟล์ชื่อเก่าอยู่ engine จะไม่เดาให้ แต่จะบอกตรงๆ ว่าให้ rename อะไรเป็นอะไร ดูหัวข้อ 8

log อยู่ที่เดียว

ทุกอย่างเขียนลง /root/ketsync/logs/ ที่เดียว ทั้งสองชั้น ชื่อไฟล์ขึ้นต้นด้วยคำสั่งที่พิมพ์ไป ตามด้วยวันที่ ตอนมีปัญหาจะได้ tar ทั้งโฟลเดอร์ส่งมาทีเดียว ไม่ต้องไล่หาสองที่

ไฟล์ตอบคำถามว่า
ketsync-<วันที่>.logใครสั่ง sync ไปเครื่องไหน ใครถูกเปลี่ยน role และ doctor เจออะไรบ้าง
migrate-<lane>-<วันที่>.logย้ายของจากเครื่องเก่ามาแล้วเกิดอะไรขึ้น
replica-<lane>-<วันที่>.logคืนนั้นก๊อปครบมั้ย ตัวไหนถูกข้าม เพราะอะไร
failback-<วันที่>.logเอาข้อมูลกลับเข้าตัวจริงแล้วผ่านด่านไหนบ้าง
distribute-<วันที่>.logตอน DR กระจายสำเนาไปเครื่องไหน ลง storage อะไร

เก่ากว่า 14 วันถูกลบเองอัตโนมัติ (ของ migrate เก็บ 30 วัน) แต่ละตัวลบเฉพาะไฟล์ของตัวเอง ไฟล์อะไรที่เอามาวางไว้เองในนั้นไม่โดนลบ

ที่เก็บ log ย้ายแล้ว ของเดิมอยู่ที่ engines/tp/logs/ ตอนนี้ทั้งสองชั้นเขียนลง logs/ ข้างบนสุดที่เดียว ของเก่ายังอยู่ที่เดิมและไม่มีอะไรไปลบให้ ถ้าจะรวมก็ mv เอาเอง ส่วน cron ไม่ต้องแก้ — คำสั่งเหมือนเดิม เปลี่ยนแค่ปลายทางที่ log ไปลง

3

3 ตารางนี้คนละคอลัมน์กันจริงๆ

เหตุผลที่ต้องแยกชื่อ ไม่ใช่เรื่องสวยงาม แต่เพราะถ้าเอาไฟล์ผิดมาใส่ engine จะอ่านคอลัมน์เพี้ยนทั้งไฟล์ ดูเทียบกันแล้วจะเห็นว่าไม่มีทางใช้แทนกันได้เลย

fleet.tsv — แผนที่ ไม่ใช่ใบงาน

110 10.100.1.32 10.100.1.32 local-lvm
# ct	home	dr	dst
110	10.100.1.32	10.100.1.32	local-lvm
120	10.100.1.33	10.100.1.33	local-lvm

อ่านว่า “CT 110 ปกติอยู่ที่ 10.100.1.32 ถ้า storage ล่ม ให้ไปขึ้นที่ 10.100.1.32 ลง local-lvm ของเครื่องนั้น” เขียนไว้ล่วงหน้า ไม่ใช่ให้เครื่องเลือกเองตอนตี 3 ทุก IP ที่เขียนตรงนี้ต้องมีแถวใน nodes.tsv ไม่งั้น ketsync doctor จะฟ้อง

สี่คอลัมน์ ต้องมีครบทุกอัน ไม่มีค่า default ให้ — เคยมีคอลัมน์ tier อยู่ตำแหน่งที่ 2 ซึ่งไม่มี engine ไหนอ่านเลย ตอนนี้ตัดทิ้งแล้ว และคอลัมน์ dst คือชื่อ storage บนเครื่องปลายทาง สะกดให้ตรงกับที่ pvesm status ของเครื่องนั้นบอก แถวที่ไม่มีจะถูกปฏิเสธ ไม่ใช่เดาให้

inventory-migrate.tsv — ใบงานย้ายเข้ามา

10.100.1.23 300 99100 10.100.1.19 tank-hdd-nas
# old_node    old_ctid  new_ctid  new_node      storage
10.100.1.23   300       99100     10.100.1.19   tank-hdd-nas

อ่านว่า “CT 300 บนเครื่องเก่า 10.100.1.23 ให้มาเกิดใหม่เป็น CT 99100 บน 10.100.1.19 ใช้ storage ชื่อ tank-hdd-nas” ใช้เฉพาะช่วงย้ายของเข้าฟลีต ย้ายเสร็จก็ไม่ต้องใช้อีก

inventory-replica.tsv — ใบงานก๊อปทุกคืน

105 ssd
# src_ctid  [tgt_ctid]  [storage-assert]  [dest]
105                                       ssd
113         8113        tank-ssd-nas      ssd

อ่านว่า “ก๊อป CT 105 ไปที่ pool ssd” ส่วนคอลัมน์หลังตัวแรกใส่ได้ไม่เรียงลำดับ engine ดูจากรูปแบบเอาเองว่าอันไหนคืออะไร ไฟล์นี้ ct-replica.sh กับ ct-failback.sh ใช้ร่วมกัน

ทุกไฟล์ .tsv มีบรรทัดหัวตารางเป็นคอมเมนต์อยู่ข้างบนแถวข้อมูลแล้ว เปิดไฟล์ปุ๊บเห็นเลยว่าคอลัมน์ไหนคืออะไร ไม่ต้องเปิดคู่มือ บรรทัดที่ขึ้นต้นด้วย # ทุก parser ข้ามหมด

3

ไม่มีตรงไหนให้พิมพ์ hostname เลย

ทุกช่องที่คนกรอกเป็น IP หมด ทั้ง nodes.tsv, fleet.tsv และ inventory-migrate.tsv เหตุผลไม่ใช่ความสวยงาม แต่เพราะเครื่อง storage อยู่นอก cluster โดยตั้งใจ มันไม่มีทั้ง /etc/hosts ของ cluster และ DNS ของ cluster — ที่อยู่ซึ่งใช้ได้ต่อเมื่อมีคนตอบชื่อให้ คือที่อยู่ที่จะใช้ไม่ได้พอดีในวันที่เกิดเหตุ

แต่ PVE เก็บ config ของ CT ไว้ที่ /etc/pve/nodes/<node-name>/ ฉะนั้น “ชื่อ node” ยังจำเป็นในฐานะข้อมูล — แค่ไม่จำเป็นในฐานะสิ่งที่คนต้องพิมพ์ ระบบจะไปถามเอาเองแล้วเก็บไว้ที่ nodes.map

ชื่อ node ที่ไหนได้มาจาก
nodes.mapketsync ถาม cluster ผ่านเครื่อง backup ตอนสั่ง doctor
BKP_NODEengine อ่าน /etc/pve/local ของเครื่อง backup เอง ไม่ต้องตั้ง
CT_NODEengine อ่านจาก path ของ config ที่เจอใน /etc/pve

ยังตั้ง BKP_NODE เองได้อยู่ แต่ความหมายเปลี่ยนไป มันไม่ใช่ “บอกให้รู้” แต่แปลว่า “ถ้าเครื่องปลายทางไม่ใช่ตัวนี้ ให้ปฏิเสธ” engine จะตรวจค่าที่ตั้งไว้เสมอ ไม่เชื่อตามที่พิมพ์ ถ้าไม่ได้ตั้ง มันก็ถามเอาเองแล้วบอกใน log ว่าได้ชื่ออะไรมา

4

ติดตั้งที่เครื่องไหนบ้าง

สองเครื่อง — เครื่อง storage กับเครื่อง backup ส่วน compute node ไม่ต้องลงอะไรเลย มันแค่ต้องมี ssh key กับตั้งชื่อ storage ให้ตรงกัน

ต้องอยู่ path เดียวกันทุกเครื่อง ใช้ /root/ketsync ให้เหมือนกันหมด ไม่ใช่เรื่องความสวยงาม — ketsync sync ส่งไปที่ path ที่ตัวมันเองติดตั้งอยู่ ถ้าอีกเครื่องเก็บไว้ที่อื่น ตารางจะไม่ไปถึงเลย ตอนนี้มันฟ้องชื่อเครื่องออกมาให้แล้ว แต่ก่อนหน้านี้เงียบสนิท

git clone /root/ketsync
# on the STORAGE node - this is the master
git clone <this repo> /root/ketsync
cd /root/ketsync

cp ketsync.conf.sample  ketsync.conf
cp nodes.tsv.sample     nodes.tsv
cp fleet.tsv.sample     fleet.tsv

cd engines/tp
cp inventory-replica.sample.tsv  inventory-replica.tsv
cp inventory-migrate.sample.tsv  inventory-migrate.tsv   # only while migrating

แก้ nodes.tsv ให้ครบทุกเครื่องก่อนอย่างอื่น เพราะทุก IP ที่ระบบนี้จะใช้มาจากไฟล์นี้ที่เดียว ถ้าเครื่องไหนไม่มีแถวในนี้ ระบบจะหยุดแล้วบอก ไม่เดา IP ให้

เครื่อง backup ต้องมีด้วย และต้องทำวันธรรมดา

ไม่ใช่เพื่อรัน replica — มันรันไม่ได้ ดูหัวข้อถัดไป — แต่เพราะวันที่เครื่อง storage ตาย เครื่องที่เก็บโค้ดไว้ก็ตายไปด้วย เครื่อง backup คือที่ที่คุณจะยืนสั่ง distribute ตอนนั้น

git clone /root/ketsync
# on the BACKUP node - same path, on purpose
git clone <this repo> /root/ketsync
cd /root/ketsync

cp ketsync.conf.sample  ketsync.conf     # KS_ROLE=slave
$EDITOR engines/tp/ctrep.conf             # BW_TOTAL_MB for THIS machine
./ketsync doctor                          # builds nodes.map here

ตาราง 4 ไฟล์ (nodes.tsv, fleet.tsv, inventory ทั้งสอง) ไม่ต้องก๊อปมา เดี๋ยว ketsync sync ส่งมาให้เอง ส่วน .conf ทั้งหมดกับ nodes.map ไม่มีวันถูกส่ง ต้องทำเองที่เครื่องนั้น เพราะมันเป็นของเฉพาะเครื่อง

ctrep.conf มาพร้อม clone อยู่แล้ว ที่ต้องดูคือ BW_TOTAL_MB ให้ตรงกับสายของเครื่องนั้น ค่าที่เหลือใน ไฟล์นี้เหมือนกันทุกเครื่อง — distribute อ่านไฟล์นี้ตอน DR

เครื่อง backup ทำอะไรได้ ทำอะไรไม่ได้

คำสั่งสั่งจากเครื่อง backup ได้มั้ย
sync · role · doctor · statusได้
distributeได้ — และนี่คือเหตุผลหลักที่ต้องลงไว้
replica · failback · migrate ไม่ได้ และจะไม่ได้ตลอดไป ทั้งสามตัวนี้ทำ ZFS snapshot กับ loop-mount ไฟล์ image ของจริง ซึ่งอยู่บนเครื่อง storage

เปลี่ยน role ไม่ได้ย้ายดิสก์ตามไปด้วย คำว่า master ในระบบนี้แปลว่า “เครื่องที่เป็นเจ้าของตารางและเป็นคนส่ง” เท่านั้น

เครื่อง storage อยู่นอก cluster โดยตั้งใจ แปลว่ามันไม่มี DNS และไม่มี /etc/hosts ของ cluster ทุกอย่างที่คนพิมพ์ในระบบนี้จึงเป็น IP ส่วนชื่อ node ที่ PVE บังคับให้ต้องมี (เพราะ config อยู่ใต้ /etc/pve/nodes/<node>/) ระบบไปถามจาก cluster เอง แล้วเก็บไว้ใน nodes.map ซึ่งไม่มีใครแก้ด้วยมือ

ssh ที่ต้องมีจริงๆ มีสามเส้น: storage → backup (ขาดไม่ได้เลย), storage → compute ทุกเครื่อง (ด่าน B1 ของ failback ถาม pct status จากเครื่องนั้นโดยตรง เพราะคำถามนี้ไม่ต้องใช้ quorum และยังตอบได้แม้ node นั้นหลุด cluster), และ compute ↔ backup (distribute กับ recall สั่ง rsync ให้ทำงานบนเครื่องปลายทาง)

4

ตั้ง sync ให้ storage เป็น master และ backup เป็น slave

หัวข้อนี้คือส่วนที่คนงงกันบ่อยที่สุด สรุปสั้นๆ ก่อน: มีเครื่องเดียวที่แก้ตารางได้ และเป็นคนส่งให้เครื่องอื่น ระบบไม่เลือกให้เอง ไม่มีการโหวต ไม่มีการสลับอัตโนมัติ — เพราะสองเครื่องแยกไม่ออกระหว่าง “อีกฝั่งตายแล้ว” กับ “ฉันติดต่ออีกฝั่งไม่ได้” และถ้าเดาผิดจะกลายเป็นสองเครื่องเขียนทับ dataset เดียวกันพร้อมกัน

ตั้งค่าที่ละเครื่อง — ต่างกันแค่สองบรรทัด

KS_ROLE=master
# on the STORAGE node - ketsync.conf
KS_ROLE=master
KS_MASTER_IP=10.100.1.17      # this machine
KS_ROLE=slave
# on the BACKUP node - ketsync.conf
KS_ROLE=slave
KS_MASTER_IP=10.100.1.17      # the storage node

ห้าม scp ไฟล์ ketsync.conf ข้ามเครื่อง ไฟล์นี้มี KS_ROLE อยู่ ถ้าก๊อปของ master ไปวางที่ slave ทุกเครื่องจะเชื่อว่าตัวเองเป็น master และนั่นคือสภาพที่ทั้งระบบนี้ออกแบบมาเพื่อเลี่ยง ตัว ketsync sync มีบัญชีดำกันไฟล์นี้ไว้ และหยุดทั้งรอบถ้าเจอ

ไฟล์ไหนถูกส่ง ไฟล์ไหนไม่ถูกส่ง

ไฟล์ส่งมั้ยทำไม
nodes.tsvส่งทุกเครื่องต้องเห็น IP ชุดเดียวกัน
fleet.tsvส่งเครื่องที่รับช่วงต่อต้องรู้ว่า CT ไหนไปไหน
inventory-replica.tsvส่งรายการงานของ replica และ recall
inventory-migrate.tsvส่งเหมือนกัน สำหรับ migrate
ketsync.confไม่ส่งมี KS_ROLE — ส่งแล้วทุกเครื่องเป็น master
ctrep.conf · ctmig.confไม่ส่งมี BW_TOTAL_MB ซึ่งขึ้นกับสายของแต่ละเครื่อง
nodes.mapไม่ส่งสร้างเองจาก cluster ด้วย ketsync doctor

ส่งจริงๆ

./ketsync sync
# on the MASTER, after editing any table
./ketsync sync

มันจะไปถามทุกเครื่องใน nodes.tsv ว่ามี ketsync ติดตั้งอยู่มั้ย เครื่องไหนไม่มีก็ข้ามไปเงียบๆ (compute node ปกติไม่มี) เครื่องไหนติดตั้งไว้คนละ path มันจะบอกชื่อเครื่องนั้นออกมา

sync ไม่ใช่ของอัตโนมัติ แก้ตารางที่ master แล้วต้องสั่งเอง ไม่งั้นเครื่อง backup จะถือรายการของเดือนที่แล้วอยู่ โดยไม่มีอะไรบอก

เจอคำว่า FORKED ทำยังไง

ทุกไฟล์ที่ถูกส่งมีบรรทัด # generation: N อยู่ข้างใน เลขนี้ใช้เรียงว่าอันไหนใหม่กว่า แต่มันไม่ได้บอกว่าเนื้อในเหมือนกัน ถ้าสองเครื่องมีเลขเท่ากันแต่เนื้อในต่างกัน แปลว่าแตกกันแล้ว — และนี่คือสภาพปกติ ของฟลีตที่เพิ่งติดตั้ง เพราะทุกเครื่องเริ่มจาก generation ที่ติดมากับไฟล์ .sample เหมือนกันหมด

ตอนเจอ มันจะหยุดและไม่ส่งอะไรเลย เพราะไม่มีทางรู้ว่าฝั่งไหนถูก

./ketsync sync --diff
# 1. read what actually differs - changes nothing
./ketsync sync --diff

# 2. edit the file until THIS machine's copy is the right one
$EDITOR fleet.tsv

# 3. say "mine is the one" - raises the generation above every machine, then pushes
./ketsync sync --bump fleet.tsv

ระบุชื่อไฟล์เสมอ --bump เฉยๆ จะเคลียร์ทุกไฟล์ที่แตกกันพร้อมกัน ซึ่งถูกต้องก็ต่อเมื่อคุณอ่าน diff ครบทุกไฟล์แล้วจริงๆ

วันที่ต้องให้เครื่อง backup เป็นคนสั่งแทน

ตอนเครื่อง storage ตาย เครื่อง backup ต้องสั่ง distribute กับ recall ได้ ซึ่งทำได้อยู่แล้วโดยไม่ต้องแก้ KS_ROLE — role คุมแค่ว่าใครเป็นคนส่งตาราง ไม่ได้คุมว่าใครสั่งงานได้

ที่ต้องแก้ KS_ROLE=master ที่เครื่อง backup คือกรณีที่ ต้องแก้ตารางแล้วส่งต่อ ระหว่างที่เครื่อง storage ยังไม่กลับมา เช่นย้าย CT ไปเครื่องอื่นแล้วต้องแก้คอลัมน์ dr แก้ด้วยมือหนึ่งบรรทัด แล้วอย่าลืมแก้กลับตอน เครื่อง storage ฟื้น ไม่งั้นจะมีสองเครื่องที่คิดว่าตัวเองเป็นเจ้าของตาราง

5

ลำดับคำสั่ง — อันนี้ห้ามข้าม

ทุกครั้งที่ตั้งเครื่องใหม่ หรือแก้อะไรที่ใหญ่กว่าเพิ่ม CT หนึ่งตัว ให้ไล่ตามนี้

  1. เช็กว่าต่อกันติดก่อน ยังไม่แตะข้อมูลอะไรทั้งนั้น
    cd /root/ketsync
    cd /root/ketsync
./ketsync doctor

    คำสั่งเดียวตรวจทั้งสองชั้น: ssh ถึงเครื่องไหนบ้าง, ชื่อ node ดึงมาได้ไหม, ทุกไฟล์มีเลข generation ไหม, IP ใน fleet.tsv มีแถวใน nodes.tsv ครบไหม, engine อยู่ครบและสั่งรันได้ไหม แล้วปิดท้ายด้วย tp doctor เรื่อง storage กับ state รหัสออกเป็นตัวที่แย่กว่าของสองชั้น

  2. ซ้อมก่อน ด้วย CT ที่ไม่สำคัญตัวเดียว — --dry-run เดินผ่าน guard ทุกด่านเหมือนของจริง ต่างกันแค่ไม่เขียนอะไรลงดิสก์เลย
    ./ketsync replica --dry-run --ctid 110
    ./ketsync replica --dry-run --ctid 110
  3. ถ้าซ้อมผ่าน ค่อยรันจริงทีละตัว
    ./ketsync replica --ctid 110
    ./ketsync replica --ctid 110
  4. รันทั้ง lane แยกตาม storage เพราะ bandwidth ceiling คิดเป็น lane
    ./ketsync replica --storage tank-hdd-nas
    ./ketsync replica --storage tank-hdd-nas
  5. ค่อยใส่ cron — ใส่ทีละ lane ไม่ใส่พร้อมกันสองอัน
    */15 * * * * /root/ketsync/engines/tp/ct-replica.sh --storage tank-hdd-nas
    */15 * * * * /root/ketsync/engines/tp/ct-replica.sh --storage tank-hdd-nas
*/15 * * * * /root/ketsync/engines/tp/ct-replica.sh --storage tank-ssd-nas
6

งานประจำ มี 3 อย่าง

ทั้ง 3 engine ใช้ flag ชุดเดียวกัน ตั้งใจให้จำชุดเดียวพอ

flagแปลว่าใช้ได้กับ
--allทุกแถวใน inventoryทั้ง 5 ตัว
--ctid <id>เฉพาะ CT ตัวเดียวทั้ง 5 ตัว
--dry-runเดินผ่าน guard ครบ ไม่เขียนอะไร แล้วพิมพ์แผนออกมาทั้ง 5 ตัว
--storage <id>ทำเฉพาะ lane นั้นmigrate, replica
--dest replica-hdd|replica-ssdเฉพาะ CT ที่ตัวสำรองอยู่ pool นั้นfailback
--listดูอย่างเดียว ใครอยู่ไหน สถานะอะไรfailback
--finalรอบสุดท้าย ทับ image ตัวจริงfailback
--stoppedต้นทางถูกปิดอยู่ ไม่ต้องรอmigrate
--to <ip>บังคับว่าจะไปลงเครื่องไหนdistribute
--dst <id>บังคับว่าจะลง storage อะไรdistribute
--node <ip>ทำทั้งเครื่องนั้น ไม่ใช่ราย CTevacuate, restore
--no-prepareวางอย่างเดียว ไม่ต้องเตรียมโหนดให้distribute
-yตัดสินใจไปแล้ว ไม่ต้องถาม — ข้ามแค่คำถาม ไม่ข้ามด่านทุกตัว
--finalรอบสุดท้าย ต้องปิด 9xxx ก่อนrecall
--listดูแผนอย่างเดียวdistribute, recall

รหัสออกก็ชุดเดียวกันทั้ง 5 ตัว: 0 ปกติ, 1 มีอย่างน้อยหนึ่ง CT ไม่ผ่านหรือถูกข้าม, 2 ปฏิเสธตั้งแต่ยังไม่แตะอะไร ตัวกรองที่ไม่ match แถวไหนเลยไม่คืน 0 เด็ดขาด

อยากทำอะไรสั่ง
ย้าย CT จากเครื่องเก่าเข้าฟลีต./ketsync migrate --storage <id>
ก๊อป CT ไปเครื่อง backup (ทุกคืน)./ketsync replica --storage <id>
เอาข้อมูลจากตัวสำรองกลับเข้าตัวจริง./ketsync failback --list
ดูว่ารอบล่าสุดของแต่ละ CT เป็นยังไง./ketsync status
เครื่อง storage ตาย ต้องกระจาย CT ไปรันที่ compute./ketsync distribute --list
ตรวจว่าทุกอย่างต่อกันติดไหม./ketsync doctor
ส่งตารางที่แก้แล้วไปให้ทุกเครื่อง./ketsync sync
เครื่องนี้เป็นอะไรอยู่./ketsync role
เอา CT ตัวจริงออกจากเน็ต ตอน storage ตาย./ketsync isolate --ctid 110
คืนค่าที่ isolate เปลี่ยนไว้./ketsync restore --all
กู้ทั้งโหนด ปิด storage ที่ตาย umount แล้วปิดตู้./ketsync evacuate --node <ip>

คำสั่งที่เขียนอะไรจะถามก่อน และคำสั่งเปล่าๆ จะไม่ทำ

พิมพ์ชื่อคำสั่งเฉยๆ เช่น ./ketsync distribute มันจะไม่ทำอะไร แต่จะพิมพ์รายการ flag ออกมาให้ แล้วปฏิเสธด้วยรหัส 2 — เพราะคำสั่งเปล่าๆ อาจแปลว่าทั้งฟลีตก็ได้ และ --all ที่พิมพ์เพิ่มสี่ตัวอักษรคือหลักฐานว่าตั้งใจ ส่วน doctor กับ status ไม่มีอะไรให้ระบุขอบเขต พิมพ์เปล่าๆ ถูกต้องแล้ว

ส่วนคำสั่งที่เขียนของจริงจะถามก่อนหนึ่งครั้ง โดยบอกว่ามันจะเขียนอะไร ไม่ใช่ถามว่าแน่ใจมั้ย กด Enter เฉยๆ = ไม่ทำ

this OVERWRITES each DR copy on the backup node with the live image.
  see exactly what it would do first:  ./ketsync replica --all --dry-run
proceed? [y/N]

cron ต้องเติม -y ถ้าไม่มีหน้าจอและไม่มี -y มันจะปฏิเสธด้วยรหัส 2 ไม่ใช่ตอบว่าไม่แล้วออก 0 เงียบๆ — เพราะ cron ที่รายงานสำเร็จทุกคืนโดยไม่ได้ก๊อปอะไรเลย คือความเงียบที่หน้าตาเหมือนความสำเร็จ -y แปลว่าตัดสินใจไปแล้ว มันข้ามแค่คำถาม ไม่ข้ามด่านสักด่าน และไม่มี --force ให้ใช้ ตั้งใจไม่ให้มี สั่ง ./ketsync doctor มันจะไล่ crontab บอกให้เองว่าบรรทัดไหนยังไม่มี

บรรทัด cron ที่เรียก engine ตรงๆ ไม่ต้องแก้อะไร คำถามอยู่ที่ชั้น ketsync ซึ่งเป็นที่ที่คนยืนอยู่ ส่วน cron เรียก engine

failback เริ่มด้วย --list เสมอ มันจะบอกว่าตอนนี้ CT ตัวไหนพร้อมเอากลับบ้าง และเครื่องไหนที่คุยไม่ได้ ห้ามข้ามไป --final เลย เพราะ --final คือรอบที่ทับ image ตัวจริง

แก้ตารางแล้วต้องสั่ง sync เอง

ไม่มี cron ไม่มีอะไรทำให้อัตโนมัติ แก้ตารางที่เครื่อง master แล้วต้องพิมพ์ ./ketsync sync เอง ถ้าลืม เครื่อง backup จะถือรายการของเดือนที่แล้ว และไม่มีอะไรบอกคุณเลย

ที่ส่งคือ 4 ตาราง — nodes.tsv, fleet.tsv และ inventory ทั้งสอง ที่ไม่ส่งคือ .conf ทุกไฟล์ กับ nodes.map เพราะ ketsync.conf มีบรรทัด KS_ROLE อยู่ ถ้าส่งไป ทุกเครื่องจะคิดว่าตัวเองเป็น master

ถ้าเจอคำว่า FORKED แปลว่าสองเครื่องถือ generation เลขเดียวกันแต่เนื้อไฟล์ไม่เหมือนกัน ซึ่งเป็นสภาพปกติของเครื่องที่เพิ่งติดตั้ง เพราะทุกเครื่องเริ่มที่เลขเดียวกันจาก .sample ตอนนั้น sync จะหยุดและไม่ส่งอะไรเลย — มันไม่รู้ว่าฝั่งไหนถูก ไล่ตามนี้

ทำอะไรสั่ง
ดูว่าต่างกันตรงไหน ไม่เขียนอะไร./ketsync sync --diff
แก้ไฟล์ที่เครื่องนี้ให้เป็นอันที่ถูก$EDITOR <file>
ยืนยันว่าของเครื่องนี้คือของถูก ทีละไฟล์./ketsync sync --bump <file>
ยืนยันทุกไฟล์ที่แตกกันพร้อมกัน./ketsync sync --bump

ปกติ inventory สองไฟล์จะแตกพร้อมกัน แนะนำให้ระบุชื่อไฟล์ทีละอัน — --bump เปล่าๆ ตัดสินให้ทุกไฟล์ในรอบเดียว ซึ่งดีถ้าคุณอ่าน diff ครบทุกอันแล้ว แต่ถ้าอ่านแค่อันเดียว อีกอันก็ถูกทับไปโดยที่ยังไม่ได้คิด

ไม่มี engine ตัวไหนสั่งเปิดหรือปิด CT ให้ ทุกตัวจะพิมพ์คำสั่ง pct start ออกมาให้คนกด เพราะจังหวะที่ service ลูกค้ากลับมา เป็นจังหวะที่ต้องมีคนนั่งดูหน้าจออยู่

7

เจอคำปฏิเสธแบบนี้ แปลว่าอะไร

engine ทุกตัวเลือกที่จะ “ปฏิเสธเสียงดัง” มากกว่า “ทำต่อแบบเงียบๆ” ฉะนั้นเจอ error ไม่ได้แปลว่าพัง ส่วนใหญ่แปลว่ามันกันไว้ให้แล้ว

ข้อความแปลว่าทำยังไง
inventory not foundยังไม่ได้ก๊อปไฟล์ตัวอย่าง หรือยังใช้ชื่อเก่าอยู่อ่านบรรทัดถัดไป มันบอกคำสั่งที่ต้องพิมพ์ไว้แล้ว
GUARD B1CT ตัวจริงยังไม่ stop หรือถามสถานะไม่ได้ปิด CT ตัวจริงก่อน ถ้าถามไม่ได้ให้เช็กว่า node ยังอยู่ใน cluster
GUARD R4เลข VMID ปลายทางมีเจ้าของอยู่แล้วในเครื่องอื่นแก้เลขใน inventory-replica.tsv ก่อนรันใหม่
GUARD R9bridge ที่ใช้เก็บตัวสำรองมีทางออกเน็ตห้ามรันต่อ — ตัวสำรองใช้ IP เดียวกับตัวจริง ถ้าออกเน็ตได้คือชนกัน
GUARD B7ทำ snapshot กันพลาดก่อน --final ไม่สำเร็จแก้ให้ snapshot ได้ก่อน หรือถ้ายอมรับความเสี่ยงจริงๆ ค่อยใส่ --no-snapshot ด้วยมือ
net line has no bridge=config ต้นทางมี net ที่ไม่ระบุ bridgeแก้ config ต้นทาง — engine จะไม่ก๊อปโดยตัด interface ทิ้งเงียบๆ
source_downstorage ต้นทางทั้งก้อนหายไป ไม่ใช่ CT ตัวเดียวไม่ต้องแก้อะไรใน inventory มันจะหายเองเมื่อ storage กลับมา
PAUSED by pause/<ctid>มีคนสั่งพัก CT ตัวนี้ไว้ด้วยมือลบไฟล์ pause/<ctid> เมื่อพร้อมให้กลับมา sync

รหัสออกก็มีความหมาย: 0 คือปกติ, 1 คือมีอย่างน้อยหนึ่ง CT ไม่ผ่าน, 2 คือยังไม่ได้เริ่มทำอะไรเลยเพราะตั้งค่าไม่ครบ ตัวกรองที่ไม่ match แถวไหนเลยจะไม่คืน 0 เด็ดขาด เพราะใต้ cron แล้ว “0 แต่ไม่ได้ทำอะไร” หน้าตาเหมือนคืนที่ปกติ

ถ้าเครื่องมีของเดิมติดตั้งอยู่แล้ว

เครื่องที่ลงไว้ก่อนหน้านี้จะมีโฟลเดอร์ /root/ct-replica/ หรือ /root/tp/ อยู่ อย่าเพิ่งลบ ทำตามนี้ทีละข้อ แล้วค่อยลบตอนมั่นใจ

  1. clone ของใหม่ไว้คนละที่ก่อน ยังไม่แตะ cron
    git clone /root/ketsync
    git clone <this repo> /root/ketsync
  2. ย้ายไฟล์ข้อมูลเดิมมา แล้วเปลี่ยนชื่อให้ตรงชื่อใหม่
    cd /root/ketsync/engines/tp
    cd /root/ketsync/engines/tp
cp /root/tp/inventory.tsv          ./inventory-migrate.tsv
cp /root/tp/inventory-replica.tsv  ./inventory-replica.tsv
cp /root/tp/ctmig.conf             ./ctmig.conf
cp /root/tp/ctrep.conf             ./ctrep.conf
cp -a /root/tp/state               ./state

    ถ้าลืมเปลี่ยนชื่อ engine จะไม่เดาให้ แต่จะบอกว่าไฟล์ชื่อเก่ายังอยู่และให้ rename เป็นอะไร

  3. ซ้อมด้วย CT ที่ไม่สำคัญตัวเดียว ตอนนี้ cron ยังชี้ของเก่าอยู่ ยังไม่มีอะไรเปลี่ยน
    ./ketsync replica --dry-run --ctid 
    ./ketsync replica --dry-run --ctid <one unimportant ctid>
  4. ย้าย cron ทีละ lane ไม่ย้ายพร้อมกัน ดูสักรอบสองรอบว่า log ออกมาปกติก่อนค่อยย้าย lane ถัดไป
  5. ถอยกลับได้เสมอ — ของเก่ายังอยู่ครบ แค่ชี้ cron กลับไปที่ path เดิม ไม่ต้อง restore อะไร

ทำไมต้องเปลี่ยนชื่อ ตอน engine หลายตัวมาอยู่โฟลเดอร์เดียวกัน ชื่อกลางๆ อย่าง inventory.tsv กลายเป็นของทุกคนและไม่ใช่ของใครเลย ทั้งที่คอลัมน์ข้างในคนละเรื่องกันสิ้นเชิง แยกชื่อแล้วเอาไฟล์ผิดมาใส่ไม่ได้อีก
