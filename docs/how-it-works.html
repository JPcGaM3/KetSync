ทิศทางนี้ไม่มีวันกลับด้าน ตราบใดที่ยังไม่มีภัยพิบัติ ตัวจริงคือความจริงเสมอ สำเนาเป็นแค่ปลายทาง

  1. อัตโนมัติ cron บนเครื่อง storage เรียก ct-replica.sh หนึ่งรอบต่อ source storage หนึ่งเส้น แต่ละเส้นได้แบนด์วิดท์ BW_TOTAL_MB / LANES ของตัวเอง เพดานรวมจึงไม่ทะลุไม่ว่าเส้นไหนจะรันพร้อมกัน
  2. อ่าน inventory-replica.tsv ทีละแถว แต่ละแถวบอก CT และ pool ปลายทางของตัวเอง แถวที่ไม่บอก pool ทำให้ทั้งไฟล์ถูกปฏิเสธ ไม่มีค่า default ให้เดา
  3. snapshot ตัวจริงบน ZFS แล้ว clone ออกมา mount แบบ ro,noload — อ่านจากสำเนาชั่วขณะ ไม่ใช่จากดิสก์ที่ลูกค้ากำลังเขียน ข้อมูลที่ได้จึงเป็นภาพ ณ วินาทีเดียว ไม่ใช่ภาพที่ขยับระหว่างก๊อป
  4. rsync -aHAX --delete ไปลง dataset ของสำเนาบนเครื่อง backup
  5. รอบแรกของ CT ตัวนั้นเท่านั้นที่เขียน config 8300 ให้ โดยเอา net ของตัวจริงมาทั้งดุ้น — IP เดิม MAC เดิม VLAN เดิม — แล้วเปลี่ยนแค่ bridge เป็น vmbr99 ซึ่งไม่มีสายออกไปไหน IP ซ้ำกันจึงไม่เป็นอันตราย และวันที่ต้องใช้จริงก็แก้ฟิลด์เดียว
  6. ปลด clone ทิ้ง แล้วขึ้นรอบถัดไป

ด่านที่ทำงานทุกรอบ

ด่านถามอะไรถ้าไม่ผ่าน
R1dataset ปลายทาง mount อยู่จริงมั้ย ถ้าไม่ rsync จะเทลง root filesystem ของเครื่อง backup จนเต็ม
R2สำเนาที่จะเขียนทับ กำลังรันอยู่หรือเปล่า สำเนาที่รันอยู่แปลว่ามีคนใช้มันอยู่ ข้าม
R4VMID ปลายทางเป็นของ guest อื่นในคลัสเตอร์มั้ย rsync --delete จะล้าง rootfs ของคนอื่นทิ้ง
R8สำเนาเดิมอยู่ pool เดียวกับที่แถวนี้สั่งมั้ย ย้าย pool ทีหลังทำให้สำเนาแตกเป็นสองที่
R9vmbr99 บนเครื่อง backup มี uplink หรือยัง ถ้ามี สำเนาจะตอบได้ = สองเครื่องบน IP เดียว หยุดทั้งรอบ
R13มี 9xxx ของ CT ตัวนี้อยู่ในคลัสเตอร์มั้ย มี = กำลัง DR อยู่ ห้ามเอาของเก่าทับสำเนา ข้ามและ exit ไม่ใช่ 0
R14มีเครื่องอื่นกำลังเขียนสำเนาตัวนี้อยู่มั้ย lock อยู่บนเครื่องที่ถือสำเนา ไม่ใช่บนเครื่องที่เขียน

PAUSE ไฟล์เปล่าๆ ชื่อ engines/tp/PAUSE บนเครื่องที่รัน cron ถ้ามีอยู่ replica จะไม่ทำอะไรเลย ใช้ตอน failback ซึ่งเป็นช่วงเดียวที่สำเนาใหม่กว่าตัวจริง

สิ่งที่วิ่งคู่กันไป

  • ketsync sync ส่งตารางที่ต้องเหมือนกันทั้งฟลีต — nodes.tsv fleet.tsv และ inventory ทั้งสอง — เรียงด้วยเลข generation เครื่องที่ถือของเก่ากว่าจะทับของใหม่ไม่ได้ ketsync.conf ไม่ถูกส่ง เพราะมันถือ KS_ROLE
  • ketsync doctor ไล่ ssh ทุกแถวใน nodes.tsv ดูว่า engine อยู่ครบและรันได้ เลข generation ตรงกัน และสำเนาแต่ละตัวเก่าแค่ไหน

สำเนารอบล่าสุดก่อนเกิดเรื่อง ยังปิดอยู่
  1. คนกด ยืนยันว่าตายจริง ไม่ใช่แค่ช้า เครื่องที่ ping ติดแต่ NFS ค้าง ยังไม่ใช่เครื่องที่ตาย และเช็ค quorum ก่อนทุกอย่าง ถ้า /etc/pve เขียนไม่ได้ ขั้นที่เหลือจะไปพังตอนท้ายสุดซึ่งแพงที่สุด
  2. คนกด ทุก CT ที่จะย้าย ตั้ง onboot 0 ก่อนไปยุ่งกับ mount คำสั่งนี้เขียนลง /etc/pve ไม่ได้ใช้อะไรจาก storage ที่ตาย ถ้าเครื่อง compute รีบูตระหว่างที่กำลังแก้ อันนี้คือสิ่งเดียวที่กัน CT ไม่ให้ขึ้นเอง
  3. คนกด กู้โหนดให้ตอบสนอง ปิด storage ที่ตายก่อน แล้วค่อย umount -f -l แล้วค่อย restart pvestatd สลับลำดับไม่ได้ ถ้า restart ก่อนถอด mount มันจะไปค้างที่เดิม
  4. คนกด เอาตัวจริงออกจากทาง มีสองทาง ปิดมัน ซึ่งทำได้เมื่อ mount ที่ตายถูกถอดแล้ว หรือ ย้ายทุก net line ไป vmbr99 ซึ่งใช้ได้แม้ตอนที่ปิดไม่ลง เพราะเขียนแค่ /etc/pve แล้ว hotplug ทันที

ทางที่สองไม่ได้ปิดมัน มันยังเป็น pending writer อยู่ — I/O ค้างตอนนี้ แต่วินาทีที่ storage กลับมามันจะเขียนต่อ ต้องปิดให้ได้ก่อนถึงตอนนั้น ด่าน B1 ของ failback จะไม่ยอมเขียนกลับจนกว่าจะปิดสนิท

เก็บกวาด

ข้อนี้คนข้ามบ่อยที่สุด และเป็นข้อที่ทำให้ครั้งหน้าชนกับครั้งนี้

  5. ลบ PAUSE แล้วรัน replica หนึ่งรอบด้วยมือ ต้องได้ failed=0 ถึงจะถือว่าจบ

สรุปว่าใครตัดสินใจอะไร

ขั้นใครทำทำไมถึงเป็นแบบนั้น
replica ทุกรอบcron ทิศทางเดียว ตัวจริงคือความจริงเสมอ ไม่มีอะไรให้ตัดสินใจ
ประกาศว่า storage ตายคน เครื่องแยกไม่ออกระหว่าง "มันตาย" กับ "ฉันติดต่อไม่ได้"
