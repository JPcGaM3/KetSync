04 — ซ้อมภัยพิบัติ

ดับ storage เทียมด้วย iptables แล้วเดินให้ครบวง — สูตรจากรอบที่ซ้อมจริง

ต้องใช้ CT ทดสอบเท่านั้น อ่านข้อ 0 ก่อนเริ่ม
0

ซ้อมทำไม และเงื่อนไขก่อนเริ่ม

ทุกขั้นในหน้านี้เคยรันจริงบนฟลีตนี้แล้ว (ครั้งล่าสุด 2026-08-16 กับ CT 110/120) สูตรนี้คือบันทึกของรอบนั้น — ซ้อมปีละสองครั้งก็พอ แต่ครั้งแรกต้องมี เพราะหน้า 05 อ่านง่ายขึ้นสิบเท่าเมื่อเคยเห็นของจริงมาแล้ว

ใช้ CT ทดสอบเท่านั้น การซ้อมตัด storage จริง CT บน storage นั้นจะโดน I/O error ทุกตัว ไม่ใช่เฉพาะตัวที่ตั้งใจซ้อม ถ้าฟลีตมี CT ลูกค้าปนอยู่ ห้ามทำวิธีนี้ — ซ้อมได้แค่ระดับ --dry-run

  • ./ketsync doctor เขียวทั้งฉบับ และรอบ replica ล่าสุด failed=0
  • conf/fleet.tsv มีแถวของ CT ที่จะซ้อมครบ (ct, home, dr, dst)
  • ตั้ง watch แล้ว จะได้เห็นเมลจริงระหว่างซ้อมด้วย
1

ตัด storage ให้ตายเทียม

ใช้ iptables ตัดทาง ไม่ต้องถอดปลั๊กจริง — ผลเหมือนกันในสายตาของทุก guard (mount ค้าง, stat ไม่ตอบ, I/O ค้าง D state)

iptables -I OUTPUT -d 10.100.1.17 -j DROP # on EVERY node
# on EVERY compute node AND the backup node
iptables -I OUTPUT -d 10.100.1.17 -j DROP
iptables -I INPUT  -s 10.100.1.17 -j DROP

ต้องตัดทุกเครื่อง — เครื่องที่ลืมตัดจะยังเห็น storage ดีอยู่ แล้ว E2 ของเครื่องนั้นจะปฏิเสธ (ซึ่งถูกแล้ว มันแปลว่า guard ทำงาน)

2

รอเมล — หรือถามเอง

ภายใน ~10 นาที watch ควรส่งเมล RAISED มา ระหว่างรอ อย่าเพิ่งทำอะไร นี่คือการซ้อมครึ่งแรก: ระบบเตือนเองได้จริงมั้ย

Subject: [ketsync] NODE: 1 raised, 0 cleared - pve-storage-r17

(storage node ไม่ตอบ ssh = NODE tier ในสายตา watch เพราะ backup ยังอยู่) ไม่อยากรอ cron ก็สั่ง ./ketsync watch เองที่เครื่อง storage — แต่รอบซ้อมจริงควรรอ เพื่อพิสูจน์ cron

3

เข้า DR — คำสั่งเดียวจากเครื่อง backup

./ketsync distribute --all # on the BACKUP node
# on the BACKUP node
cd /root/ketsync
./ketsync distribute --all --dry-run    # read the plan first
./ketsync distribute --all

สิ่งที่จะเห็นเรียงกัน ต่อโหนด แล้วต่อ CT — เทียบกับของจริงจากรอบซ้อม 2026-08-16:

[10.100.1.32] E2: storage 'tank-hdd-nas' is dead here [10.100.1.32] disabled storage tank-hdd-nas [10.100.1.32] unmounted /mnt/pve/tank-hdd-nas [110] pct: command 'lxc-stop -n 110 --nokill --timeout 30' failed [110] pct itself never returned (rc=124) - isolating CT 110 instead [110] ISOLATED: net0 now on vmbr99, verified from /sys/class/net [110] placed: CT 9110 on pve-r32, local-lvm:vm-9110-disk-0, rsync rc=0 [110] ssh root@10.100.1.32 pct start 9110

CT ทดสอบจะปิดไม่ลง — ถูกต้องแล้ว โปรเซสของมันค้างอยู่ใน I/O ที่ไม่มีวันตอบ (D state) สัญญาณปิดเข้าคิวไว้แล้วแต่ยังทำไม่ได้ เครื่องมือจึงตัดเน็ตแทน (ISOLATED) ซึ่งกันอันตรายที่ DR สนใจจริงๆ คือสองเครื่องตอบ IP เดียวกัน — และพอ storage กลับมา CT พวกนี้จะดับเองเพราะสัญญาณที่ค้างอยู่เพิ่งถูกส่งถึง

ปิดท้ายด้วยการเปิดตัวชั่วคราวเอง แล้วเช็กว่า service ใช้ได้จริง

ssh root@10.100.1.32 pct start 9110
ssh root@10.100.1.32 pct start 9110
ssh root@10.100.1.33 pct start 9120
4

ทางกลับ — recall แล้ว recover

  1. ปิดตัวชั่วคราว แล้วดึงรอบสุดท้ายกลับเข้าสำเนา (บนเครื่อง backup)
    pct shutdown 9110 && ./ketsync recall --all --final
    ssh root@10.100.1.32 pct shutdown 9110
ssh root@10.100.1.33 pct shutdown 9120
./ketsync recall --all --final
  2. เปิดทางให้ storage กลับมา — ถอน iptables ทุกเครื่องที่ใส่ไว้
    iptables -D OUTPUT -d 10.100.1.17 -j DROP # on EVERY node
    iptables -D OUTPUT -d 10.100.1.17 -j DROP
iptables -D INPUT  -s 10.100.1.17 -j DROP
  3. ทางกลับทั้งสาย คำสั่งเดียว (บนเครื่อง storage)
    ./ketsync recover --all --destroy
    cd /root/ketsync
./ketsync recover --all --dry-run       # the checklist, rehearsed
./ketsync recover --all --destroy

    มันไล่เอง: เปิด storage คืนทุกโหนด → เช็ก superblock (ถ้า image มีแผลจะ e2fsck ให้) → failback --final → คืน network → เก็บ 9xxx ทิ้ง → ลบ PAUSE → รอบ replica แรกต้อง failed=0 จบด้วยพิมพ์คำสั่ง pct start ของตัวจริงให้กด

  4. เปิดตัวจริง แล้วปิดซ้อม
    ssh root@10.100.1.32 pct start 110
    ssh root@10.100.1.32 pct start 110
ssh root@10.100.1.33 pct start 120
./ketsync doctor          # must end green, "nothing left over"

ซ้อมผ่านเมื่อ doctor เขียวทั้งฉบับ, ไฟล์ในตัวจริงอยู่ครบ, และ watch ส่งเมล CLEARED มาปิดเรื่อง — สามอย่างนี้คือคำตอบเดียวกันจากสามมุม

5

สิ่งที่รอบซ้อมจริงสอนไว้

  • ปิด CT ที่ storage ตายไม่ได้เป็นเรื่องปกติ — รอครบ 10+30 วิแล้ว isolate คือพฤติกรรมที่ออกแบบไว้ ไม่ใช่ข้อผิดพลาด
  • rc=23 จาก rsync ครั้งเดียวคืออาการชั่วคราวของ snapshot (ro,noload) — รอบถัดไปเก็บเอง ถ้าซ้ำสองรอบติดตัวเดิมค่อยเป็นเรื่อง
  • ระหว่าง 9xxx ให้บริการ สำเนา 8xxx จะไม่ถูก cron เขียนทับ (R13) และรอบ cron จะขึ้นแดงตลอด — นั่นคือระบบบอกว่า DR ยังไม่จบ ไม่ใช่พัง
  • จดเวลาแต่ละขั้นไว้ — ครั้งหน้าตัวเลขนี้คือคำตอบของคำถามว่า “อีกนานมั้ย”
