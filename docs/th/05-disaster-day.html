DR ทำได้แค่ไหน เตรียมก่อน 1 ยืนยัน 2 ปลุกสำเนา 3 recall 4 storage กลับมา 5 ตัดกลับ 6 เก็บกวาด

05 — เครื่อง storage ตาย ทำยังไง

อ่านหน้านี้ตอนยังไม่เกิดเหตุ แล้วเปิดซ้ำตอนเกิด — ทุกขั้นเป็นคำสั่งที่พิมพ์ได้เลย ถ้ามาถึงหน้านี้เพราะเมล [ketsync] INFRA จาก watch มาถึงคุณ: ใช่ หน้านี้แหละ

ถ้าเมลใบนั้นเขียนว่า master-unreachable แปลว่ามันส่งมาจากเครื่อง backup เพราะเครื่อง storage เงียบไปแล้ว — คำสั่งทุกอันข้างล่างนี้พิมพ์ที่เครื่อง backup ได้เลย นั่นคือที่ที่ DR ถูกสั่งอยู่แล้วโดยการออกแบบ

ทุกคำสั่งในหน้านี้พิมพ์บนเครื่อง backup (10.100.1.9) เว้นแต่จะเขียนบอกไว้
0

ภาพรวม 6 ขั้น — อ่านให้จบก่อนเริ่มขั้นแรก

ทั้งเหตุการณ์มี 6 ขั้น และแต่ละขั้นมีคำสั่งของมันครบแล้ว ไม่มีขั้นไหนที่ต้องทำมือ ตัวเลขที่เห็นในคำสั่งไม่ต้องพิมพ์เอง เครื่องมือคิดให้จากเลข CT ตัวจริงตัวเดียว

ขั้นทำอะไรคำสั่งข้อมูลไปทางไหน
1กันตัวจริงไม่ให้บูตเอง pct set 300 --onboot 0—
2ปลุกสำเนาไปรันที่ compute ketsync distribute --all8300 → 9300
3ก๊อปกลับมาเก็บ ทำซ้ำได้เรื่อยๆ ketsync recall --all9300 → 8300
4storage กลับมา ไล่ช่องว่างให้แคบ recall + failback9300 → 8300 → 300
5ตัดกลับตัวจริง --final ทั้งสองคำสั่ง9300 → 8300 → 300
6เก็บกวาด ketsync cleanup --all—

สิ่งที่หน้านี้จะย้ำอยู่เรื่อยๆ มีอยู่สองเรื่อง เรื่องแรกคือเลข 9 นำหน้า แปลว่าของชั่วคราว — ข้อมูลในนั้นไม่มีใครก๊อปให้เลยจนกว่าจะสั่ง recall เรื่องที่สองคือไม่มีคำสั่งไหนในชุดนี้เปิดหรือปิด container ให้ มันย้ายข้อมูล เขียน config แล้วพิมพ์คำสั่งเปิดออกมาให้คนกดเอง

ทำไมต้องอ้อมผ่านเครื่อง backup

ตอนเอาข้อมูลกลับ ทางที่สั้นที่สุดคือ compute → storage ตรงๆ แต่เราไม่ทำแบบนั้น เราให้ recall พา 9300 กลับไปที่ 8300 บนเครื่อง backup ก่อน แล้วค่อยให้ failback พา 8300 กลับเข้าไฟล์ดิสก์ตัวจริง เหตุผลมีสองข้อ

  • มีของสำรองอยู่ตลอดเวลา ทุกวินาทีจะมีข้อมูลชุดใหม่อยู่อย่างน้อยสองที่เสมอ ถ้าเลือกทางลัด ช่วงที่กำลังเขียนทับไฟล์ดิสก์ตัวจริงคือช่วงที่มีข้อมูลชุดเดียวในโลก
  • ขั้นสุดท้ายมี snapshot ให้ถอยกลับ การเขียนทับไฟล์ดิสก์ตัวจริงทำโดย failback ซึ่งด่าน B7 ของมันสั่ง snapshot ก่อนเสมอ ถ้าอ้อมทางนี้ ขั้นที่อันตรายที่สุดจะได้ตาข่ายมาฟรีๆ

ถอยได้ทุกขั้น ระหว่างขั้น 3 กับ 4 ถ้าอะไรดูไม่ถูก ตัว 9300 ยังรันอยู่ ยังให้บริการลูกค้าอยู่ และยังเป็นข้อมูลชุดที่ใหม่ที่สุด — หยุดตรงไหนก็ได้แล้วคิดต่อ ไม่มีขั้นไหนก่อนขั้น 5 ที่ทำแล้วถอยไม่ได้

ข้อจำกัดที่ต้องยอมรับ ต่อให้กระจายไปหลายเครื่องแล้ว ก็ยังไม่พอรัน CT ทุกตัวพร้อมกัน ต้องเลือกเฉพาะตัวสำคัญ เรียงลำดับไว้ล่วงหน้าดีกว่ามานั่งเลือกตอนตี 3

1

เตรียมไว้ก่อน ตอนยังไม่มีอะไรเกิด

สามอย่างนี้ทำวันธรรมดา ใช้เวลารวมไม่ถึง 10 นาที และเป็นตัวตัดสินว่าคืนนั้นจะราบรื่นหรือไม่

  1. ก๊อปตัวโปรแกรมไว้ที่เครื่อง backup ด้วย ถ้ารอไปทำตอนเกิดเหตุ เครื่องที่เก็บโค้ดอาจตายไปแล้ว
    git clone <this repo> /root/ketsync
    # on the BACKUP node
git clone <this repo> /root/ketsync

    ต้องเป็น /root/ketsync เท่ากันทุกเครื่อง เพราะ ketsync sync ส่งตารางไปที่ path ที่ตัวเองติดตั้งอยู่ ถ้า clone ไว้ที่อื่นจะไม่ได้รับอะไรเลย

  2. เขียนลำดับความสำคัญไว้ ว่า CT ตัวไหนต้องขึ้นก่อน ใส่ในไฟล์ธรรมดาก็ได้
    cat > /root/dr-order.txt <<'EOF'
    # on the BACKUP node
cat > /root/dr-order.txt <<'EOF'
300   shop  - customer facing, first
113   api   - second
121   batch - can wait
EOF

    เขียนเลข CT ตัวจริง ไม่ต้องเขียน 8xxx หรือ 9xxx — ทุกคำสั่งในชุดนี้รับเลขตัวจริงเสมอ

  3. ซ้อมอ่านเดือนละครั้ง สามคำสั่งนี้ไม่แตะอะไรเลย มันบอกว่าถ้าวันนี้ต้องกู้จริงจะติดตรงไหน
    ./ketsync doctor
    # on the STORAGE node, on an ordinary day
./ketsync doctor
./ketsync failback --list
# on the BACKUP node - the machine you will actually be typing on
./ketsync distribute --list

    อันสุดท้ายสำคัญที่สุด เพราะมันคือคำสั่งที่ต้องใช้ตอนเครื่อง storage ตาย ถ้าวันธรรมดามันยังรันไม่ได้ ตอนตี 3 ก็จะรันไม่ได้เหมือนกัน

2

ขั้น 1 — ยืนยันว่าตายจริง แล้วกันตัวจริงไม่ให้กลับมาเอง

อย่ารีบ ปลุกสำเนาขึ้นมาทั้งที่ตัวจริงยังรันอยู่ = มีสองเครื่องใช้ IP เดียวกัน ซึ่งพังหนักกว่าเดิมและแก้ยากกว่า

ping -c3 10.100.1.17
# on the BACKUP node
ping -c3 10.100.1.17
ssh -o ConnectTimeout=5 root@10.100.1.17 true; echo "rc=$?"
  • ถ้ายัง ping ติดหรือ ssh เข้าได้ อย่าเพิ่งทำต่อ เครื่องอาจแค่ช้าหรือ NFS ค้าง ให้ไปแก้ที่ต้นเหตุก่อน สำเนายังอยู่ครบ ไม่ได้หายไปไหน
  • ถ้าเครื่อง storage ยังพอมีชีวิต ให้ปิด cron ก่อนเป็นอย่างแรก ไม่งั้นรอบถัดไปมันจะพยายามก๊อปทับสำเนา ตอนที่คุณกำลังจะใช้สำเนานั้น
    touch /root/ketsync/engines/PAUSE
    # on the STORAGE node, if you can still reach it
touch /root/ketsync/engines/PAUSE

คำสั่งเดียว — ให้เครื่องมือเตรียมให้ทั้งโหนด

ขั้นนี้เคยเป็นคำสั่งดิบสี่ห้าตัวต่อโหนด และเกือบทุกคนทำผิดลำดับ เพราะสัญชาตญาณบอกให้ปิดตู้ก่อนแตะ mount ซึ่งเป็นลำดับที่ทำงานไม่ได้ ตอนนี้เครื่องมือทำให้ตามลำดับที่ถูกต้องเสมอ

# see what it would do to every node first - writes nothing
./ketsync evacuate --all --dry-run

# then do it, one node at a time or the whole fleet
./ketsync evacuate --node 10.100.1.32
./ketsync evacuate --all

มันทำสี่อย่างเรียงกัน ปิด storage ที่ตายก่อน เพื่อให้ pvestatd เลิกเดินเข้าไปในนั้น แล้วบังคับ mount ให้พัง เพื่อให้ I/O ที่ค้างเด้ง EIO ออกมา แล้ว restart pvestatd เพื่อให้โหนดกลับมารายงานตัวเองได้ แล้วค่อยสั่งปิดตู้ที่อยู่บน storage นั้น — ตู้ที่ปิดไม่ลงจะถูกย้ายไป vmbr99 ให้แทน ไม่มีการบังคับปิดที่แรงกว่านั้น

มันจะไม่ยอมทำถ้า storage ยังดีอยู่ ด่าน E2 พิสูจน์ก่อนว่า storage ตายจริง ด้วยการ stat ที่ mountpoint ของมันเอง พร้อม timeout — การค้างคือผลบวก mount ที่ยังดีตอบทันที ถ้ามันตอบ = ปฏิเสธทั้งโหนด ไม่มี override และตู้ที่อยู่บน storage ดีๆ บนโหนดเดียวกัน (เช่น local-lvm) จะไม่ถูกแตะเลยแม้แต่ตัวเดียว

ถ้าอยากจัดการทีละตู้แทนทั้งโหนด — เช่นไม่อยากให้เพื่อนบ้านโดนปิดไปด้วย — ใช้ isolate ตรงๆ มันย้ายทุก net line ไป vmbr99 แล้วจดไว้ว่า bridge เดิมคืออะไร

./ketsync prepare --list
./ketsync isolate --ctid 110
./ketsync restore --ctid 110

ไม่ต้องพิมพ์อะไรลงเครื่อง compute เลย ทุกคำสั่งข้างบนพิมพ์ที่เครื่อง backup แล้วมันไป ssh ทำให้เอง ส่วน onboot ไม่ต้องไปตั้งเอง เพราะทุกตู้ในฟลีตนี้เป็น onboot 0 อยู่แล้ว และ isolate จดค่าเดิมไว้ให้ตอน restore

PAUSE ช่วยเรื่องนี้ไม่ได้ เครื่อง storage ตายโดยไม่บอกล่วงหน้า ไม่มีใครทันพิมพ์ touch PAUSE และไฟล์นั้นก็อยู่บนเครื่องที่ตายไปแล้วด้วย ด่าน D1 จึงไปอ่าน onboot จากเครื่อง compute โดยตรง และปฏิเสธจนกว่าจะเป็น 0

ถ้ายังปิดไม่ได้จริงๆ — ย้ายมันไปอยู่บน bridge ที่ไม่มีทางออก

สิ่งที่ด่าน D1 กลัวไม่ใช่ "container ยังรันอยู่" แต่คือ "มีสองเครื่องตอบบน IP เดียวกัน" เพราะสำเนาที่กำลังจะวางถือ IP และ MAC ของตัวจริงไว้ทั้งคู่ ถ้าย้ายตัวจริงไปอยู่บน bridge ที่ไม่มีสายออกไปไหน มันก็ตอบใครไม่ได้ อันตรายข้อนั้นหมดไปทันที — กลไกเดียวกับที่ทำให้สำเนา 8xxx บนเครื่อง backup อยู่ร่วมโลกกับตัวจริงได้มาตลอด

ข้อดีของทางนี้คือมันไม่ต้องใช้อะไรจาก storage ที่ตายไปเลย config ของ container อยู่ใน /etc/pve และ PVE จะ hotplug ให้ทันที เป็นทางเดียวที่ยังทำงานได้ตอนที่ pct shutdown ค้างอยู่

pct config 300 | grep '^net'
# on the COMPUTE node - look at EVERY net line first, not just net0
pct config 300 | grep '^net'

# move each one, keeping name, hwaddr and ip exactly as they were
pct set 300 --net0 name=eth0,bridge=vmbr99,hwaddr=BC:24:11:00:00:01,ip=10.100.2.10/24

# then check the KERNEL, which is what D1 reads - a config can say one
# thing while the running container never received the change
ls -l /sys/class/net/veth300i*/master
ls /sys/class/net/vmbr99/brif/

ต้องย้ายทุกเส้น ไม่ใช่แค่ net0 — เส้นที่ลืมคือเส้นที่ตอบ และ vmbr99 บนเครื่องนั้นต้องไม่มี port จริงเสียบอยู่ ถ้าเห็นว่า veth ทุกเส้นชี้ไป vmbr99 และใน brif ไม่มีการ์ดจริงเลย D1 จะยอมวาง 9xxx ให้ ทั้งที่ตัวจริงยังรันอยู่ ถ้ามันหา veth ได้ไม่ครบตามจำนวน net ที่ config บอก มันจะไม่ยอม — ตรวจไม่ครบไม่นับว่าตัดขาดแล้ว

ยังต้องปิดมันอยู่ดี CT ตัวจริงยังเป็น pending writer คือ I/O ของมันค้างอยู่ตอนนี้เพราะ storage หายไป แต่วินาทีที่ storage กลับมา มันจะเขียนลง image ของ 300 ต่อทันทีโดยไม่มีใครสั่ง ต้องปิดให้ได้ก่อนถึงตอนนั้น ซึ่งตอนนั้นปิดง่ายแล้ว และตอนปิดให้สั่ง pct set 300 --onboot 0 ไปด้วย ไม่งั้นรีบูตรอบหน้ามันขึ้นมาเขียนเองอีก ด่าน B1 ของ failback จะไม่ยอมเขียนกลับลง image จนกว่าตัวจริงจะปิดสนิท

3

ขั้น 2 — ย้ายสำเนาไปรันที่เครื่อง compute

สำเนาอยู่ที่เครื่อง backup ก็จริง แต่ไม่ได้เอาไปรันที่นั่น เครื่อง backup มีหน้าที่เก็บของ ไม่ได้มีแรงพอจะรัน CT ทั้งฟลีต ของต้องถูกก๊อปต่ออีกทอดไปลงดิสก์ในตัวเครื่อง compute เอง ซึ่งเป็นที่เก็บของที่เดียวในตึกที่ไม่ได้พึ่งเครื่องที่เพิ่งตายไป

เลข CT บอกว่ากำลังดูอะไรอยู่

เลขคืออะไรอยู่ที่ไหน
300ตัวจริงดิสก์บนเครื่อง storage ผ่าน NFS
8300สำเนาที่ก๊อปทุก 15 นาที ปิดอยู่เครื่อง backup
9300ตัวชั่วคราวตอนฉุกเฉินlocal-lvm ของเครื่อง compute

เห็นเลข 9 นำหน้าเมื่อไหร่ให้รู้ทันทีว่านี่คือของชั่วคราว ข้อมูลข้างในไม่มีใครก๊อปให้ และต้องมีคนเก็บกวาดทีหลัง

ขั้นที่ 1 — ดูก่อนว่ามันจะทำอะไร ยังไม่แตะอะไร

cd /root/ketsync
cd /root/ketsync
./ketsync distribute --list

มันจะพิมพ์ออกมาว่า CT ตัวไหนจะไปเครื่องไหน ลง storage อะไร ใช้เนื้อที่เท่าไหร่ ตัวไหนที่ไม่มีที่ไปมันจะบอกว่าไม่มีแถวใน fleet.tsv — ไม่เดาให้ ต้องบอกด้วย --to เอง

ขั้นที่ 2 — ซ้อมตัวเดียวก่อน

./ketsync distribute --ctid 300 --dry-run
./ketsync distribute --ctid 300 --dry-run

เดินผ่านด่านตรวจครบทุกด่านเหมือนของจริง ต่างกันแค่ไม่จองเนื้อที่ ไม่ก๊อป ไม่เขียน config

ขั้นที่ 3 — ของจริง ทีละตัวตามลำดับความสำคัญ

./ketsync distribute --ctid 300
./ketsync distribute --ctid 300
./ketsync distribute --ctid 300 --to 10.100.1.33          # override the placement
./ketsync distribute --ctid 300 --to 10.100.1.33 --dst local-zfs

มันจะจองเนื้อที่บนเครื่องปลายทาง ทำ filesystem ก๊อปข้อมูลจากเครื่อง backup แล้วเขียน config ให้ — แต่ไม่เปิดให้ มันจะพิมพ์คำสั่งเปิดออกมาให้คนกดเอง

[300] placed: CT 9300 on pve01, local-lvm:vm-9300-disk-0, rsync rc=0 in 412s
[300]   net: net0 on vmbr0 - taken from CT 300's own config
[300]   check it, then start it BY HAND:
[300]     ssh root@10.100.1.32 pct config 9300
[300]     ssh root@10.100.1.32 pct start 9300

network ของ 9300 มาจาก config ของ CT 300 ตัวจริงโดยตรง ไม่ใช่ของสำเนา — สำเนาบนเครื่อง backup อยู่บน vmbr99 โดยตั้งใจ ส่วนตัวนี้วางไว้เพื่อให้ ตอบ IP MAC และ VLAN จึงตรงกับของเดิมทุกตัว ไม่ต้องพิมพ์เอง (พิมพ์ MAC ผิดตัวเดียวคือ ARP ทั้งวงเพี้ยน)

ตอนสั่ง ketsync distribute มันตัดขาด CT ตัวจริงไปก่อนแล้ว config ของ 300 ตอนนั้นจึงเป็น vmbr99 ทั้งแถบ — ตัวที่รู้ว่า bridge จริงคืออะไร คือไฟล์บันทึกที่ขั้นแรกเขียนไว้ก่อนย้าย มันอ่านจากตรงนั้นให้เอง แล้วบอกว่าอ่านมาจากไหน

[300]  net0 came from the isolate record on pve-r32: production CT 300 is
[300]   on vmbr99 right now because ct-prepare.sh put it there, and that
[300]   record is where its real bridge went. Nothing was guessed.

ยกเว้นกรณีเดียว ถ้าคุณย้าย CT 300 ไป vmbr99 เองด้วยมือ ไม่ได้ผ่านเครื่องมือ แปลว่า bridge จริงถูกทับไปแล้วและไม่มีใครจดไว้ ตอนนั้นมันจะวางให้ตามปกติ แต่ขึ้นเตือนตัวใหญ่ว่า would come up UNABLE TO ANSWER — ต้องใส่ bridge จริงเองก่อนเปิด นี่คือเหตุผลที่ควรใช้ ketsync evacuate หรือ ketsync isolate แทนการพิมพ์ pct set เอง

ขั้นที่ 4 — ทั้งฟลีตทีเดียว เมื่อซ้อมตัวแรกผ่านแล้ว

./ketsync distribute --all
./ketsync distribute --all

ตัวไหนพลาดมันข้ามไปตัวถัดไป ไม่หยุดทั้งชุด แล้วสรุปตอนท้ายว่าตัวไหนไม่ผ่านเพราะอะไร

4

ขั้น 3 — ก๊อปข้อมูลกลับมาเก็บ ระหว่างที่ 9xxx ยังให้บริการอยู่

นี่คือขั้นที่ห้ามข้าม ตั้งแต่วินาทีที่ 9300 เริ่มรับงาน ทุกอย่างที่ลูกค้าทำอยู่บนดิสก์ในตัวเครื่อง compute เครื่องเดียว ไม่มีอะไรก๊อปไปไหนเลย เครื่องมือที่แก้ปัญหา single point of failure อันหนึ่ง เพิ่งสร้างอันใหม่ขึ้นมา ketsync recall คือสิ่งที่ปิดช่องนั้น

./ketsync recall --list
# read only, changes nothing
./ketsync recall --list
# 9300 -> 8300, repeatable, run it as often as you like
./ketsync recall --all

มันก๊อปจาก 9300 กลับเข้าสำเนา 8300 บนเครื่อง backup — ทิศทางตรงข้ามกับ distribute รอบแรกนานหน่อย รอบต่อๆ ไปย้ายเฉพาะส่วนที่เปลี่ยน สั่งได้บ่อยเท่าที่อยากสั่ง ทุกชั่วโมงก็ได้ ลูกค้ายังใช้งานได้ตามปกติระหว่างนั้น

[300] OK -> 8300 (rc=0) changed=2.2GiB files=161 in 94s

ตัวเลข changed= คือสิ่งที่ต้องเฝ้า พอมันไม่ลดลงแล้ว แปลว่ารอบตัดจริงจะสั้นมาก

อย่าลบบรรทัด ct-distribute ออกจากช่อง Notes ของ 9xxx ตอน distribute สร้าง container มันเขียนบรรทัดหนึ่งลงไป ซึ่งใน GUI จะไปโผล่ในช่อง Notes รวมกับโน้ตที่คุณเขียนเอง เขียนโน้ตเพิ่มได้ตามสบาย ภาษาไทยก็ได้ (PVE เก็บเป็น URL-encode แล้วแปลงกลับให้เอง เครื่องมือชุดนี้ก็อ่านออก) แต่ถ้าลบบรรทัดนั้นทิ้ง recall จะปฏิเสธทันที เพราะนั่นคือหลักฐานชิ้นเดียวที่บอกว่าข้อมูลข้างไหนใหม่กว่า

ทิศทางมาจากไหน — ทำไมสลับข้างไม่ได้

คำสั่งนี้เขียนทับสำเนา DR ด้วย --delete ถ้าสลับข้างจะลบงานหลายชั่วโมงของลูกค้าทิ้งทันที และไม่มีอะไรให้กู้กลับ มันจึงไม่รับทิศทางเป็นอาร์กิวเมนต์ และไม่ดูวันเวลาไฟล์ตัดสินว่าข้างไหนใหม่กว่า — rsync รักษา mtime ไว้ ไฟล์ในสำเนาจึงอาจดู "ใหม่กว่า" ทั้งที่ข้อมูลเก่ากว่า

สิ่งที่มันดูคือที่มา ตอน distribute สร้าง 9300 มันเขียนบรรทัดหนึ่งลงใน config บอกว่าตัวนี้เกิดจากสำเนาไหนของ CT ไหน ด่าน C3 อ่านบรรทัดนั้น ไม่มีบรรทัดนั้นก็ไม่ทำ นี่คือข้อเท็จจริงที่ PVE ถืออยู่ ไม่ใช่การเดา

เฝ้าเนื้อที่บนเครื่อง compute ไปด้วย

free -h
# on each COMPUTE node running a 9xxx container
free -h
lvs pve
df -h /

RAM ใกล้เต็มแปลว่าย้ายมาเพิ่มไม่ได้แล้ว เนื้อที่ pool ใกล้เต็มอันตรายกว่ามาก: thin pool ที่เต็มไม่ได้แค่เขียนไม่ได้ มันทำให้ทั้ง pool กลายเป็น read-only ซึ่งลาก CT ทุกตัวบนเครื่องนั้นลงไปด้วย เหลือน้อยกว่า 20% เมื่อไหร่ให้หยุดย้ายเพิ่มทันที

ถ้ามี PBS สั่ง backup ตัวสำคัญไว้ระหว่างนี้ด้วยก็ยิ่งดี — recall ทำให้มีสำเนาสองที่แล้ว แต่สำรองเพิ่มอีกชั้นไม่เคยเสียหาย

5

ขั้น 4 — เครื่อง storage กลับมา

อ่านให้จบก่อนเปิดเครื่อง storage พอมันบูตขึ้นมา cron จะเริ่มทำงานภายใน 15 นาที แล้วมันจะเห็นว่า “ดิสก์ตัวจริงกลับมาแล้ว” จึงก๊อปทับสำเนาตามหน้าที่ของมัน

มีด่านกันอยู่แล้ว แต่ให้ใส่ PAUSE ด้วยอยู่ดี

ด่าน R13 ของ replica จะข้าม CT ตัวไหนก็ตามที่มี 9xxx อยู่ในคลัสเตอร์ ตราบใดที่ยังไม่มีใคร pct destroy 9300 สำเนา 8300 ก็จะไม่ถูกเขียนทับ — ด่านนี้ทำงานได้แม้ไม่มีใครทันใส่ PAUSE ซึ่งเป็นสิ่งที่ PAUSE ทำไม่ได้ เพราะตอนเครื่องตายไม่มีใครทันพิมพ์

ถึงอย่างนั้นก็ใส่ PAUSE ด้วย มันคือด่านที่สอง ราคาถูก และเป็นอันเดียว ที่ failback --final ต้องการ

ลำดับที่ปลอดภัย

  1. เปิดเครื่อง storage ขึ้นมา แล้วใส่ PAUSE ทันที
    touch /root/ketsync/engines/PAUSE
    # on the STORAGE node, immediately after boot
touch /root/ketsync/engines/PAUSE
  2. เช็กว่าดิสก์และ storage กลับมาครบ
    zpool status
    zpool status
pvesm status
./ketsync doctor
  3. เริ่มไล่ช่องว่างให้แคบลง ทำสองคำสั่งนี้สลับกันได้เรื่อยๆ ลูกค้ายังใช้งานอยู่
    ./ketsync recall --all
    # 9300 -> 8300, on the machine driving the DR
./ketsync recall --all
# 8300 -> the production image, on the STORAGE node
./ketsync failback --all

    ทั้งคู่เป็นเครื่องมือแบบ presync ยิ่งทำหลายรอบ รอบตัดจริงยิ่งสั้น ดูตัวเลข changed= ของทั้งสองคำสั่ง พอมันไม่ลดแล้วก็พร้อมตัด

ทำไม failback ยอมทำงานทั้งที่สำเนาปิดอยู่ ด่าน B2 เดิมต้องการให้สำเนารันอยู่ เพราะนั่นคือสิ่งที่ทำให้ R2 ข้ามมันไป แต่เคสนี้ไม่มีใครปลุกสำเนาเลย — ข้อมูลไปอยู่ที่ 9300 ต่างหาก B2 จึงยอมเมื่อเห็นว่า 9300 ยังมีอยู่ เพราะตอนนั้น R13 กันให้อยู่แล้ว และกันได้แน่นกว่า R2 ด้วย

ถ้าเผลอปล่อยให้ cron ทำงานไปก่อน

grep -l 'GUARD R13' /root/ketsync/logs/replica-*.log
grep -l 'GUARD R13' /root/ketsync/logs/replica-*.log
grep 'ok=' /root/ketsync/logs/replica-*-$(date +%F).log | tail -3

บรรทัดที่ขึ้น GUARD R13 คือตัวที่รอด เพราะมี 9xxx อยู่ ตัวที่ขึ้นว่า ok ในรอบนั้นคือตัวที่ไม่มี 9xxx และถูกก๊อปทับไปตามปกติ ซึ่งถูกต้องแล้ว

6

ขั้น 5 — ตัดกลับตัวจริง

ทำทีละ CT ตอนที่พร้อม ไม่ต้องทำทั้งฟลีตพร้อมกัน ช่วงที่ลูกค้าใช้ไม่ได้คือช่วงระหว่าง pct shutdown 9300 กับ pct start 300 ซึ่งถ้าทำขั้น 3 กับ 4 มาดีแล้วจะเหลือเป็นวินาที

  1. ปิดตัวชั่วคราว
    pct shutdown 9300
    # on the COMPUTE node running it
pct shutdown 9300
  2. ดึงรอบสุดท้ายจาก 9300 เข้าสำเนา
    ./ketsync recall --ctid 300 --final
    ./ketsync recall --ctid 300 --final

    ต้องปิด 9300 ก่อนถึงจะสั่ง --final ได้ และถ้ามันปิดอยู่แล้ว แต่ไม่ได้ใส่ --final มันจะปฏิเสธ — “บังเอิญมันปิดอยู่” กับ “เรากำลังตัดกลับ” เป็นคนละเจตนา

  3. ดึงรอบสุดท้ายจากสำเนาเข้าไฟล์ดิสก์ตัวจริง
    ./ketsync failback --ctid 300 --final
    # on the STORAGE node - PAUSE must already exist
./ketsync failback --ctid 300 --final

    ด่าน B7 จะ snapshot ไฟล์ดิสก์ตัวจริงก่อนเขียนทับ ถ้า snapshot ไม่สำเร็จมันจะไม่ทำ นี่คือทางถอยทางเดียวของขั้นนี้

  4. คืน network กับ onboot ของตัวจริง จากที่เครื่องมือจดไว้ตอนตัดขาด แล้วเปิดเอง
    ./ketsync restore --ctid 300
    # bridge and onboot come out of the isolate record - nothing is typed
./ketsync restore --ctid 300
    pct start 300
    # on the COMPUTE node that owns CT 300 - a person decides this one
pct start 300

    ไม่ต้องจำว่า bridge เดิมชื่ออะไร restore อ่านจากไฟล์บันทึกที่ isolate เขียนไว้ก่อนย้าย ส่วนคำสั่งเปิดยังเป็นของคน — ทั้งชุดนี้ไม่มีตัวไหนเปิด container ให้

อย่าเพิ่ง destroy 9300 ปล่อยไว้จนกว่าจะเช็กแล้วว่าตัวจริงกลับมาถูกต้อง ตราบใดที่ 9300 ยังอยู่ R13 ก็ยังกันไม่ให้ cron เขียนทับสำเนา — ทางถอยยังอยู่ครบ ขั้นถัดไปเป็นคนเก็บให้ด้วยคำสั่งเดียว ไม่ต้องไปพิมพ์ pct เอง

ตั้งแต่ failback เป็นต้นไป ย่อเหลือคำสั่งเดียวได้ พอปิด 9xxx และสั่ง recall --final ครบทุกตัวแล้ว ขั้น 3 ของหน้านี้กับขั้น 6 ทั้งขั้นรวมอยู่ใน recover คำสั่งเดียว: เปิด storage คืนจากบันทึกของ evacuate, สั่ง e2fsck ให้ image ที่ superblock มีแผล, failback ทุกตัวที่มี 9xxx ค้างอยู่, คืน network จากบันทึกของ isolate, แล้วเก็บ 9xxx — มันอ่านจากบันทึกจริงในคลัสเตอร์ว่าเหลืออะไร ขั้นที่ทำไปแล้วมันข้ามพร้อมบอกว่าข้ามทำไม เพราะฉะนั้นสั่งซ้ำกี่รอบก็ได้ และรอบที่ทุกอย่างเสร็จแล้วมันบอกว่าไม่เหลืออะไร

./ketsync recover --list
# read only - the checklist, with what is already done
./ketsync recover --list
./ketsync recover --all
# on the STORAGE node. Keeps each 9xxx as a fallback
./ketsync recover --all
./ketsync recover --all --destroy
# the complete return: also destroys each 9xxx, removes PAUSE,
# and runs the first replica round - decide this AFTER checking the real ones
./ketsync recover --all --destroy

สองอย่างที่มันไม่มีวันทำแทนคน: pct start ของตัวจริง (มันพิมพ์คำสั่งให้ท้ายรัน) กับการตัดสินใจปิด 9xxx — ตัวไหนยังรันอยู่มันปฏิเสธ แล้วชี้ไปที่ recall --final เพราะการหยุดเครื่องที่กำลังตอบลูกค้า เป็นการตัดสินใจของคน ไม่ใช่ของสคริปต์

7

ขั้น 6 — เก็บกวาด ไม่งั้นครั้งหน้าจะชนกับครั้งนี้

  1. เช็กก่อนว่าตัวจริงใช้งานได้จริง ไม่ใช่แค่บูตขึ้น — เข้าเว็บ ลองสั่งงาน ดู log ของ CT เอง
  2. เก็บตัวชั่วคราวบนเครื่อง compute ให้เรียบร้อย
    ./ketsync cleanup --ctid 300
    # on the STORAGE node - the one that ran the failback
./ketsync cleanup --ctid 300

    มันเช็กก่อนว่า failback --final ของตัวนี้จบ ok จริง (ด่าน K2 อ่านจาก state ของ failback เอง) ถ้ายังไม่มี network ตัวจริงคืนมันคืนให้ก่อน แล้วค่อยสั่งหยุด 9300 ย้าย net ของ 9300 ไป vmbr99 และตั้ง onboot 0 — จากตรงนี้ 9300 เปิดขึ้นมาเองก็ตอบใครไม่ได้อีกแล้ว ข้อมูลยังอยู่ครบเป็นทางถอย

    ถ้า 9300 ยังรันอยู่ แต่ตัวจริงยังไม่ได้เปิด มันจะปฏิเสธ (ด่าน K3) — หยุดตัวที่กำลังตอบอยู่ ทั้งที่ยังไม่มีใครมารับแทน คือ downtime ที่เกิดจากการเก็บกวาดเอง

  3. เมื่อมั่นใจแล้วว่าไม่ต้องถอย ค่อยลบทิ้ง
    ./ketsync cleanup --ctid 300 --destroy
    # this is what releases R13 - after this the nightly copy resumes
./ketsync cleanup --ctid 300 --destroy

    ตราบใดที่ config ของ 9300 ยังอยู่ R13 ยังกัน ไม่ให้ cron เขียนทับสำเนา 8300 — ทางถอยยังครบ แต่ก็แปลว่า CT 300 ยังไม่ถูกก๊อปทุกคืน และรอบ cron จะขึ้นแดงอยู่อย่างนั้น --destroy คือสิ่งที่ปลดมัน ทำเมื่อพร้อมเท่านั้น

  4. ลบ PAUSE เพื่อให้เริ่มก๊อปตามปกติอีกครั้ง
    rm /root/ketsync/engines/PAUSE
    # on the STORAGE node
rm /root/ketsync/engines/PAUSE
  5. ดูรอบแรกหลังเปิดใหม่ว่าเขียวจริง
    ./ketsync replica --ctid 300
    ./ketsync replica --ctid 300
./ketsync status

watch จะบอกเองว่าจบจริง ตราบใดที่ยังมี 9xxx หรือบันทึกของ evacuate/isolate ค้างอยู่ เมล INFRA/NODE ของมันยังถือเรื่องไว้ พอเก็บครบทุกขั้น จะได้เมล CLEARED มาปิดเรื่อง — ไม่ได้ = ยังเหลืออะไรสักอย่าง สั่ง ./ketsync watch --list ดู

จบแล้วจดไว้หน่อย ว่าติดตรงไหน ใช้เวลาเท่าไหร่ อะไรที่หน้านี้ไม่ได้บอก ครั้งหน้าจะได้ไม่ต้องคิดใหม่ และเอามาเติมในหน้านี้ได้เลย

ให้เครื่องมือบอกเองว่าเหลืออะไร

ทุกอย่างที่ DR ทิ้งไว้ ตอนนี้ doctor เห็นหมด และมันเห็นทุกวัน ไม่ใช่เห็นตอนภัยพิบัติครั้งหน้า — ตู้ที่ยังถูกตัดเน็ตอยู่ storage ที่ยังปิดอยู่ 9xxx ที่ยังไม่ถูกลบ และบรรทัด cron ที่จะโดนปฏิเสธเพราะไม่มี -y

./ketsync doctor

คืนค่าที่เครื่องมือเปลี่ยนไว้ ด้วยของที่มันจดไว้เอง ไม่ต้องจำว่า bridge เดิมชื่ออะไร

# bridges and onboot, per container
./ketsync restore --all

# the storages evacuate switched off, per node
./ketsync restore --node 10.100.1.32
