ก่อนเริ่ม

เอกสารนี้เป็นลำดับคำสั่งล้วน ตัวอย่างทั้งหมดใช้ค่าสมมติชุดนี้ ให้เปลี่ยนเป็นของจริงก่อนพิมพ์

ค่าตัวอย่างในเอกสารนี้คืออะไร
--old-node10.100.1.11เครื่องเก่าที่ CT อยู่ตอนนี้
--old-ctid100เลข CT บนเครื่องเก่า
--vmid9100เลข VM ที่จะสร้างใหม่ ต้องยังว่าง
--storagetank-hdd-nasที่เก็บ disk ของ VM
--isolocal:iso/CentOS-7-x86_64-DVD-2009.isoแผ่นติดตั้ง เอาไว้ใช้ในเฟส 2 ต้องตรงรุ่นของ CT

storage ต้องเป็นแบบไฟล์ ไม่ใช่ LVM หรือ ZFS เพราะขั้นตอนนี้ต้อง mount ไฟล์ image ตรงๆ ถ้าใส่ storage แบบ block โปรแกรมจะไม่ทำงานและบอกให้เปลี่ยน ทำเสร็จแล้วค่อย qm move-disk ไป LVM หรือ ZFS ทีหลังได้

เช็กก่อนว่า CT ตัวนี้เป็นรุ่นอะไร

ทั้งเอกสารนี้แยกเป็นสองทางตั้งแต่เฟส 2 เป็นต้นไป ต้องรู้ก่อนว่าจะเดินทางไหน ถามตัว CT เอง อย่าเดาจากชื่อเครื่อง พิมพ์บนเครื่องเก่า

$ pct exec 100 -- cat /etc/redhat-release

คำตอบจะเป็นประมาณ CentOS release 6.10 (Final) หรือ CentOS Linux release 7.9.2009 (Core) ตัวเลขตัวแรกหลังคำว่า release คือสิ่งเดียวที่ต้องจำ

ถ้าไฟล์นั้นไม่มี แปลว่ามาผิดเล่ม ให้ถามอีกไฟล์แทนด้วย pct exec 100 -- cat /etc/os-release ถ้าได้ ID=debian หรือ ID=ubuntu ให้ไปที่ c2v-deb.html ทางนั้นไม่ต้องใช้แผ่นติดตั้ง และเฟส 2 พิมพ์บน node ใหม่ได้เลย ไม่ต้องเข้าหน้าจอของ VM

แผ่นติดตั้งต้องเป็นรุ่นเดียวกับ CT เฟส 2 ลง kernel กับ boot loader จากแผ่น ด้วย rpm ของตัว CT เอง CT รุ่น 6 ต้องใช้แผ่น 6.x รุ่น 7 ต้องใช้แผ่น 7.x สลับกันไม่ได้

เช็กว่ามีแผ่นติดตั้งแล้วหรือยัง

$ pvesm list local --content iso

ถ้ายังไม่มี ให้โหลดลงเครื่อง หรือถ้าเครื่องออกเน็ตไม่ได้ก็อัปโหลดผ่านหน้าเว็บ PVE ที่ local > ISO Images เอาบรรทัดที่ตรงกับรุ่นของ CT บรรทัดเดียว

$ cd /var/lib/vz/template/iso
$ wget https://vault.centos.org/6.10/isos/x86_64/CentOS-6.10-x86_64-bin-DVD1.iso
$ wget https://vault.centos.org/7.9.2009/isos/x86_64/CentOS-7-x86_64-DVD-2009.iso

ต้องเป็นแผ่นเต็มเท่านั้น รุ่น 6 คือแผ่นที่ชื่อลงท้ายว่า DVD1 ประมาณ 4.0G รุ่น 7 คือ DVD-2009 ประมาณ 4.4G แผ่น minimal มีแพ็กเกจไม่ครบ และที่ร้ายกว่าคือ yum ไม่ถือว่าเป็นความผิดพลาดเมื่อหาชื่อที่สั่งลงเจอไม่ครบ มันจะจบแบบเรียบร้อยแล้วไปพังตอนบูตแทน

1

งานนี้มี 2 เฟส

CT ไม่มีของอยู่ 3 อย่างที่ VM ต้องมี คือ kernel, ตัว boot loader และ initramfs ที่รู้จัก virtio เฟสแรกก๊อบข้อมูล เฟสสองใส่ 3 อย่างนั้น

ทำอะไรพิมพ์ที่ไหนใช้เวลา
c2v-prepare.shสร้าง VM เปล่า แบ่ง partition ก๊อบไฟล์ทั้งหมดจาก CTnode ใหม่ตามขนาดข้อมูล
c2v-inside.shลง kernel + grub ทำให้ boot ได้ในหน้าจอ VM ตอน rescueประมาณ 10 นาที

เหตุผลที่แยกเป็นสองตัว คือเฟส 2 รันบน PVE 9 ไม่ได้ ทั้งสองรุ่นแต่คนละเหตุผล

รุ่นของ CTทำไมรันบน host ไม่ได้
CentOS 6คำสั่ง rpm dracut grub ในตัวมันเป็นโปรแกรมของ glibc 2.12 ซึ่ง segfault ทันทีบน kernel ใหม่
CentOS 7รันได้ แต่ไม่มีประโยชน์ เพราะ host ไม่มี rpm กับ yum จะเอาที่ไหนลง kernel ให้ และ grub2 บน host เป็นของ Debian เขียน core.img ที่วิ่งไปหา /boot/grub พร้อมชุด module ของ Debian ส่วนตัว CT รอที่ /boot/grub2

ทั้งสองทางลงเอยเหมือนกัน คือต้องรันในตัวมันเอง ผ่านแผ่นติดตั้งของรุ่นตัวเองเท่านั้น

CT ตัวเก่าไม่ถูกแตะต้องเลย ทั้งสองเฟสเป็นการอ่านอย่างเดียว ระหว่างทำ CT เก่ายังรันตามปกติ และตัวโปรแกรมไม่เคยสั่งเปิดหรือปิดอะไรเอง

เฟส 1 — ก๊อบข้อมูล

ลองเปล่าก่อนหนึ่งรอบ ยังไม่มีอะไรถูกสร้าง

$ cd ~/ct-migrate
$ ./tools/c2v-prepare.sh \
    --old-node 10.100.1.11 \
    --old-ctid 100 \

    --dry-run

ถ้าไม่มี ERROR ให้ถอด --dry-run ออกแล้วรันจริง เติม --bwlimit 500000 ถ้าไม่อยากให้กิน bandwidth หมด

ต่อจากบรรทัดสุดท้าย โปรแกรมจะพิมพ์ขั้นตอนของเฟส 2 ให้ดูด้วย โดยอ่านรุ่นจากไฟล์ในตัว image ที่เพิ่งก๊อบเสร็จ บรรทัดที่ขึ้นต้นว่า Guest is คือรุ่นที่มันอ่านได้ ถ้าไม่ตรงกับที่เช็กไว้ในขั้น 0 แปลว่าใส่เลข CT ผิดตัว

c7root เป็นแค่ป้ายชื่อ ไม่มีอะไรในโปรแกรมอ่านรุ่นจากชื่อนี้ มันคือชื่อ partition ที่ทั้งสองเฟสต้องเรียกตรงกันเท่านั้น เฟส 1 ตั้งชื่อตอน format เฟส 2 เอาชื่อเดียวกันนี้ไปเขียนใน grub ถ้าสองที่ไม่ตรงกัน เครื่องจะบูตไปตกที่หน้าจอ dracut และห้ามเปลี่ยนทีหลังถ้า image ถูกสร้างไปแล้ว เพราะรอบหลังโปรแกรมไม่ format ซ้ำ ป้ายเดิมจึงยังอยู่ แต่เฟส 2 จะเขียน grub ตามชื่อใหม่ที่ไม่มีใครตอบ

image เก่าที่สร้างไว้ตอนที่ค่าตั้งต้นยังเป็น c6root ถ้าจะ sync ทับของเดิม ต้องใส่ --label c6root ต่อท้ายคำสั่งด้วย ถ้าลืม โปรแกรมจะหยุดแล้วบอกชื่อที่ถูกให้เอง ไม่ format ทับ

ถ้าขึ้น WARN เรื่อง mountpoint แปลว่า CT ตัวนี้มี disk ก้อนที่สองต่ออยู่ ข้อมูลในนั้นไม่ถูกก๊อบ จะกลายเป็นโฟลเดอร์ว่างใน VM ต้องย้ายเองทีหลัง หรือต่อเป็น disk ลูกที่สองให้ VM

รันซ้ำกี่รอบก็ได้ รอบหลังจะก๊อบเฉพาะส่วนที่เปลี่ยน ข้อแม้เดียวคือ VM ต้องหยุดอยู่ ถ้า VM รันอยู่โปรแกรมจะไม่ยอมทำและบอกให้ไปสั่งหยุดก่อน

cpu กับ ram ไม่ต้องใส่เอง

สองค่านี้อ่านมาจาก pct config ของ CT ตัวนั้นให้เลย ไม่ต้องไปเปิดดูแล้วพิมพ์ตาม ถ้าอยากได้ไม่เท่าเดิมค่อยใส่ --memory หรือ --cores ทับ ใส่แล้วมันจะบอกว่า forced by ให้เห็นชัดๆ ว่าเลขนี้มาจากมือเรา ไม่ได้มาจาก CT

มีสองกรณีที่อ่านมาตรงๆ ไม่ได้ ทั้งสองกรณีจะขึ้น WARN ให้เห็น

อย่างแรกคือ CT ที่ไม่มีบรรทัด cores: เลย ตัวนั้นไม่ได้ถูกจำกัด คือใช้ core ทั้งเครื่องเท่าที่ node มี ซึ่งไม่ใช่ตัวเลขที่เอามาใส่ VM ได้ ต้องเลือกเองว่าจะให้เท่าไหร่ ค่าที่มันตั้งให้คือ 2 ซึ่งเป็นแค่ตัวเลขที่ทำให้เดินต่อได้ ไม่ใช่ตัวเลขที่ถูก

อย่างที่สองคือ CT ที่ ram น้อยกว่า 1024M มันจะดันขึ้นเป็น 1024M ให้ ไม่ใช่เพราะเดาว่างานต้องใช้เท่านั้น แต่เพราะเฟส 2 ต้องรัน yum กับ dracut อยู่ในตัว guest เอง แล้วเท่าที่ container พอใจมันไม่พอ ถ้ายืนยันว่าจะเอาน้อยกว่านั้นจริงๆ ใส่ --memory ทับได้ มันไม่ดันซ้ำ

ชื่อสะพานของสองเครื่องไม่เหมือนกัน

vmbr1 ของเครื่องเก่ากับ vmbr1 ของเครื่องใหม่ เป็นแค่ชื่อที่เขียนเหมือนกัน ไม่ได้แปลว่าเป็นวงเดียวกัน และไม่มีอะไรในไฟล์ตั้งค่าฝั่งไหนบอกได้ว่าใช่หรือไม่ใช่ การก๊อบชื่อข้ามมาเฉยๆ จึงเป็นการแทนค่าอย่างเดียวที่ทำให้เครื่องไปโผล่ผิดวงโดยที่ทุกอย่างดูถูกต้องหมด

บอกให้มันรู้ด้วยไฟล์ bridgemap.tsv วางไว้ที่โฟลเดอร์เดียวกับตัวโปรแกรม ก๊อบจาก bridgemap.tsv.example มาแก้ สี่ช่องต่อบรรทัด คั่นด้วย tab หรือเว้นวรรคก็ได้

pve6a	vmbr0	pve9a	vmbr0
pve6a	vmbr1	pve9a	vmbr2

อ่านว่า สะพานชื่อ vmbr1 บนเครื่อง pve6a เครื่อง pve9a เรียกมันว่า vmbr2 ใส่ * ได้ในสามช่องแรก บรรทัดที่ตรงก่อนชนะ เพราะฉะนั้นบรรทัดเจาะจงต้องอยู่บนบรรทัดกว้างๆ

สะพานที่ไม่มีบรรทัดรองรับ จะถูกก๊อบชื่อเดิมข้ามมาแล้วติดป้าย UNMAPPED ไว้ให้เห็น พร้อมพิมพ์บรรทัดที่ต้องเติมลงไฟล์ให้ด้วย มันไม่เดาให้ เพราะเดาผิดแล้วจะไม่มีอะไรฟ้องจนกว่าจะมีคนถามหาเครื่องนี้แล้วไม่มีใครตอบ

ไฟล์นี้ไม่เปลี่ยนอะไรด้วยตัวเอง มันมีผลแค่กับบรรทัด qm set ที่พิมพ์ไว้ให้ตอนจบเท่านั้น คนยังเป็นคนพิมพ์คำสั่งพวกนั้นเองอยู่ดี

เฟส 2 — ทำให้ boot ได้

เปิด VM ขึ้นมา มันจะ boot เข้าแผ่นติดตั้งที่ต่อไว้ให้แล้ว

$ qm start 9100

เปิดหน้าจอผ่านหน้าเว็บ PVE เลือก VM 9100 แล้วกด Console ตรงนี้ต้องใช้หน้าเว็บ ใช้ qm terminal ไม่ได้ เพราะเมนูของแผ่นติดตั้งออกทางจอภาพอย่างเดียว

ตรงนี้เป็นจุดที่สองรุ่นแยกทางกัน หน้าจอกู้ระบบของ CentOS 6 กับ 7 คนละโปรแกรมกันคนละหน้าตากัน ดูตรงที่เฟส 1 พิมพ์ทิ้งไว้ให้ตอนจบ บรรทัด Guest is หรือถ้าเลื่อนหายไปแล้วก็ดูจากหน้าจอที่ขึ้นมาเองก็ได้

ตัวโปรแกรมอ่านรุ่นจากในเครื่องเอง ไม่ต้องบอกมัน รอจนจบ

ทำไมถึงเหลือบรรทัดเดียว ของเดิมต้องพิมพ์ chroot /mnt/sysimage ก่อน แล้วพอเข้าไปแล้วมองไม่เห็นแผ่น ก็ต้องถอยออกมาผูกแผ่นเข้าไปเองอีกที ซึ่งเป็นคำสั่งยาวที่มีคำว่า sysimage กับ source ปนกันอยู่ในบรรทัดเดียว และ console ของ PVE ก็วางไม่ได้ ต้องพิมพ์มือล้วน

ตอนนี้ตัวโปรแกรมทำสองอย่างนั้นเอง มันรู้ว่าถูกเรียกจากนอก chroot เพราะเห็น /mnt/sysimage อยู่ แล้วมันจะหาแผ่นจาก /run/install/repo (รุ่น 7), /mnt/source (รุ่น 6) และทุกจุดที่เมาท์ iso9660 ไว้ ตรวจว่ามี repodata หรือ Packages จริงก่อนค่อยผูก แล้วเช็ก /dev /proc /sys ให้ด้วยว่าผูกเข้าไปครบไหม เสร็จแล้วมันถึง chroot ตัวเองเข้าไป จบแล้วมันถอดที่ผูกไว้ออกให้หมด — ถ้าค้างไว้ ตอน rescue ถอดระบบออกจะถอดไม่สะอาด แล้ว ext4 ต้อง fsck ตอนบูตจริงรอบแรก

ถ้าชินกับของเดิมมากกว่า พิมพ์ chroot /mnt/sysimage เองแล้วค่อยรัน /root/c2v-inside.sh ก็ยังใช้ได้เหมือนเดิมทุกอย่าง

ทดสอบด้วยไอพีอีกตัว

ขั้นนี้ข้ามได้ แต่ถ้าอยากลองใช้งานจริงก่อนสลับตัว ต้องทำตามลำดับนี้เท่านั้น — CT ตัวเก่ายังรันอยู่ตลอดเวลา ไม่ต้องดับ

ตัว CT ไม่เสี่ยงอะไรเลย เฟส 1 แค่อ่านข้อมูลออกมาจาก CT ที่กำลังรัน ตัวที่เสี่ยงคือ VM ที่ก๊อบมา เพราะพอเปิดขึ้นมามันเชื่อว่าตัวเองคือเครื่องจริง งานตามเวลา ตัวส่งเมล ตัวส่งค่าไปเครื่องมอนิเตอร์ ตัวสำรองข้อมูล จะเริ่มทำงานกับของจริงทันทีพร้อมกับเครื่องเก่า

ห้ามใส่การ์ดเน็ตแล้วค่อยเข้าไปแก้ทีหลัง ตั้งแต่กดเปิดจนกว่าคุณจะล็อกอินได้ เครื่องเปิดบริการทุกตัวไปแล้ว งานตามเวลาอาจยิงไปแล้ว เมลที่ค้างในคิวอาจส่งออกไปหาคนจริงแล้ว ต้องแก้ในไฟล์ก่อนเปิดเสมอ

หนึ่ง ดับ VM แล้วเปิดไฟล์ disk ออกมาแก้

ทำบน node ใหม่ ที่เดียวกับเฟส 1

$ qm stop 9100
$ IMG=$(pvesm path tank-hdd-nas:9100/vm-9100-disk-0.raw)
$ LOOP=$(losetup -Pf --show "$IMG")
$ mkdir -p /mnt/c2v
$ mount "${LOOP}p1" /mnt/c2v

อย่า chroot เข้าไป คำสั่งข้างล่างนี้อ่านกับแก้ไฟล์ล้วนๆ ทั้งหมดโดยตั้งใจ CT รุ่น 6 ถ้า chroot แล้วสั่งโปรแกรมในนั้น มันจะ segfault ทันที ด้วยเหตุผลเดียวกับที่เฟส 2 ต้องไปทำในแผ่น ส่วนรุ่น 7 chroot ได้ก็จริง แต่คำสั่งอย่าง systemctl ในนั้นจะไปคุยกับ systemd ของตัว node ไม่ใช่ของ image ที่ mount ไว้ ผลคือไม่เกิดอะไรขึ้น หรือแย่กว่านั้นคือไปโดนบริการของ node เข้าจริงๆ

$ ls -1 /mnt/c2v/etc/rc.d/rc3.d/S* | sed 's#.*/S[0-9]*##'

$ sed -i -E 's@^([^#].*[[:space:]](nfs|nfs4|cifs|glusterfs)[[:space:]].*)$@#C2VTEST# \1@' \

ทางที่ดีกว่า สะพานตัน แล้วใส่ไอพีจริงเข้าไปเลย

วิธีข้างบนใช้ไอพีปลอมเพราะกลัวชนของจริง แต่ไอพีปลอมมีราคาที่มองไม่เห็น — ไฟล์ตั้งค่าของบริการเก่าเกือบทุกตัวเขียนไอพีจริงไว้ตรงๆ พอไอพีไม่ตรง nginx จะ bind ไม่ขึ้นแล้วตายด้วยรหัส 99 ทั้งที่การ์ดปกติดีทุกอย่าง กลายเป็นว่าที่ทดสอบไปไม่ได้บอกอะไรเลย

ทำสะพานที่ไม่มีการ์ดจริงเสียบอยู่เลยสักใบแทน แพ็กเก็ตออกไปชนของจริงไม่ได้เพราะไม่มีทางออก ไม่ใช่เพราะเราตั้งไอพีหลบ พอเป็นแบบนั้นแล้วใส่ไอพีจริงของ CT ลงไปได้

เครื่องเราจัดการด้วย OVS ทั้งหมด ทำบนตัว node

$ ovs-vsctl add-br vmbr99
$ ovs-vsctl show

ไม่ต้องสั่ง add-port ให้มัน นั่นแหละคือทั้งหมดของเรื่องนี้

ต่อ VM เข้าไป จำนวนการ์ดกับค่าที่ต้องใส่ให้แต่ละใบ ไม่ต้องนึกเอง เฟส 1 อ่านมาจาก pct config แล้วพิมพ์บรรทัดที่ถูกต้องไว้ให้ตอนจบ เปลี่ยนแค่ชื่อสะพานเป็น vmbr99 หน้าตาประมาณนี้

$ qm set 9100 --net0 virtio,bridge=vmbr99,mtu=9000,firewall=0
$ qm set 9100 --net1 virtio,bridge=vmbr99,tag=255,firewall=0

ค่า mtu เป็นตัวที่หายเงียบที่สุดตอนย้าย ของ CT ค่านี้อยู่ในบรรทัด net0: ของฝั่ง host ไม่ได้อยู่ในไฟล์ไหนใน guest เลย แปลว่าถ้าใส่การ์ดให้ VM เฉยๆ มันจะขึ้นมาเป็น 1500 แล้วใช้งานได้ปกติทุกอย่างจนกว่าจะเจอข้อมูลก้อนใหญ่พอ ถึงตอนนั้นจะดูเหมือนปัญหาเน็ตช้า ไม่มีอะไรชี้กลับมาที่การย้าย ส่วน tag= ก็เรื่องเดียวกันแต่จะพังทันทีให้เห็นเลย

firewall=0 ใส่ไว้เพื่อไม่ให้ PVE แทรกสะพานแบบ Linux กับสายคู่หนึ่งเข้ามาคั่นระหว่างการ์ดของ VM กับ OVS ซึ่งจะทำให้ ovs-vsctl show อ่านยากขึ้นเปล่าๆ

ประตูออกเน็ตจะไม่มีใครตอบ อันนั้นถูกแล้ว เส้นทางไปหามันอยู่ในวงเดียวกับการ์ดอยู่แล้ว ระบบจึงเพิ่มเส้นทางได้สำเร็จและบริการเน็ตขึ้นเขียวปกติ ที่จะค้างคือของที่ต้องออกไปข้างนอกจริงๆ เช่นตัวลงโปรแกรม ตัวเทียบเวลา หรือฐานข้อมูลตัวลูกที่ตามหาตัวแม่ ค้างเพราะตั้งใจ ไม่ใช่อาการเสีย

เปิดทาง ssh ให้ตัวเอง

หน้าจอ console ของ PVE วางข้อความไม่ได้ ซึ่งเป็นปัญหาทันทีที่ต้องพิมพ์อะไรยาวกว่าสองสามคำ แก้ด้วยการให้ตัว node มีขาข้างหนึ่งยื่นเข้าไปในสะพานตันด้วย ขาแบบนี้ OVS เรียกว่า port ชนิด internal

$ ovs-vsctl add-port vmbr99 vlan99 -- set interface vlan99 type=internal
$ ovs-vsctl set port vlan99 tag=99
$ ip link set vlan99 mtu 9000 up
$ ip addr add 192.168.99.1/24 dev vlan99

แล้วเติมการ์ดอีกใบให้ VM ไว้คุยกับขานี้โดยเฉพาะ วง 192.168.99.x เป็นวงส่วนตัวที่ไม่เกี่ยวกับไอพีจริงของเครื่องเลย เลือกมาเพราะมันไม่ชนกับอะไร ต้องใส่ tag ให้ตรงกับขาของ node

$ qm set 9100 --net2 virtio,bridge=vmbr99,tag=99,mtu=9000,firewall=0

ถ้าขา vlan99 มี tag แล้วการ์ดของ VM ไม่มี จะไม่มีทางคุยกันได้เลย พอ port ไหนถูกตั้ง tag=99 OVS จะถือว่าเป็นขาแบบ access คือรับส่งเฉพาะ VLAN 99 เท่านั้น ส่วน port ที่ไม่ได้ตั้ง tag เลยเป็นขาแบบ trunk เฟรมที่ไม่มี tag วิ่งเข้าไปจะไปโผล่ที่ VLAN 0 คนละวงกัน สองข้างนี้ต้องเหมือนกัน จะใส่ tag ทั้งคู่หรือไม่ใส่ทั้งคู่ก็ได้ แต่ต้องเหมือนกัน ที่เขียนไว้ข้างบนใส่ทั้งคู่เพราะไฟล์ /etc/network/interfaces ของเครื่องนี้ตั้ง ovs_options tag=99 ไว้ที่ vlan99 อยู่แล้ว

เรื่อง mtu ก็คู่กัน สะพานตั้ง ovs_mtu 9000 ไว้ ถ้าการ์ดของ VM เป็น 1500 ssh จะเข้าได้เหมือนไม่มีอะไรผิด แล้วไปค้างตอน scp ไฟล์ใหญ่ ซึ่งเป็นอาการที่ไม่มีอะไรชี้กลับมาที่ตรงนี้เลย

ในตัว VM สร้างไฟล์ตั้งค่าให้การ์ดใบนั้น ไม่ใส่ GATEWAY เพราะประตูออกเน็ตของเครื่องนี้คือของจริงที่อยู่บนการ์ดใบแรก

cat > /etc/sysconfig/network-scripts/ifcfg-eth2 <<'EOF'
DEVICE=eth2
ONBOOT=yes
BOOTPROTO=none
IPADDR=192.168.99.10
NETMASK=255.255.255.0
EOF
service network restart

จากนั้นเข้าจาก node ได้เลย ที่เหลือพิมพ์ยาวแค่ไหนก็ได้

$ ssh root@192.168.99.10

ไฟล์ ifcfg-eth2 นี้จะโดนลบตอนก๊อบรอบถัดไป เพราะมันไม่มีอยู่ใน CT ตัวจริง ตัวก๊อบเห็นแล้วจะเก็บกวาดให้เอง ถ้ายังต้องใช้ทาง ssh นี้อยู่ ให้เขียนใหม่ทุกครั้งหลังก๊อบ หรือเก็บไว้ในไฟล์ที่อยู่นอกรายการที่ก๊อบ แล้วเอามาวางคืน

เช็กว่าบริการขึ้นจริง

ต้องเช็กจากในตัว VM เท่านั้น เพราะบริการอย่าง nginx ผูกกับไอพีจริงเจาะจง ไม่ได้ฟังทุกใบ ยิงจากข้างนอกเข้าวงจริงไม่ได้อยู่แล้วเพราะสะพานมันตัน

systemctl --failed
curl -sS -o /dev/null -w '%{http_code}\n' http://58.82.170.211/
ss -lntp | head -20

บรรทัดแรกต้องว่าง หรือเหลือแต่ตัวที่รู้อยู่แล้วว่าจะไม่ขึ้น

สะพานที่สร้างด้วย ovs-vsctl อยู่รอดข้าม reboot เพราะ OVS เก็บของมันเองไว้ที่ /etc/openvswitch/conf.db ซึ่งเป็นคนละที่กับ /etc/network/interfaces ตัวที่ไม่รอดคือไอพีที่ใส่ด้วย ip addr add ถ้าอยากได้ถาวรจริงให้เขียนลงไฟล์ interfaces แทน

$ cat >> /etc/network/interfaces <<'EOF'

auto vmbr99
iface vmbr99 inet manual
    ovs_type OVSBridge
    ovs_ports vlan99

auto vlan99
iface vlan99 inet static
    address 192.168.99.1/24
    ovs_type OVSIntPort
    ovs_bridge vmbr99
EOF
$ ifup vmbr99

ทดสอบเสร็จแล้วเก็บกวาด สั่งบนตัว node

$ qm set 9100 --delete net2
$ ovs-vsctl del-br vmbr99

ของจริงที่ ovs-vsctl show บอก คือของจริง ถ้ามันยังเห็น vmbr99 อยู่แปลว่ายังไม่ได้ลบ ไม่ว่าไฟล์ interfaces จะเขียนว่าอะไร

หก ทดสอบเสร็จแล้ว ดับทิ้ง

$ qm shutdown 9100

อย่าใช้งานจริงบน VM ตัวทดสอบ อะไรที่พิมพ์เพิ่มเข้าไปตอนทดสอบ จะโดนลบทิ้งหมดตอนก๊อบรอบสุดท้ายในขั้นถัดไป มันเป็นสำเนาสำหรับดูเฉยๆ ตามตั้งใจ ของจริงยังอยู่ที่ CT ตัวเก่าเสมอ

ของที่ต้องแก้คืนเอง กับของที่กลับมาเอง

ตอนก๊อบรอบสุดท้ายในขั้นถัดไป ของเดิมจาก CT จะทับกลับมาให้เองเกือบหมด ยกเว้นสองไฟล์ที่ตัวก๊อบข้ามไว้ตั้งแต่แรก สองอันนี้ต้องแก้คืนด้วยมือ ไม่งั้นเครื่องจริงจะขึ้นมาแบบพิการ

ที่แก้ไว้ตอนทดสอบรอบสุดท้ายจัดการให้มั้ย
ifcfg-eth0กลับเป็นไอพีจริงให้เอง
rc3.dบริการที่ตัดไป กลับมาเอง
multi-user.target.wantsบริการที่ตัดไป กลับมาเอง
คิวเมลกลับมาเอง
เลขเจ้าของไฟล์เฟส 1 วัดใหม่แล้วลบส่วนที่บวกไว้ออกให้ทุกรอบ
/etc/fstabไม่กลับ ต้องเอา #C2VTEST# ออกเอง
/bootไม่กลับ ตัวก๊อบข้ามทั้งโฟลเดอร์ ถ้าเคยไปแก้ grub ไว้ก็ยังเป็นของที่แก้
ifcfg-eth2โดนลบ เพราะ CT ไม่มีไฟล์นี้ ถ้ายังใช้ทาง ssh อยู่ต้องเขียนใหม่
/etc/securettyเสียหาย บรรทัด ttyS0 หลุด ล็อกอินทางพอร์ตอนุกรมไม่ได้
getty@tty1เสียหาย ทางลัดโดนลบ หน้าจอ noVNC จะดำ

สามอันล่างสุดคือของที่เฟส 2 เป็นคนแก้ไว้ ไม่ใช่ของที่คุณแก้ตอนทดสอบ แต่มันอยู่ใน /etc เหมือนกันจึงโดนทับเหมือนกัน ทั้งสามอันแก้คืนได้ด้วยบรรทัดเดียวจากในตัว VM หลังก๊อบเสร็จ ไม่ต้องต่อแผ่น

/root/c2v-inside.sh
reboot

คำสั่งแก้คืน ทำหลังก๊อบรอบสุดท้ายเสร็จ ก่อนเปิดเครื่องจริง

$ LOOP=$(losetup -Pf --show "$(pvesm path tank-hdd-nas:9100/vm-9100-disk-0.raw)")
$ mount "${LOOP}p1" /mnt/c2v
$ sed -i 's@^#C2VTEST# @@' /mnt/c2v/etc/fstab
$ grep -Ev '^[[:space:]]*#' /mnt/c2v/etc/fstab
$ umount /mnt/c2v && losetup -d "$LOOP"

ถ้าเปิดไปแล้วโดยยังไม่ได้ตัดอะไรเลย ยังกู้ได้ ดับทันทีแล้วเปิดใหม่แบบไม่ให้บริการไหนขึ้นเลย ด้วยการเติมคำว่า single ต่อท้ายบรรทัด kernel ที่หน้าเมนู boot จะได้หน้าจอ root เปล่าๆ ที่ไม่มีเน็ตและไม่มีงานตามเวลา เข้าไปแก้แล้วค่อย telinit 3 วิธีเติมไม่เหมือนกันสองรุ่น

CentOS 6กด a ที่เมนู แล้วพิมพ์ single ต่อท้ายบรรทัดที่โผล่มา กด Enter

CentOS 7กด e ที่เมนู เลื่อนลงไปหาบรรทัดที่ขึ้นต้นด้วย linux16 พิมพ์ single ต่อท้ายบรรทัดนั้น แล้วกด Ctrl + X ปุ่ม Enter ไม่ใช่ปุ่มสั่งบูตในเมนูนี้

6

ย้ายจริง

ถึงตรงนี้ VM boot ได้แล้ว เหลือแค่ก๊อบข้อมูลรอบสุดท้ายแล้วสลับตัว ช่วงนี้บริการจะดับ ยาวเท่ากับเวลาก๊อบส่วนที่เปลี่ยน

หนึ่ง ดับ CT ตัวเก่า พิมพ์บนเครื่องเก่า

$ ssh root@10.100.1.11
$ pct shutdown 100
$ pct status 100

สอง กลับมาที่ node ใหม่ ก๊อบรอบสุดท้ายด้วย --stopped

$ ./tools/c2v-prepare.sh \
    --old-node 10.100.1.11 \
    --old-ctid 100 \
    --vmid 9100 \
    --storage tank-hdd-nas \
    --iso local:iso/CentOS-7-x86_64-DVD-2009.iso \
    --stopped

รอบนี้ไม่ทับ kernel ที่เพิ่งลงไป เพราะตัวก๊อบข้าม /boot กับ /etc/fstab ไว้ตั้งแต่แรก จะรันก่อนหรือหลังเฟส 2 ก็ปลอดภัยเท่ากัน

สาม เฉพาะคนที่ทำขั้น 5 มา แก้ /etc/fstab คืน ถ้าไม่ได้ทำขั้น 5 ให้ข้ามไปข้อสี่

$ LOOP=$(losetup -Pf --show "$(pvesm path tank-hdd-nas:9100/vm-9100-disk-0.raw)")
$ mkdir -p /mnt/c2v && mount "${LOOP}p1" /mnt/c2v
$ sed -i 's@^#C2VTEST# @@' /mnt/c2v/etc/fstab
$ grep -Ev '^[[:space:]]*#' /mnt/c2v/etc/fstab
$ umount /mnt/c2v && losetup -d "$LOOP"

ไอพีทดสอบกับบริการที่ตัดไป ไม่ต้องแก้คืน ข้อสองทับกลับมาให้เองแล้ว แต่ /etc/fstab อยู่ในรายการที่ตัวก๊อบข้ามเสมอ มันจึงยังค้างเป็น #C2VTEST# อยู่ ลืมข้อนี้แล้วเครื่องจริงจะขึ้นมาโดยไม่มีที่เก็บข้อมูลจากเครื่องอื่น

สี่ ใส่การ์ดเน็ตให้ VM แล้วเปิด ต้องใส่ให้ครบทุกใบที่ CT เคยมี เฟส 1 พิมพ์บรรทัดที่ถูกต้องไว้ให้แล้วตอนจบ ก๊อบมาจากตรงนั้นดีที่สุด อย่านึกเอง ตัวอย่างของเครื่องที่มีสองใบและใบแรกเป็น jumbo

$ qm set 9100 --net0 virtio,bridge=vmbr0,mtu=9000
$ qm set 9100 --net1 virtio,bridge=vmbr1,tag=255
$ qm start 9100
$ qm terminal 9100

ขาดการ์ดไปใบหนึ่ง ไม่ได้แปลว่าเสียแค่ใบนั้น ไฟล์ตั้งค่าของใบที่หายยังอยู่ในเครื่อง บริการที่ผูกกับไอพีของใบนั้นจะพยายาม bind แล้วตายด้วยรหัส 99 ทั้งที่อีกใบทำงานปกติ อาการที่เห็นคือเว็บบางตัวขึ้นบางตัวไม่ขึ้น ซึ่งอ่านเหมือนปัญหาเส้นทางแต่ไม่ใช่ ค่า mtu กับ tag ก็ต้องตรงของเดิมด้วย ไม่งั้นได้เครื่องที่ดูดีแต่ส่งข้อมูลก้อนใหญ่ไม่ผ่าน

ก่อนเช็กอย่างอื่น รันบรรทัดนี้ในหน้า console ของ VM ก่อนเสมอ การก๊อบรอบสุดท้ายเอา /etc จาก CT กลับมาทับทั้งชุด ของที่เฟส 2 เคยแก้ไว้ในนั้นหายไปหมด — HWADDR กลับเข้ามาในไฟล์ ifcfg ทุกใบ, ttyS0 หลุดจาก /etc/securetty, ทางลัดของ getty@tty1 โดนลบ ผลคือการ์ดไม่ขึ้นสักใบและหน้าจอดำ ทั้งที่เมื่อวานทดสอบผ่านหมด

/root/c2v-inside.sh
reboot

สั้นแบบนี้เพราะออกแบบมาให้พิมพ์เองได้ในหน้า console ที่วางข้อความไม่ได้ ปกติรอบนี้จะเห็นว่า kernel กับ boot loader ลงไว้แล้ว เลยข้ามขั้นที่ใช้เวลานานทั้งหมด ใช้เวลาไม่กี่วินาที

ยกเว้นตอนที่เฟส 1 ขึ้น WARN ว่ามีของหาย ให้ดูบรรทัดท้ายๆ ของเฟส 1 ก่อนกดเปิดเครื่องเสมอ ถ้ามันบอกว่า this image has a kernel in /boot but not: ... แปลว่าของที่เฟส 2 เคยลงไว้โดนก๊อบรอบนี้ลบไป มันจะใส่แผ่นกลับเข้าไปในไดรฟ์ให้เองแล้วยังบูตจากดิสก์เหมือนเดิม รอบนี้ c2v-inside.sh จะกลับไปลงจากแผ่นใหม่ ใช้เวลาเป็นนาที ไม่ใช่วินาที ถ้ามันบอกว่า phase 2's kernel, bootloader and dracut all survived the sync ก็คือปกติ

ของที่ไม่โดนทับกลับมี /boot, /etc/fstab, /etc/mtab, 70-persistent-net.rules, ตัว boot loader ที่อยู่นอกระบบไฟล์ และของสามอย่างที่เฟส 2 ลงไว้เอง คือ /lib/modules, grub และ dracut เพราะทั้งหมดอยู่ในรายการที่ตัวก๊อบข้ามไว้ตั้งแต่แรก ส่วน /root/c2v-inside.sh เฟส 1 วางให้ใหม่ทุกรอบอยู่แล้ว จึงเป็นรุ่นล่าสุดเสมอ

ห้า เช็กในตัว VM ว่าไอพีขึ้นแล้ว

ip addr show eth0
ping -c 3 10.100.1.1

ถ้าไอพียังไม่ขึ้น สั่งบรรทัดนี้ในตัว VM แล้วดูใหม่

service network restart

CentOS 7ถ้าบรรทัดบนตอบว่าไม่รู้จักบริการชื่อ network แปลว่าเครื่องนี้ไม่ได้ลง initscripts ไว้ ให้ใช้บรรทัดนี้แทน

systemctl restart NetworkManager
nmcli device reapply eth0

ถ้ายังไม่ขึ้นอีก ดูว่าชื่อการ์ดยังเป็น eth0 อยู่จริงไหม เพราะไฟล์ตั้งค่าที่ก๊อบมาจาก CT ตั้งชื่อนี้ไว้ชื่อเดียว

ip -o link show
cat /proc/cmdline

บรรทัดล่างต้องมีคำว่า net.ifnames=0 กับ biosdevname=0 อยู่ ถ้าไม่มี ชื่อการ์ดจะกลายเป็น ens18 แล้วไฟล์ ifcfg-eth0 จะไม่ถูกใช้เลย แก้โดยกลับไปรันเฟส 2 ใหม่ อย่าไปแก้ชื่อไฟล์ให้ตรงกับ ens18 เพราะรอบก๊อบถัดไปมันจะทับกลับมาเป็น eth0 อีก

หก ให้มันเปิดเองตอน node บูต แล้วปิด CT เก่าไม่ให้เปิดเองด้วย

$ qm set 9100 --onboot 1
$ ssh root@10.100.1.11 pct set 100 --onboot 0

อย่าเพิ่งลบ CT เก่า ทิ้งไว้แบบดับๆ อย่างน้อยสองสามวัน มันคือ rollback ทางเดียวที่มี ถ้าต้องถอย แค่ดับ VM แล้วเปิด CT เก่ากลับ

7

คำสั่งทั้งหมดรวดเดียว

สำหรับตอนที่ทำเป็นแล้ว ตั้งค่า 5 บรรทัดบนสุดครั้งเดียว ที่เหลือก๊อบวางทีละท่อน

OLD=10.100.1.11
CTID=100
VMID=9100
STOR=tank-hdd-nas
ISO=local:iso/CentOS-7-x86_64-DVD-2009.iso   # must match the CT's own release
LABIP=192.168.99.10   # lab-only NIC for ssh. the real IPs stay untouched

cd ~/ct-migrate

# phase 1 - copy the rootfs
./tools/c2v-prepare.sh --old-node $OLD --old-ctid $CTID --vmid $VMID \
  --storage $STOR --iso $ISO --dry-run
./tools/c2v-prepare.sh --old-node $OLD --old-ctid $CTID --vmid $VMID \
  --storage $STOR --iso $ISO --bwlimit 500000

# phase 2 - open the web console and boot the ISO into its rescue mode:
#           EL6:  type   linux rescue           at the boot prompt
#           EL7:  choose Troubleshooting > Rescue a CentOS system > 1) Continue
#           both: mount READ/WRITE, then in the rescue shell one line -
#           it binds the DVD onto the image and chroots itself:
#             /mnt/sysimage/root/c2v-inside.sh
#             exit
qm start $VMID

# first real boot
qm stop $VMID
qm set $VMID --delete ide2
qm set $VMID --boot order=virtio0
qm start $VMID
qm terminal $VMID
qm shutdown $VMID

# OPTIONAL - test on a dead-end bridge while the CT keeps running.
# everything up to 'qm start' MUST be done before the VM is ever
# given a NIC. do not chroot into /mnt/c2v: on EL6 it segfaults, and
# on EL7 systemctl there talks to the node's systemd, not the image.
qm stop $VMID
LOOP=$(losetup -Pf --show "$(pvesm path $STOR:$VMID/vm-$VMID-disk-0.raw)")
mkdir -p /mnt/c2v && mount "${LOOP}p1" /mnt/c2v

#   look first - add anything you see here to the list below.
#   EL6 answers on the first line, EL7 on the second
ls -1 /mnt/c2v/etc/rc.d/rc3.d/S* | sed 's#.*/S[0-9]*##'
ls -1 /mnt/c2v/etc/systemd/system/multi-user.target.wants/ | sed 's/\.service$//'
cat /mnt/c2v/var/spool/cron/* 2>/dev/null
grep -Ev '^[[:space:]]*#' /mnt/c2v/etc/fstab | grep -E 'nfs|cifs|gluster'

#   then cut - both lines are harmless on the release that does not use them

อาการคือเปิดเครื่องแล้วผ่านหมด ล็อกอินได้ ls ได้ df ได้ ข้อมูลอยู่ครบ แต่ systemctl --failed ยาวเป็นหางว่าว และเกือบทุกตัวบ่นเรื่องเดียวกัน

ทำไมถึงเป็นแบบนั้น

CT แบบ unprivileged เก็บไฟล์ทุกไฟล์ด้วยเลขเจ้าของที่ถูกบวกไว้แล้วตามตารางแปลงของ kernel ค่ามาตรฐานของ PVE คือบวกหนึ่งแสน แปลว่า root ข้างใน CT ซึ่งเห็นตัวเองเป็นเลข 0 พอมองจากฝั่ง host จริงๆ แล้วไฟล์นั้นเป็นของเลข 100000 บน PVE 6 ตัวเลขนี้อยู่ในไฟล์จริงๆ ไม่ได้แปลงตอนอ่าน

VM ไม่มีตารางแปลงนั้น เลขที่ติดมาจึงเป็นเลขที่ใช้ตรงๆ พูดสั้นๆ คือ root ของ CT คือ 100000 ส่วน root ของ VM คือ 0 ก๊อบข้ามมาเฉยๆ เลขไม่ตรงกัน

แล้วทำไมยัง ls ได้ทั้งที่เจ้าของไฟล์ผิดหมด เพราะ root ยังถือสิทธิ์ข้ามการตรวจเจ้าของไฟล์อยู่ ทุกอย่างที่เป็นการอ่านเขียนธรรมดาจึงผ่านหมด นี่คือเหตุผลที่มันซ่อนตัวได้เก่งขนาดนี้

สิ่งที่พังคือโปรแกรมกลุ่ม setuid โปรแกรมพวกนี้ตอนรันจะไปหยิบสิทธิ์จากเลขเจ้าของของตัวไฟล์ ไม่ได้หยิบจากคนที่สั่ง ปกติ /bin/mount เป็นของเลข 0 ใครสั่งก็กลายเป็น 0 แต่ตอนนี้มันเป็นของเลข 100000 root สั่งแล้วเลยถูกลดสิทธิ์ลงไปเป็น 100000 แทน mount เลยปฏิเสธ

จากตรงนั้นลูกโซ่ก็ครบ kernel เมาท์ระบบไฟล์หลักแบบอ่านอย่างเดียวมาตั้งแต่แรกตามปกติ ตัวที่จะมาเปลี่ยนให้เขียนได้เรียก mount ไม่สำเร็จ ระบบไฟล์เลยอ่านอย่างเดียวตลอดกาล แล้วทุกบริการที่ต้องเขียนตอนเปิดก็ตายด้วยรหัส 30 เหมือนกันหมด

ปัญหาไก่กับไข่คือจะแก้เจ้าของไฟล์ต้องเขียนได้ก่อน แต่ตอนนี้เขียนไม่ได้ ทางออกคือสั่ง kernel ให้เมาท์แบบเขียนได้ตั้งแต่แรก ไม่ต้องพึ่งตัวที่พัง สั่ง reboot แล้วที่หน้าเมนู boot

CentOS 7กด e เลื่อนไปหาบรรทัดที่ขึ้นต้นด้วย linux16 ต่อท้ายบรรทัดนั้นด้วยคำว่า rw แล้วกด Ctrl + X

CentOS 6กด a แล้วพิมพ์ rw ต่อท้ายบรรทัดที่โผล่มา กด Enter

คราวนี้จะได้ระบบไฟล์ที่เขียนได้ พอล็อกอินแล้วสั่งบรรทัดเดียวจบ เฟส 2 รุ่นใหม่ตรวจเรื่องนี้เป็นอย่างแรกและแก้ให้เอง

/root/c2v-inside.sh
reboot

รอบนี้บูตปกติได้เลย ไม่ต้องไปแตะเมนู เพราะ mount กลับมาเป็นของเลข 0 แล้ว

ถ้าไฟล์ c2v-inside.sh ในเครื่องเป็นรุ่นเก่าที่ยังไม่มีขั้นนี้ แก้มือได้ สองบรรทัด สั้นพอจะพิมพ์เองในหน้า console ที่ paste ไม่ได้

find / -xdev -uid 100000 -exec chown -h 0 {} +
find / -xdev -gid 100000 -exec chgrp -h 0 {} +

สองบรรทัดนี้แก้เฉพาะของที่เป็นของ root ซึ่งพอให้เครื่องกลับมาใช้งานได้ แต่ผู้ใช้อื่นเช่น mysql หรือ apache จะยังเป็นเลขที่บวกไว้อยู่ ให้ตามเก็บทีละเลข เอาเลขจากบรรทัดแรก

find / -xdev -printf '%U\n' | sort -un
find / -xdev -uid 100027 -exec chown -h 27 {} +

ไล่จากเลขน้อยไปมากเสมอ เพราะทุกเลขมีแต่ลดลง ตัวที่แก้ไปแล้วจึงไม่มีทางโดนหยิบซ้ำในรอบหลัง

อย่าลืมกลับไปแก้ที่ต้นทางด้วย ที่แก้ในตัว VM คือแก้ปลายเหตุ ถ้าเฟส 1 บนเครื่อง host ยังเป็นรุ่นเก่า พอก๊อบรอบถัดไปเลขจะกลับมาบวกใหม่ทั้งเครื่อง เอาชุด tools/ รุ่นใหม่ขึ้นไปทับแล้วรันเฟส 1 อีกรอบ รุ่นใหม่จะวัดค่าที่บวกไว้เองจากตัว image แล้วลบออกให้ทุกครั้งหลังก๊อบเสร็จ พร้อมตรวจซ้ำว่าไม่เหลือค้าง ถ้ายังเหลือมันจะหยุดและไม่ยอมให้ไปต่อ

ถ้าอยากรู้ว่า CT ต้นทางเป็นแบบไหน ดูจากเครื่องเก่า มีบรรทัด unprivileged: 1 คือใช่

$ pct config 140 | grep -E 'unprivileged|idmap'

หน้าจอค้างที่คำว่า GRUB หรือขึ้น No bootable device

ตัว boot loader ไม่ได้ลง เฟส 2 ไม่จบ ให้เอาแผ่นกลับมาต่อแล้วทำเฟส 2 ใหม่ ต้องเป็นแผ่นรุ่นเดียวกับ CT เหมือนเดิม บรรทัดล่างนี้เป็นตัวอย่างของรุ่น 7

$ qm stop 9100
$ qm set 9100 --ide2 local:iso/CentOS-7-x86_64-DVD-2009.iso,media=cdrom
$ qm set 9100 --boot 'order=ide2;virtio0'
$ qm start 9100

เฟส 2 ขึ้นคำว่า is not EL6 หรือบอกให้ใส่แผ่น CentOS 6 ทั้งที่เครื่องเป็นรุ่น 7

ไฟล์ /root/c2v-inside.sh ในเครื่องนั้นเป็นของเก่า รุ่นที่ยังไม่รู้จัก CentOS 7 อย่าปล่อยให้มันทำต่อ ถ้ามันหาแผ่นเจอขึ้นมา มันจะลง grub 0.97 ทับระบบรุ่น 7 ซึ่งพังกว่าเดิม เพราะของเดิมก็เสียไปด้วย

ดูตรงวงเล็บเหลี่ยมในบรรทัดแรกที่มันพิมพ์ออกมา นั่นคือวันที่ของตัวโปรแกรม ถ้าไม่มีวงเล็บนั้นเลย แปลว่าเก่ากว่าทุกรุ่นที่เอกสารนี้พูดถึง

ต้นเหตุอยู่ที่เครื่อง host ไม่ใช่ที่ VM เพราะเฟส 1 เป็นคนวางไฟล์นี้ลงไป แปลว่าโฟลเดอร์ tools/ บนเครื่องที่รันเฟส 1 ยังเป็นชุดเก่า ให้ก๊อบชุดใหม่ขึ้นไปทับ แล้วรันเฟส 1 อีกรอบ มันวางไฟล์ให้ใหม่ทุกรอบอยู่แล้ว รอบนี้เร็วเพราะก๊อบเฉพาะส่วนต่าง ระหว่างนั้นปิดหน้าจอ rescue ทิ้งไว้ได้เลย ยังไม่ต้องทำอะไร

ถ้า image ก้อนนั้นถูกสร้างด้วยชุดเก่า ป้ายชื่อของมันจะเป็น c6root ไม่ใช่ c7root พอรันเฟส 1 ชุดใหม่ทับ โปรแกรมจะหยุดแล้วบอกให้ใส่ --label c6root ใส่ตามนั้นถ้าจะใช้ก้อนเดิมต่อ หรือถ้าอยากเริ่มใหม่ให้สะอาด สั่ง qm destroy แล้วรันเฟส 1 ตั้งแต่ต้น ไม่ต้องใส่ --label

ls -l /dev/sr0
grep iso9660 /proc/mounts

ว่างทั้งคู่คือลืมต่อแผ่นให้ VM ตั้งแต่แรก ต้องกลับไปสั่งที่ host แล้วเปิดใหม่ รันเฟส 1 ซ้ำก็ได้ มันใส่แผ่นกลับให้เอง หรือสั่งตรงๆ ก็ได้

qm set 9100 --ide2 local:iso/CentOS-7-x86_64-DVD-2009.iso,media=cdrom

เฟส 2 หยุดแล้วบอกว่า yum finished but there is still no bootloader

แผ่นที่ต่ออยู่เป็น Minimal ไม่ใช่แผ่นเต็ม ตัว yum จบด้วยสถานะสำเร็จทั้งที่ลงได้ไม่ครบ เพราะมันถือว่าชื่อที่หาไม่เจอไม่ใช่ความผิดพลาด ตัวโปรแกรมเลยต้องเช็กซ้ำเองว่ามี boot loader จริงไหม นี่คือจุดที่มันจับได้ ให้เปลี่ยนเป็นแผ่น DVD เต็มแล้วเริ่มเฟส 2 ใหม่ ไม่ต้องทำเฟส 1 ซ้ำ

ขึ้น dracut แล้วค้างที่ Warning: /dev/root does not exist

initramfs ไม่มี driver ของ virtio ให้ boot เข้า rescue ใหม่ แล้วสั่งบรรทัดนี้ใน chroot โดยใส่เลข kernel ตามที่เห็นในบรรทัด kernel: ตอนเฟส 2

$ ls -1 /boot/vmlinuz-*

CentOS 6เลขจะหน้าตาแบบนี้

/root/c2v-inside.sh --kver 2.6.32-754.35.1.el6.x86_64

CentOS 7ของรุ่น 7 สั้นกว่า

/root/c2v-inside.sh --kver 3.10.0-1160.el7.x86_64

Kernel panic — unable to mount root fs

ชื่อ label ของ disk ไม่ตรงกับที่เขียนไว้ใน grub เช็กด้วยคำสั่งนี้ในโหมด rescue บรรทัดของ grub แยกตามรุ่น ที่เหลือเหมือนกัน

blkid
cat /mnt/sysimage/etc/fstab

CentOS 6ไฟล์ของ grub รุ่นเก่าอยู่ที่นี่

cat /mnt/sysimage/boot/grub/grub.conf

CentOS 7ของ grub2 อยู่คนละที่ คนละชื่อ

cat /mnt/sysimage/boot/grub2/grub.cfg

ทั้งสามที่ต้องเป็นชื่อเดียวกัน ปกติคือ c7root ส่วน image ที่สร้างไว้นานแล้วจะเป็น c6root

CentOS 7บูตขึ้นแล้วแต่หน้าจอ noVNC ดำสนิท ไม่มีอะไรให้พิมพ์

ตัวเครื่องขึ้นปกติแล้ว แค่ไม่มีใครวาดหน้าจอให้ ลองเข้าทาง qm terminal 9100 ก่อน ถ้าทางนั้นได้แปลว่าที่ขาดคือ getty@tty1 เฟส 2 เปิดให้อยู่แล้ว ถ้าไม่ได้เปิดแปลว่าใช้ c2v-inside.sh รุ่นเก่า สั่งในตัว VM เองได้เลย

systemctl enable --now getty@tty1

รุ่น 6 ไม่มีอาการนี้ เพราะ upstart เปิด tty1 ให้ตั้งแต่ต้นอยู่แล้ว

CentOS 7รันเฟส 1 ซ้ำในเครื่องที่เคยบูตได้ แล้วมันวนอยู่ที่ Failed to mount /

เครื่องนี้เคยบูตได้ปกติมาก่อน สิ่งเดียวที่ทำลงไปคือรันเฟส 1 ซ้ำเพื่อวาง c2v-inside.sh รุ่นใหม่ลงไป ซึ่งเป็นวิธีที่เอกสารนี้บอกให้ทำเองในอีกหลายข้อ แล้วรอบถัดมามันขึ้นชุดนี้วนไม่จบ

[DEPEND] Dependency failed for D-Bus System Message Bus Socket. Starting Login Service... [FAILED] Failed to start Login Service. [ OK ] Stopped Login Service. Mounting /... [FAILED] Failed to mount /.

อาการมีสองระดับ ตัวที่หนักคือวนแบบข้างบนจนไม่ได้หน้าจอให้พิมพ์เลย ตัวที่เบากว่าคือบูตจนได้ shell แต่ระบบไฟล์หลักเขียนไม่ได้ และ systemctl --failed ขึ้นตัวเดียวคือ systemd-logind.service ทั้งสองแบบเป็นเรื่องเดียวกัน ต่างกันแค่ว่าบูตไปได้ไกลแค่ไหนก่อนจะติด

อย่าเพิ่งสับสนกับข้อ unprivileged ข้างบน ข้อนั้นระบบไฟล์เขียนไม่ได้เหมือนกัน แต่ mount จะบ่นเรื่องเลข UID ส่วนข้อนี้สั่ง mount -o remount,rw / แล้วผ่าน ถ้าสั่งแล้วผ่าน คืออ่านข้อนี้ ไม่ใช่ข้อนั้น

ทำไมถึงเป็นแบบนั้น

ไฟล์ /etc/mtab ต้องเป็นคนละอย่างกันในสองช่วงของงานนี้ ตอนเข้าโหมด rescue มันต้องเป็นไฟล์จริง ไม่งั้นโปรแกรมกู้ระบบตายทั้งตัว ตามข้อล่างสุดของหน้านี้ เฟส 1 จึงเขียนทับให้เป็นไฟล์เปล่า แต่พอเครื่องบูตด้วยตัวเองแล้ว รุ่น 7 ต้องการทางลัดกลับ เพราะ systemd ไม่เคยเขียนไฟล์นี้ให้ใคร เฟส 2 จึงเปลี่ยนกลับให้ตอนจบ

สคริปต์รุ่นเก่าเขียนทับทุกรอบ ไม่ได้ดูว่า image ก้อนนั้นผ่านเฟส 2 มาแล้วหรือยัง พอรันเฟส 1 ซ้ำในเครื่องที่บูตได้แล้ว ทางลัดที่เฟส 2 วางไว้ก็หายไป กลายเป็นไฟล์เปล่า และรุ่น 7 ไม่มี rc.sysinit มาสร้างใหม่ให้เหมือนรุ่น 6 มันจึงว่างอยู่อย่างนั้นตลอดไป

ของที่อ่านตารางเมาท์จากไฟล์นี้ก็เลยเห็นว่าไม่มีอะไรเมาท์อยู่สักอย่าง จากตรงนั้นลูกโซ่ก็ไล่ลงมาเป็นทอดๆ ดูได้จาก journalctl ตอนบูต

journalctl -b | grep -A2 'Failed to mount'
systemd[1]: Failed to mount /. systemd-logind[487]: Failed to connect to system bus: No such file or directory systemd-logind[487]: Failed to fully start up daemon: No such file or directory systemd[1]: Failed to start Login Service.

อ่านจากล่างขึ้นบน ตัวที่ตายจริงคือบรรทัดบนสุด ที่เหลือเป็นผลตามมา เมาท์ / ไม่ผ่าน ช่องทางคุยกันของ dbus เลยไม่ถูกสร้าง systemd-logind ต่อไม่ติดแล้วตาย systemd เห็นว่าตายก็เปิดใหม่ให้ วนแบบนี้จนครบโควตา

ตรงนี้สำคัญ พอวนครบโควตาแล้ว systemd จะเลิกเปิดให้ถาวร systemctl status systemd-logind จะขึ้นว่า start-limit แปลว่าต่อให้แก้ต้นเหตุแล้วมันก็ยังไม่ขึ้นมาเอง ต้องสั่งเปิดเองหรือ reboot

แก้ยังไง ถ้ายังได้ shell

เอาทางลัดกลับคืน แล้วต้องสั่งเปิด logind เองด้วย เพราะเหตุผลย่อหน้าบน สองบรรทัด สั้นพอจะพิมพ์เองในหน้า console ที่ paste ไม่ได้ ชื่อบริการคือ systemd-logind ไม่ใช่ logind เฉยๆ

ln -sf /proc/self/mounts /etc/mtab
systemctl restart systemd-logind

ต้องขึ้นว่า active (running) แล้ว reboot หนึ่งรอบเพื่อดูว่ารอบหน้าบูตสะอาดจริง จบแล้วบรรทัดนี้ต้องว่าง

systemctl --failed

แก้ยังไง ถ้าวนจนไม่ได้ shell เลย

แก้จากเครื่อง host แทน อันนี้สั่งที่ host ไม่ใช่ในตัว VM จึง paste ได้ ต้องปิด VM ก่อน ห้ามเมาท์ดิสก์ของเครื่องที่ยังเปิดอยู่ เปลี่ยนเลข 9100 กับชื่อ storage ตามของจริง

$ qm stop 9100
$ IMG=$(pvesm path tank-hdd-nas:9100/vm-9100-disk-0.raw)
$ LOOP=$(losetup -P -f --show "$IMG")
$ mkdir -p /mnt/fix && mount ${LOOP}p1 /mnt/fix
$ ln -sf /proc/self/mounts /mnt/fix/etc/mtab
$ umount /mnt/fix && losetup -d $LOOP
$ qm start 9100

รอบนี้จะบูตผ่าน ไม่ต้องไปสั่งเปิด logind เอง เพราะ reboot ล้างโควตาที่นับไว้ให้อยู่แล้ว

วิธีที่ง่ายกว่าถ้าเอาชุด tools/ รุ่นใหม่ขึ้นไปแล้ว คือรันเฟส 1 ซ้ำอีกรอบเลย รุ่นใหม่จะเจอเองว่าไฟล์นี้ถูกทำพังไว้แล้วซ่อมให้ ไม่ต้องเมาท์มือ

ต้นเหตุอยู่ที่ชุดสคริปต์บนเครื่อง host ถ้ายังเป็นรุ่นเก่า รันเฟส 1 ซ้ำอีกครั้งก็พังใหม่อีกครั้ง เอาชุด tools/ รุ่นใหม่ขึ้นไปทับ รุ่นใหม่จะดูก่อนว่า image ก้อนนั้นบูตด้วยตัวเองได้แล้วหรือยัง ถ้าได้แล้วมันจะไม่แตะทั้ง /etc/mtab และ /etc/fstab เลย เพราะสองไฟล์นั้นคือสิ่งที่พาเครื่องผ่านการบูตรอบล่าสุดมา และถ้าเจอ image รุ่น 7 ที่ถูกทำพังไว้แล้ว มันจะซ่อมให้ พร้อมขึ้น WARN สามบรรทัดบอกว่าซ่อมอะไร ส่วนรุ่น 6 ปล่อยเป็นไฟล์ธรรมดาเหมือนเดิม เพราะ rc.sysinit สร้างใหม่ให้ทุกบูตอยู่แล้ว

ที่เฟส 1 รุ่นใหม่ดูว่าเคยผ่านเฟส 2 มาแล้วหรือยัง มันไม่ได้ดูจากไฟล์ในระบบไฟล์ แต่ดูจากลายเซ็นของ boot loader ที่อยู่นอกระบบไฟล์ ตรงหัวดิสก์ ที่นั่นการก๊อบไม่มีทางไปแตะได้ จึงเป็นคำตอบที่เชื่อได้จริงเพียงที่เดียว

CentOS 7สั่ง df หรือ mount แล้วไม่ขึ้นอะไรเลย

ไฟล์ /etc/mtab เป็นไฟล์ธรรมดาที่ว่างอยู่ ไม่ใช่ทางลัด เฟส 1 ตั้งใจเขียนแบบนั้นเพราะโหมด rescue ต้องการไฟล์จริง แล้วเฟส 2 จะเปลี่ยนกลับเป็นทางลัดให้ตอนจบ ถ้ายังเป็นไฟล์ว่างอยู่แปลว่าเฟส 2 ไม่จบ หรือใช้รุ่นเก่า หรือรันเฟส 1 ซ้ำด้วยรุ่นเก่าทับของที่เฟส 2 วางไว้ ตามข้อบน แก้ในตัว VM ได้เลย

ln -sf /proc/self/mounts /etc/mtab

รุ่น 6 ห้ามทำแบบนี้ ต้องเป็นไฟล์ธรรมดาเท่านั้น เพราะ rc.sysinit เขียนทับทุกครั้งที่บูต

CentOS 6โหมด rescue เด้ง Traceback ของ python แล้วขึ้น install exited abnormally

ถ้าบรรทัดล่างสุดเขียนว่า IOError: [Errno 22] Invalid argument และบรรทัดเหนือขึ้นไปมีคำว่า makeMtab อาการนี้คือไฟล์ /etc/mtab ในตัวที่ก๊อบมาเป็นทางลัดชี้เข้า /proc ซึ่ง CT ทุกตัวเป็นแบบนั้น เพราะ container ไม่มีตารางเมาท์ของตัวเอง พอโหมด rescue เขียนไฟล์นั้น มันไปเขียนลง /proc ของแผ่นกู้ระบบแทน แล้วตายทั้งโปรแกรม ยังไม่ทันได้หน้าจอพิมพ์คำสั่ง

ตัว c2v-prepare.sh รุ่นใหม่แก้ไฟล์นี้ให้แล้วตั้งแต่เฟส 1 ถ้าเจอแปลว่าใช้รุ่นเก่าสร้างมา แก้ได้ในที่เดิมไม่ต้องกลับไปที่ host กด Ctrl + C ให้มัน reboot แล้วพิมพ์ linux rescue ใหม่ คราวนี้ตอนถามให้เลือก Skip ไม่ใช่ Continue จะได้ # มาเลยโดยไม่ต้องผ่านขั้นที่พัง แล้วพิมพ์ตามนี้

mkdir -p /mnt/sysimage
mount /dev/vda1 /mnt/sysimage
rm -f /mnt/sysimage/etc/mtab
: > /mnt/sysimage/etc/mtab
chroot /mnt/sysimage
/root/c2v-inside.sh

สองบรรทัดกลางคือตัวแก้ ลบทางลัดทิ้งแล้วสร้างไฟล์เปล่าจริงๆ แทน CentOS 6 เขียนไฟล์นี้ใหม่ทุกครั้งที่บูตอยู่แล้ว แก้ครั้งเดียวจบถาวร ครั้งต่อไปเลือก Continue ได้ตามปกติ

ที่ต้องใช้ rm ก่อน เพราะถ้าเขียนทับเฉยๆ มันจะวิ่งตามทางลัดไปเขียนที่ /proc เหมือนเดิม

โหมด rescue บอกว่าหาระบบที่ติดตั้งไว้ไม่เจอ

แปลว่าเฟส 1 ไม่จบ ยังไม่ได้เขียน /etc/fstab ให้กลับไปรันเฟส 1 ใหม่จนขึ้นคำว่า phase 1 done

รัน c2v-inside.sh แล้วบอกว่า you are still in the rescue shell

ข้อความนี้เป็นของรุ่นเก่า รุ่นนี้ไม่บ่นแล้ว เพราะมันจัดการให้เองตั้งแต่อยู่นอก chroot ถ้ายังเจออยู่แปลว่าไฟล์ในเครื่องเป็นของเก่า ให้รันเฟส 1 ใหม่ มันวางตัวใหม่ให้ทุกรอบ แล้วดูเลขรุ่นในบรรทัดแรกว่าตรงกับที่ host บอกไหม

รันจากนอก chroot แล้วบอกว่า /mnt/sysimage has no /root/c2v-inside.sh in it

โหมด rescue ไม่ได้ mount disk ของ VM ให้ มักเป็นเพราะเลือก Read-Only หรือ Skip ให้ย้อนกลับไปเลือก Continue ใหม่ ถ้าเลือก Continue แล้วยังขึ้นแบบเดิม แปลว่าเฟส 1 ยังไม่จบ กลับไปดูที่ host ว่าขึ้นคำว่า phase 1 done หรือยัง

เปิด VM แล้วไอพีไม่ขึ้น

เข้าไปดูในตัว VM ว่าไฟล์ตั้งค่ายังอยู่ครบไหม

cat /etc/sysconfig/network-scripts/ifcfg-eth0
cat /etc/udev/rules.d/70-persistent-net.rules
ip link

ไฟล์ 70-persistent-net.rules ต้องว่างเปล่า ถ้ามีบรรทัดอยู่ให้ล้างแล้ว reboot

: > /etc/udev/rules.d/70-persistent-net.rules
reboot

ย้ายจริงแล้ว แต่ที่เก็บข้อมูลจากเครื่องอื่นไม่ขึ้น

เกือบทุกครั้งคือลืมข้อสามของขั้น 6 หลังทดสอบด้วยไอพีอีกตัวมา บรรทัดพวกนั้นยังถูกปิดอยู่ ดูในตัว VM

grep C2VTEST /etc/fstab

ถ้ามีบรรทัดขึ้นมา แปลว่าใช่ แก้ในตัว VM ได้เลยไม่ต้องดับ

sed -i 's@^#C2VTEST# @@' /etc/fstab
mount -a
df -h

เปิด VM ทดสอบไปแล้วทั้งที่ยังไม่ได้ตัดบริการ

ดับทันที อย่าเพิ่งเข้าไปแก้ในเครื่องเพราะบริการเปิดไปหมดแล้ว

$ qm stop 9100

แล้วไปดูสองอย่างที่แก้กลับไม่ได้ คือเมลที่ส่งออกไปแล้ว กับงานตามเวลาที่ยิงไปแล้ว เช็กจากฝั่งปลายทาง ไม่ใช่จากในเครื่องนี้ ส่วนตัว VM ให้เริ่มขั้น 5 ใหม่ตั้งแต่ข้อหนึ่ง ข้อมูลไม่เสียหาย

บูตแรกช้ามาก ขึ้นข้อความ relabel

ปกติ SELinux กำลังติดป้ายไฟล์ใหม่ทั้งเครื่อง เกิดครั้งเดียว ปล่อยให้มันทำจนจบ อย่าปิดเครื่องกลางคัน

โฟลเดอร์ที่เคยเป็น mountpoint กลายเป็นโฟลเดอร์ว่าง

เป็นตามที่เตือนไว้ตอนเฟส 1 ข้อมูลก้อนนั้นไม่ถูกก๊อบมาตั้งแต่แรก ต้องย้ายแยกเอง

อยากเลิกกลางคัน

ลบ VM ทิ้งได้เลย CT เก่าไม่เคยถูกแตะ

$ qm stop 9100
