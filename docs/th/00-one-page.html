แผ่นเดียวจบ ระบบคืออะไร คำสั่งทั้งหมด ก๊อปทุกคืน storage ตาย storage กลับมา เพิ่ม CT เครื่องดับกลางก๊อป แก้ไฟล์ไหน เมล พังบ่อย

ketsync — แผ่นเดียวจบ

ระบบทำอะไร มีคำสั่งอะไร และแต่ละสถานการณ์พิมพ์อะไรบ้าง — อ่านจบใน 5 นาที

หน้านี้คือทางลัด ถ้าอยากได้รายละเอียดเต็มไปที่ สารบัญ
1

ระบบนี้ทำอะไร

ก๊อปดิสก์ของ CT ทุกตัวไปเก็บไว้อีกเครื่องทุก 15 นาที และถ้าเครื่องเก็บดิสก์ตาย ก็เอาสำเนานั้นไปรันบนเครื่อง compute ให้ลูกค้าใช้งานต่อได้

เครื่องตัวอย่างหน้าที่
storage10.100.1.17เก็บดิสก์จริงของทุก CT + เป็นเครื่องที่สั่งงาน (master)
backup10.100.1.9เก็บสำเนา + เป็นเครื่องที่สั่งงานตอน storage ตาย
compute10.100.1.32/.33เครื่องที่รัน CT จริงๆ
เลขคืออะไร
300CT ตัวจริงของลูกค้า — เลขเดียวที่คนพิมพ์
8300สำเนาบนเครื่อง backup (หยุดอยู่เสมอ) = 300 + 8000
9300ตัวชั่วคราวตอนภัยพิบัติ รันบน compute = 300 + 9000
vmbr99bridge ตัน ไม่ต่อสายจริง — ที่พักของสำเนาและตัวที่ถูกตัดเน็ต

กฎเหล็ก 2 ข้อ ระบบนี้ไม่เคยสั่ง start CT เอง (พิมพ์เองเสมอ) และไม่เคยเดาค่าที่ไม่ได้กรอก

2

คำสั่งทั้งหมด

ทุกคำสั่งขึ้นต้นด้วย ./ketsync ในโฟลเดอร์ /root/ketsync ตัวที่เขียนข้อมูลจะถามยืนยันก่อนเสมอ เติม --dry-run เพื่อดูว่าจะทำอะไรโดยไม่ทำจริง

คำสั่งทำอะไรพิมพ์ที่เครื่อง
replicaก๊อป CT จริง → สำเนา 8xxx (cron ทำเองทุก 15 นาที)storage
distributeเอาสำเนาไปรันเป็น 9xxx บน compute — ใช้ตอน storage ตายbackup
recallดึงข้อมูลที่ 9xxx ทำงานไว้ กลับเข้าสำเนาbackup
recoverทางกลับทั้งหมดในคำสั่งเดียว หลัง storage กลับมาstorage
failbackเขียนสำเนากลับเข้าดิสก์จริง (recover เรียกให้อยู่แล้ว)storage
migrateย้าย CT จากเครื่องเก่านอกฟลีตเข้ามาstorage
isolate / restoreตัด CT ออกจากเน็ต / เอากลับคืนstorage หรือ backup
evacuateปิด storage ที่ตายทั้ง node แล้วสั่งหยุด CT บนนั้นbackup
cleanupเก็บ 9xxx เข้าที่หลังจบงาน (--destroy = ลบทิ้ง)storage
doctorตรวจทุกอย่าง อ่านอย่างเดียว — พิมพ์ได้ทุกเมื่อทุกเครื่อง
statusรอบล่าสุดของแต่ละ CTทุกเครื่อง
watchเมลเตือนเมื่อมีอะไรเปลี่ยน (cron ทำเอง)ทุกเครื่อง
syncส่งตาราง (fleet/inventory/nodes) ไปเครื่องอื่นstorage
mail-setupตั้ง postfix ให้ส่งเมลออกได้storage + backup
roleดู/เปลี่ยนว่าเครื่องนี้เป็น master หรือ slaveทุกเครื่อง

ไม่แน่ใจว่าคำสั่งไหนรับ flag อะไร พิมพ์ --help ต่อท้ายได้เลย ไม่ถามอะไรและไม่รันอะไรทั้งนั้น

3

สถานการณ์ 1 — ก๊อปทุกคืน (replica)

งานประจำที่ cron ทำเองอยู่แล้ว จะมายุ่งก็ต่อเมื่อเพิ่ม CT ใหม่หรืออยากสั่งรอบพิเศษ

ต้องแก้ไฟล์: inventory/inventory-replica.tsv — CT ที่ไม่มีแถวในนี้ จะไม่ถูกก๊อป และไม่มีใครเตือน

  1. เติมแถว — เลข CT + pool ปลายทาง (replica-hdd ช้าแต่เยอะ / replica-ssd เร็ว)
    inventory/inventory-replica.tsv
    130	replica-hdd
  2. ส่งตารางให้เครื่องอื่นรู้ด้วย
    ./ketsync sync
    ./ketsync sync
  3. สั่งรอบแรกด้วยมือ แล้วดูว่าจบสวย
    ./ketsync replica --ctid 130
    ./ketsync replica --ctid 130
./ketsync status

    ต้องจบด้วย failed=0 — หลังจากนี้ cron ดูแลต่อเอง

สองอย่างที่สำเนาให้กลับมา ทุกรอบที่เขียวจะทิ้ง snapshot ลงวันที่ไว้บนเครื่อง backup เก็บ 7 วัน ไฟล์ที่ถูกลบไปเมื่อเช้าจึงยังอยู่ในของเมื่อวาน — ลำพัง replica ไม่ใช่ backup ตรงนี้แหละที่ทำให้มันเป็น และสำเนาย้าย pool ได้ด้วยคำสั่งเดียว ไม่ต้องไล่ทำมือทีละขั้นอีกแล้ว

ดึงไฟล์เมื่อวานกลับมา · ย้ายสำเนาไปอีก pool
# on the backup node: which days exist, then take a file out of one
ls /replica-hdd/ct/subvol-8130-disk-0/.zfs/snapshot/
cp /replica-hdd/ct/subvol-8130-disk-0/.zfs/snapshot/ketsync-2026-08-18/etc/nginx/nginx.conf /tmp/

# change the row's dest column first, sync, then move it (dry-run reads the plan)
./ketsync replica --ctid 130 --move-dest --dry-run
./ketsync replica --ctid 130 --move-dest
4

สถานการณ์ 2 — storage ตาย (distribute)

CT ทุกตัวค้างเพราะดิสก์หาย เป้าหมายคือเอาสำเนาขึ้นมารันบน compute ให้เร็วที่สุด พิมพ์ที่เครื่อง backup เพราะเครื่อง storage ไม่อยู่แล้ว

ต้องมีในไฟล์: conf/fleet.tsv ครบทุก CT — 4 ช่อง ct / home / dr / dst ถ้าแถวไหนขาด CT ตัวนั้นจะถูกปฏิเสธ (ไม่เดาให้) ที่พลาดบ่อยคือช่อง dst ต้องสะกดตรงกับ pvesm status บนเครื่องปลายทางจริงๆ

  1. ดูแผนก่อน ไม่เขียนอะไรทั้งนั้น
    ./ketsync distribute --all --dry-run
    ./ketsync distribute --all --dry-run
  2. ของจริง — มันจะปิด storage ที่ตาย ตัด CT เก่าออกจากเน็ต แล้วค่อยวางสำเนา
    ./ketsync distribute --all
    ./ketsync distribute --all

    ระหว่างโอนจะเห็นแถบ progress เหมือน replica และจบด้วยบรรทัด stats: ต่อ CT

  3. สั่ง start เอง ทีละตัว (ระบบไม่ทำให้ — ตรงนี้มีลูกค้าอยู่ปลายทาง)
    ssh root@compute pct start 9xxx
    # the log prints the exact line for every CT
ssh root@10.100.1.32 pct config 9110
ssh root@10.100.1.32 pct start 9110

ถ้ารันไปแล้วรอบหนึ่ง แล้วต้องรันซ้ำ ใช้ --no-prepare ได้ ไม่ต้องปิด storage ซ้ำ

5

สถานการณ์ 3 — storage กลับมา (recover)

ทางกลับ ทำทีละขั้นได้แต่ยาว recover คือทั้งเช็คลิสต์ในคำสั่งเดียว และรันซ้ำได้ตลอด (ขั้นไหนทำแล้วมันข้ามให้) พิมพ์ที่เครื่อง storage

ต้องมีในไฟล์: conf/fleet.tsv อีกครั้ง — คราวนี้ใช้ช่อง home เพื่อรู้ว่าจะไป fsck ดิสก์ของ CT นั้นที่เครื่องไหน CT ที่ไม่มีแถวจะขึ้น no row in fleet.tsv แล้วข้ามไป

  1. ก่อนอื่น ที่เครื่อง backup: ดึงข้อมูลที่ 9xxx ทำงานไว้กลับเข้าสำเนาก่อน (ต้องหยุด 9xxx ก่อน)
    ./ketsync recall --all --final
    # on the BACKUP node - stop each 9xxx first, that is the cutover
ssh root@10.100.1.32 pct shutdown 9110
./ketsync recall --all --final
  2. ดูว่าเหลืออะไรบ้าง (อ่านอย่างเดียว)
    ./ketsync recover --list
    ./ketsync recover --list
  3. ของจริง — เปิด storage คืน, fsck ดิสก์ที่พัง, เขียนสำเนากลับ, คืนเน็ต, เก็บ 9xxx
    ./ketsync recover --all
    ./ketsync recover --all
# or one container at a time
./ketsync recover --ctid 137
  4. สั่ง start CT จริงเอง แล้วเช็คว่าลูกค้าใช้ได้
    ssh root@compute pct start 110
    ssh root@10.100.1.32 pct start 110
  5. พอใจแล้วค่อยเก็บกวาดครั้งสุดท้าย — ลบตัวชั่วคราว แล้วปล่อยให้ replica เดินต่อ
    ./ketsync recover --all --destroy
    ./ketsync recover --all --destroy

    ตราบใดที่ยังไม่ --destroy ระบบจะหยุดก๊อปทุกคืนไว้ตั้งใจ เพื่อกันเขียนทับสำเนาที่ยังมีค่า

สถานการณ์ 4 — เพิ่ม CT ใหม่ให้ลูกค้า

แก้ 2 ไฟล์ แล้ว sync จบ ถ้าลืมไฟล์ใดไฟล์หนึ่ง มันจะเงียบจนถึงวันที่ต้องใช้จริง

ไฟล์ใส่อะไรถ้าลืม
inventory/inventory-replica.tsv130  replica-hddไม่มีสำเนาเลย
conf/fleet.tsv130  home  dr  dstวันภัยพิบัติกู้ตัวนี้ไม่ได้
./ketsync sync && ./ketsync doctor
./ketsync sync
./ketsync doctor

สถานการณ์ 5 — เครื่อง storage ดับกลางรอบก๊อป

ไฟดับหรือเครื่องรีบูตขณะ replica กำลังเขียนสำเนาอยู่พอดี ตัวข้อมูลไม่หายถาวร — รอบเขียวรอบแรกหลังเครื่องกลับมาจะซ่อมสำเนาที่ค้างครึ่งให้ครบเอง แต่ lock กันชน 2 ตัวที่ระบบฝากไว้บนเครื่อง backup จะค้างไว้โดยตั้งใจ (ระบบไม่มีวันเดาเองว่าเครื่องตายจริงหรือแค่เน็ตขาด) CT ตัวนั้นเลยถูก skip ทุกรอบ จนกว่าจะมีคนปลด — 2 คำสั่ง พิมพ์ที่เครื่อง storage

ทุกคำสั่งข้างล่างรันซ้ำได้ และรันเปล่าก็ได้: ถ้ามี lock ค้างมันปลดให้ ถ้าไม่มีมันก็เงียบไปเฉยๆ เหมือนไม่ได้ทำอะไร ไม่แน่ใจว่าโดนตัวไหนก็ไล่ทำทั้งชุดได้เลย ไม่มีทางพัง

  1. ดูก่อนว่า CT ไหนโดน — ตัวที่ถูก skip จะบอกชื่อ lock ใน log เอง
    grep GUARD · ./ketsync status
    grep -h 'GUARD R14\|GUARD R15' logs/replica-*-$(date +%F).log | tail
./ketsync status
  2. ขั้นเดียวที่ต้องคิด: ยืนยันว่าตอนนี้ไม่มี replica หรือ failback รันอยู่จริง
    pgrep -af 'ct-replica|ct-failback'
    pgrep -af 'ct-replica|ct-failback' || echo idle

    ถ้ามีตัวรันอยู่ = lock นั้นของจริง ไม่ได้ค้าง — ปล่อยให้รอบนั้นจบก่อนแล้วไม่ต้องทำอะไรเลย

  3. ปลด lock ตัวที่ 1 — ไฟล์บนเครื่อง backup (rm -f = ไม่มีไฟล์ก็เงียบ ไม่ error)
    ssh root@10.100.1.9 rm -f /run/ketsync-ct-8130.lock
    # the COPY id, not the production id (CT 130 -> copy 8130)
ssh root@10.100.1.9 'rm -f /run/ketsync-ct-8130.lock'
  4. ปลด lock ตัวที่ 2 — ใน config ของสำเนา แต่ดูก่อนปลดหนึ่งครั้ง: ถ้าขึ้น lock: backup คือ PBS กำลัง backup ตัวนั้นอยู่จริง ห้ามปลด รอ job จบแล้วมันหายเอง ถ้าขึ้น lock: disk หรือไม่ขึ้นอะไรเลย ปลดได้ (ตัวที่ไม่ได้ lock สั่ง unlock ก็ไม่ทำอะไร)
    pct config → pct unlock
    ssh root@10.100.1.9 'pct config 8130 | grep ^lock || echo no-lock'
ssh root@10.100.1.9 'pct unlock 8130'
  5. จบแล้ว — รอ cron รอบถัดไป หรือสั่งเองเลยก็ได้ รอบนี้จะเทียบใหม่ทั้งก้อนและซ่อมส่วนที่ค้างให้ครบ
    ./ketsync replica --ctid 130
    ./ketsync replica --ctid 130

ถ้าเครื่อง storage ตายถาวร (ไม่ใช่แค่ดับแล้วฟื้น): ไม่ต้องปลดอะไรทั้งนั้น ข้ามไปสถานการณ์ 2 ได้เลย — แต่ก่อน distribute ให้ถอยสำเนาที่ค้างครึ่ง กลับไป snapshot รายวันตัวล่าสุดก่อน จะได้ไม่แจก rootfs ครึ่งๆ ออกไป (สำเนาแต่ละตัวเป็น dataset แยกของใครของมัน rollback ไม่กระทบ CT อื่น)

zfs rollback @ketsync-<last day>
# on the backup node: list the days this copy has, then roll back to the newest
zfs list -t snapshot -o name -s creation replica-hdd/ct/subvol-8130-disk-0 | tail -3
zfs rollback replica-hdd/ct/subvol-8130-disk-0@ketsync-2026-08-27

เมลที่จะได้

NODEเครื่องเดียวมีปัญหา ssh ไม่ติด หรือ storage ถูกปิดค้าง
daily digestรายงาน doctor ตอนเช้า กวาดตาดูหัวข้อที่ไม่ใช่ ok

พังบ่อยๆ

อาการทำอะไร
cron ไม่รันเลย เงียบสนิทไฟล์ใน /etc/cron.d/ ต้องมีช่อง root เป็นช่องที่ 6 — doctor จับให้
replica ไม่ทำงานตั้งแต่วันที่ตั้ง cronเอา -y ออกจากบรรทัดที่เรียก engine ตรงๆ — engine ไม่รู้จัก flag นี้
no row in fleet.tsvเติมแถวนั้นแล้ว ./ketsync sync
สั่งอะไรก็ขึ้น refusedอ่านบรรทัดถัดไป มันบอกเสมอว่าขาดอะไรและต้องพิมพ์อะไร
replica ไม่เดินหลังภัยพิบัติยังมีไฟล์ engines/PAUSE ค้าง — จบงานให้ครบด้วย recover --all --destroy
CT ตัวหนึ่งขึ้น GUARD R15 ทุกรอบPBS กำลัง backup สำเนาตัวนั้นอยู่ ไม่ต้องทำอะไร หายเองเมื่องานจบ
CT เดิมถูก skip ทุกรอบ ขึ้น GUARD R14 หรือ R15: lock: disk หลังไฟดับ/รีบูตlock ค้างจากรอบที่ตายกลางทาง — ไปสถานการณ์ 5 ปลด 2 คำสั่ง
replica ขึ้น GUARD R16 ทุกรอบรอบ migrate ล่าสุดของตัวนั้นจบไม่สวย (interrupted/failed) — สั่ง ./ketsync migrate --ctid <id> ให้จบ ok หนึ่งรอบ แล้ว replica เดินต่อเอง
แก้ pool ในใบงานแล้วขึ้น GUARD R8./ketsync replica --ctid <id> --move-dest — ก๊อป ตรวจ แล้วค่อยลบของเก่า
