ketsync เพิ่งมาใหม่ คู่มือ 5 เล่ม ระบบนี้คืออะไร หาเรื่องที่ต้องการ

คู่มือทั้งชุด

เริ่มที่หน้านี้ถ้าไม่รู้ว่าจะเปิดเล่มไหน — เลือกจากสิ่งที่กำลังจะทำ ไม่ใช่จากชื่อไฟล์

ทุกเล่มเป็นไฟล์ HTML ธรรมดา เปิดจากเครื่องไหนก็ได้ ไม่ต้องต่อเน็ต
1

เพิ่งมาใหม่ อ่านตามลำดับนี้

  1. อ่าน start-here.html ให้จบ ประมาณ 20 นาที จบแล้วจะรู้ว่าระบบมีกี่ชั้น ไฟล์ไหนคืออะไร ใครแก้ได้ และคำสั่งประจำวันมีอะไรบ้าง
  2. ถ้าต้องติดตั้งเอง ต่อด้วย infrastructure-setup.html มันพาไล่ตั้งแต่เครื่องเปล่า ทุกขั้นมีวิธีเช็กว่าทำถูกแล้ว
  3. อ่าน disaster-recovery.html ตอนที่ยังไม่มีอะไรเกิด นี่คือเล่มที่ห้ามอ่านครั้งแรกตอนตี 3 หัวข้อ 0 กับ 1 อ่าน 10 นาทีก็พอ

ถ้าอยากรู้ว่า “ทำไมถึงออกแบบแบบนี้” มากกว่า “ต้องพิมพ์อะไร” ให้อ่าน docs/decisions.md ทุกด่านในระบบมีเหตุผลอยู่ในนั้น และหลายข้อมาจากเรื่องที่เคยพลาดมาแล้วจริงๆ

คู่มือ 5 เล่ม ใช้ตอนไหน

เล่มเปิดตอนไหนยาวแค่ไหน
start-here.html วันแรกที่มาเจอระบบนี้ และทุกครั้งที่ลืมว่าคำสั่งประจำวันมีอะไร อ่านรวดเดียวได้
infrastructure-setup.html ตั้งเครื่องใหม่ตั้งแต่ศูนย์ หรือเพิ่มเครื่อง compute เข้าฟลีต ทำตามทีละขั้น
disaster-recovery.html เครื่อง storage ตาย — และควรอ่านล่วงหน้าก่อนวันนั้น 6 ขั้น อ่านล่วงหน้า 10 นาที
start-here.html วันแรกที่มาเจอระบบนี้ และทุกครั้งที่ลืมว่าคำสั่งประจำวันมีอะไร อ่านรวดเดียวได้
infrastructure-setup.html ตั้งเครื่องใหม่ตั้งแต่ศูนย์ หรือเพิ่มเครื่อง compute เข้าฟลีต ทำตามทีละขั้น
how-it-works.html อะไรต่อกับอะไร ทั้ง replica ตอนปกติและหกขั้นตอนกู้ภัย บนหน้าเดียว พร้อมตารางว่าขั้นไหนเครื่องทำ ขั้นไหนคนต้องกด อ่านตอนว่าง ไม่ใช่ตอนไฟไหม้
c2v-el.html แปลง CT เป็น VM สำหรับ guest ตระกูล EL (Rocky, Alma, CentOS) เปิดเฉพาะตอนใช้
c2v-debian.html อันเดียวกัน สำหรับ guest ตระกูล Debian และ Ubuntu เปิดเฉพาะตอนใช้

สองเล่มสุดท้ายเป็นงานคนละเรื่องกับที่เหลือ มันไม่เกี่ยวกับ DR หรือการก๊อปสำเนา — เป็นการแปลง container เป็น virtual machine ซึ่งทำนานๆ ครั้ง ตอนที่ guest ตัวนั้น ต้องการ kernel ของตัวเอง เก็บไว้ในชุดเดียวกันเพราะมันเป็นงานบนฟลีตเดียวกัน และใช้เครื่องมือเดียวกันหลายตัว

3

ระบบนี้คืออะไร ใน 1 หน้า

มีสองชั้น ketsync ตัดสินใจ ว่าใครทำอะไรที่ไหน และ tp ย้ายข้อมูล ทั้งหมดอยู่ใน repo เดียว clone เดียว และมีคำสั่งเดียวอยู่ข้างหน้า

คำสั่งทำอะไรสั่งจากเครื่องไหน
ketsync replicaไฟล์ดิสก์ตัวจริง → สำเนาที่ปิดอยู่บนเครื่อง backupstorage
ketsync distributeสำเนา → ดิสก์ในตัวเครื่อง compute (9xxx)ที่ไหนก็ได้
ketsync recall9xxx → กลับเข้าสำเนาบนเครื่อง backupที่ไหนก็ได้
ketsync failbackสำเนา → กลับเข้าไฟล์ดิสก์ตัวจริงstorage
ketsync migrateCT จาก node เก่า → ไฟล์ดิสก์บนเครื่อง storagestorage
ketsync syncส่งตารางไปทุกเครื่องที่มี ketsyncmaster
ketsync doctorตรวจทุกอย่างที่ไม่มีใครจำได้ว่าต้องตรวจที่ไหนก็ได้
ketsync statusรอบล่าสุดของทุก CTที่ไหนก็ได้

เลข 3 ชุด ที่ไม่มีใครต้องพิมพ์เอง

เลขคืออะไรอยู่ที่ไหน
300ตัวจริงไฟล์ดิสก์บนเครื่อง storage ผ่าน NFS
8300สำเนา DR ปิดอยู่เสมอเครื่อง backup
9300ตัวชั่วคราวตอนฉุกเฉินดิสก์ในตัวเครื่อง compute

ทุกคำสั่งรับเลขตัวจริงตัวเดียว ที่เหลือมันคิดเองจากตัวเลขสองตัวใน ctrep.conf เห็นเลข 9 นำหน้าใน pct list เมื่อไหร่ ให้รู้ทันทีว่านั่นคือของชั่วคราว

ไม่มีคำสั่งไหนในชุดนี้เปิดหรือปิด container ให้ ทุกตัวย้ายข้อมูล เขียน config แล้วพิมพ์คำสั่ง pct start ออกมาให้คนกดเอง การเอาบริการของลูกค้ากลับมาเป็นการตัดสินใจ ไม่ใช่ขั้นตอน

หาเรื่องที่ต้องการเร็วๆ

อยากทำเปิดเล่มไหน
เพิ่ม CT เข้าไปในรายการก๊อปstart-here.html ข้อ 6
ตั้ง sync ระหว่าง master กับ slavestart-here.html ข้อ 4
เจอคำว่า FORKEDstart-here.html ข้อ 4
ตั้งเครื่อง backup ใหม่infrastructure-setup.html
เพิ่มเครื่อง compute เข้าฟลีตinfrastructure-setup.html
เครื่อง storage ตายอยู่ตอนนี้disaster-recovery.html ข้อ 2
เอาข้อมูลกลับหลัง storage ฟื้นdisaster-recovery.html ข้อ 5-6
เจอ GUARD อะไรสักอย่างแล้วไม่เข้าใจstart-here.html ข้อ 7
แปลง CT เป็น VMc2v-el.html หรือ c2v-debian.html
อยากรู้ว่าทำไมถึงออกแบบแบบนี้docs/decisions.md
