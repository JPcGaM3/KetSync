แปลง CT เป็น VM — Debian กับ Ubuntu

ทางนี้สั้นกว่าทางของ CentOS มาก ไม่ต้องใช้แผ่นติดตั้ง ไม่ต้องเข้าโหมด rescue และไม่ต้องพิมพ์อะไรในหน้าจอ VM เลย ทั้งสองเฟสพิมพ์บน node ใหม่เครื่องเดียว

ก่อนเริ่ม

เอกสารนี้เป็นลำดับคำสั่งล้วน ตัวอย่างทั้งหมดใช้ค่าสมมติชุดนี้ ให้เปลี่ยนเป็นของจริงก่อนพิมพ์

ค่าตัวอย่างในเอกสารนี้คืออะไร
--old-node10.100.1.11เครื่องเก่าที่ CT อยู่ตอนนี้
--old-ctid140เลข CT บนเครื่องเก่า
--vmid9140เลข VM ที่จะสร้างใหม่ ต้องยังว่าง
--storagetank-hdd-nasที่เก็บ disk ของ VM
--isoไม่ต้องใส่ทางนี้ไม่ใช้แผ่นเลย ใส่มาก็จะขึ้น WARN แล้วโดนตัดทิ้ง

storage ต้องเป็นแบบไฟล์ ไม่ใช่ LVM หรือ ZFS เพราะทั้งสองเฟสต้อง mount ไฟล์ image ตรงๆ ถ้าใส่ storage แบบ block โปรแกรมจะไม่ทำงานและบอกให้เปลี่ยน ทำเสร็จแล้วค่อย qm move-disk ไป LVM หรือ ZFS ทีหลังได้

เช็กก่อนว่า CT ตัวนี้เป็นตระกูลอะไร

ถามตัว CT เอง อย่าเดาจากชื่อเครื่องและอย่าเชื่อบรรทัด ostype: ในไฟล์ตั้งค่า เพราะนั่นเป็นป้ายที่คนตั้งไว้ตอนสร้าง ไม่ใช่สิ่งที่อยู่ข้างในจริงๆ พิมพ์บนเครื่องเก่า

$ pct exec 140 -- cat /etc/os-release

สองบรรทัดที่ต้องดูคือ ID= กับ ID_LIKE= ถ้าได้ ubuntu debian devuan หรือ raspbian คือมาถูกที่แล้ว

NAME="Ubuntu" VERSION="20.04.6 LTS (Focal Fossa)" ID=ubuntu ID_LIKE=debian PRETTY_NAME="Ubuntu 20.04.6 LTS" VERSION_ID="20.04" VERSION_CODENAME=focal

ถ้าอ่านแล้วได้ centos, rhel, rocky, almalinux หรืออะไรก็ตามในตระกูลนั้น ให้ปิดหน้านี้ ไปใช้ เอกสารของ CentOS แทน คนละทางกันตั้งแต่เฟส 2 และสลับกันไม่ได้ ถ้าเครื่องเก่าเก่าถึงขั้นไม่มีไฟล์ /etc/os-release เลย นั่นคือ CentOS 6 แน่นอน เพราะไฟล์นี้เพิ่งมีตอน CentOS 7

ไม่ต้องหาแผ่นติดตั้ง ไม่ต้องโหลดอะไรมาก่อน เฟส 2 ของทางนี้ใช้ apt ของตัว guest เอง ยิงไปที่ repository ที่ตัว guest ตั้งไว้อยู่แล้ว ข้อแม้ข้อเดียวคือ node ที่รันต้องออกไปหา repository นั้นได้ ซึ่งถ้า Ubuntu 20.04 ตัวนั้นเคยรัน apt-get update ได้ก็คือได้

งานนี้มี 2 เฟส แต่ไม่ต้องย้ายที่นั่ง

CT ไม่มีของอยู่ 3 อย่างที่ VM ต้องมี คือ kernel, ตัว boot loader และ initramfs ที่รู้จัก virtio เฟสแรกก๊อบข้อมูล เฟสสองใส่ 3 อย่างนั้น

ทำอะไรพิมพ์ที่ไหนใช้เวลา
c2v-prepare.shสร้าง VM เปล่า แบ่ง partition ก๊อบไฟล์ทั้งหมดจาก CTnode ใหม่ตามขนาดข้อมูล
c2v-inside-deb.shลง kernel + grub + initramfs ทำให้ boot ได้node ใหม่ เครื่องเดียวกัน2 ถึง 5 นาที

ทำไมทางนี้ถึงไม่ต้องเข้าไปทำในตัว VM

ของฝั่ง CentOS ต้องเข้าไปทำในโหมด rescue ของแผ่นตัวเอง ด้วยเหตุผลสองข้อ และทั้งสองข้อหายไปหมดเมื่อ guest เป็น Debian หรือ Ubuntu

เหตุผลของฝั่ง CentOSทำไมไม่เป็นปัญหาทางนี้
CentOS 6 มี rpm dracut grub ที่เป็นโปรแกรมของ glibc 2.12 ซึ่ง segfault ทันทีที่ chroot เข้าไปจาก host ที่ kernel ใหม่Ubuntu 20.04 เป็น glibc 2.31 chroot จาก host แล้วรันได้ปกติทุกคำสั่ง
CentOS 7 chroot ได้ แต่ host ไม่มี rpm กับ yum จะเอาที่ไหนลง kernel ให้ และ grub2 บน host เป็นของ Debianตัว PVE node ก็คือ Debian apt dpkg grub-pc initramfs-tools บน host จึงไม่ใช่ของยี่ห้ออื่น มันคือเครื่องมือของ guest เอง

เฟส 2 ของทางนี้จึงเป็นแค่ chroot ธรรมดาที่รันบน node ผลพลอยได้คือเร็วกว่า รันซ้ำได้ และที่สำคัญที่สุดคือทุกบรรทัดพิมพ์บน shell ของ node ซึ่งวางข้อความได้ ต่างจากหน้าจอ console ของ VM ที่วางไม่ได้

แพ็กเกจยังมาจาก repository ของ guest เอง ไม่ได้มาจาก host ที่ chroot เข้าไปแล้ว apt ที่รันคือตัวที่อยู่ในดิสก์ของ guest อ่าน sources.list ของ guest เพราะฉะนั้น Ubuntu 20.04 ก็ยังได้ kernel ของ Ubuntu 20.04 host ให้มาแค่ kernel ที่ตัวเองกำลังรันอยู่เท่านั้น

CT ตัวเก่าไม่ถูกแตะต้องเลย ทั้งสองเฟสเป็นการอ่านอย่างเดียวฝั่ง CT ระหว่างทำ CT เก่ายังรันตามปกติ และตัวโปรแกรมไม่เคยสั่งเปิดหรือปิดอะไรเอง

เฟส 1 — ก๊อบข้อมูล

ลองเปล่าก่อนหนึ่งรอบ ยังไม่มีอะไรถูกสร้าง สังเกตว่าไม่มี --iso

$ cd ~/ct-migrate
$ ./tools/c2v-prepare.sh \
    --old-node 10.100.1.11 \
    --old-ctid 140 \
    --vmid 9140 \
    --storage tank-hdd-nas \
    --dry-run

ถ้าไม่มี ERROR ให้ถอด --dry-run ออกแล้วรันจริง เติม --bwlimit 500000 ถ้าไม่อยากให้กิน bandwidth หมด

$ ./tools/c2v-prepare.sh \
    --old-node 10.100.1.11 \
    --old-ctid 140 \
    --vmid 9140 \
    --storage tank-hdd-nas \
    --bwlimit 500000

จบแล้วต้องเห็นบรรทัดพวกนี้ สามบรรทัดบนสุดคือคำตอบว่ามันอ่าน CT ตัวนี้ออกว่าเป็นอะไร

บรรทัด guest family คือสิ่งที่ต้องอ่านทุกครั้ง ถ้าคำในวงเล็บเป็นอย่างอื่นที่ไม่ใช่ from the CT itself แปลว่ามันถาม CT ไม่ได้และไปเดาจากป้าย ostype: แทน ซึ่งอาจถูกก็ได้แต่ไม่มีอะไรรับประกัน

ถ้าขึ้น WARN ว่าอ่านไฟล์ของ guest ไม่ได้ มักเป็นเพราะ CT ถูกสั่งดับไปแล้ว หรือ ssh ไปเครื่องเก่าไม่ผ่าน ให้ใส่ --family debian ต่อท้ายคำสั่งเพื่อบอกมันตรงๆ ค่านี้ชนะทุกอย่างที่มันอ่านได้เอง

ป้ายชื่อ partition ทางนี้คือ debroot

เป็นแค่ชื่อ ไม่มีอะไรในโปรแกรมอ่านตระกูลจากชื่อนี้ มันคือชื่อที่ทั้งสองเฟสต้องเรียกตรงกันเท่านั้น เฟส 1 ตั้งชื่อตอน format เฟส 2 อ่านชื่อนี้ไปเทียบว่ากำลังจับดิสก์ถูกก้อนอยู่ไหม ถ้า image เคยถูกสร้างไว้ตั้งแต่ก่อนที่จะมีค่าตั้งต้นแยกตามตระกูล มันจะยังชื่อ c7root อยู่ ก็ให้ใส่ --label c7root ต่อท้ายทั้งสองเฟส ถ้าลืม โปรแกรมจะหยุดแล้วบอกชื่อที่ถูกให้เอง ไม่ format ทับ

ถ้าขึ้น WARN เรื่อง mountpoint แปลว่า CT ตัวนี้มี disk ก้อนที่สองต่ออยู่ ข้อมูลในนั้นไม่ถูกก๊อบ จะกลายเป็นโฟลเดอร์ว่างใน VM ต้องย้ายเองทีหลัง หรือต่อเป็น disk ลูกที่สองให้ VM

รันซ้ำกี่รอบก็ได้ รอบหลังจะก๊อบเฉพาะส่วนที่เปลี่ยน ข้อแม้เดียวคือ VM ต้องหยุดอยู่ ถ้า VM รันอยู่โปรแกรมจะไม่ยอมทำและบอกให้ไปสั่งหยุดก่อน

cpu กับ ram ไม่ต้องใส่เอง

สองค่านี้อ่านมาจาก pct config ของ CT ตัวนั้นให้เลย ถ้าอยากได้ไม่เท่าเดิมค่อยใส่ --memory หรือ --cores ทับ ใส่แล้วมันจะบอกว่า forced by ให้เห็นชัดๆ ว่าเลขนี้มาจากมือเรา

เพดานล่างของ ram ทางนี้คือ 512M ไม่ใช่ 1024M เหมือนฝั่ง CentOS เพราะสองทางเสียแรงคนละที่ ฝั่งนั้นเฟส 2 รัน yum กับ dracut อยู่ในตัว guest เอง ram ที่ container พอใจจึงไม่พอ ส่วนทางนี้เฟส 2 รันบน node ใช้ ram ของ node ที่เหลือให้ต้องเผื่อคือ boot แรกเท่านั้น ตรงจังหวะที่ initramfs ถูกแตกลง RAM ก่อนที่ / จะถูก mount ซึ่งเป็นงานที่ container ไม่เคยต้องทำ ถ้ายืนยันว่าจะเอาน้อยกว่านั้นจริงๆ ใส่ --memory ทับได้ มันไม่ดันซ้ำ

ชื่อสะพานของสองเครื่องไม่เหมือนกัน

vmbr1 ของเครื่องเก่ากับ vmbr1 ของเครื่องใหม่ เป็นแค่ชื่อที่เขียนเหมือนกัน ไม่ได้แปลว่าเป็นวงเดียวกัน บอกให้มันรู้ด้วยไฟล์ bridgemap.tsv วางไว้ที่โฟลเดอร์เดียวกับตัวโปรแกรม ก๊อบจาก bridgemap.tsv.example มาแก้ สี่ช่องต่อบรรทัด คั่นด้วย tab หรือเว้นวรรคก็ได้

เฟส 2 — ทำให้ boot ได้

อยู่ที่เดิม ไม่ต้องเปิด VM ไม่ต้องเปิดหน้าจอ console คำสั่งเดียวจบ

$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas --dry-run

ถ้าไม่มี ERROR ก็ถอด --dry-run ออก

$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas

VM ต้องหยุดสนิทก่อน ถ้ามันรันอยู่ โปรแกรมจะไม่ทำและบอกให้ไปสั่ง qm stop ก่อน เหตุผลไม่ใช่ความเรียบร้อย แต่เป็นเพราะ qemu เปิดไฟล์ image นั้นค้างไว้พร้อม cache ของตัวเอง ถ้า mount ซ้อนเข้าไปตอนนั้น kernel จะเห็นระบบไฟล์เดียวกันคนละมุมมองโดยไม่มีใครคุยกัน อาการปลายทางไม่ใช่ error แต่เป็น ext4 ที่พัง

ระหว่างทางมันจะพิมพ์ประมาณนี้ บรรทัดที่ต้องอ่านคือบรรทัดที่ทำสีไว้ ทั้งห้าบรรทัดนั้นคือด่านที่กันไม่ให้ได้ VM ที่บูตไม่ขึ้น

เลขในวงเล็บเหลี่ยมบรรทัดแรกคือรุ่นของ script เวลาไปเจอหัวข้อในส่วนเจอปัญหาที่บอกว่า "รุ่นนี้แก้แล้ว" ให้ดูเลขนี้ก่อนว่าตรงกับตัวที่รันอยู่จริงไหม ก๊อบไปวางบน node แล้วลืมทับตัวเก่าเป็นเรื่องที่เกิดง่ายที่สุด และอาการที่ได้จะเหมือนกับตอนที่ยังไม่แก้ทุกประการ

มันทำอะไรให้บ้าง

ของที่ใส่ให้ทำไมต้องมี
linux-image-*container ยืม kernel ของ host มาใช้ตลอดชีวิต VM ต้องมีของตัวเอง
grub-pccontainer ไม่เคยถูก boot จึงไม่เคยมี boot loader
initramfs-toolsต้องมี initramfs ที่มี module ของ virtio ไม่งั้นหาดิสก์ตัวเองไม่เจอ
net.ifnames=0ไม่ให้ชื่อการ์ดเปลี่ยนจาก eth0 เป็น ens18 ไฟล์ตั้งค่าที่ก๊อบมาจาก CT จะได้ยังใช้ได้
ttyS0เพื่อให้ qm terminal ใช้ได้ ทั้ง console ของ kernel และ getty กับบรรทัดใน securetty
getty@tty1container ไม่เคยมีจอ ถ้าไม่เปิดตัวนี้ หน้า noVNC จะดำสนิทหลัง boot เสร็จ
unmask unitsตัวที่ LXC ปิดตายไว้ ที่สำคัญที่สุดคือ systemd-udevd ถ้าปิดไว้ VM จะไม่มี /dev/vda1 ให้ mount ตั้งแต่แรก
hooks/c2vใส่ blkid เข้าไปใน initramfs ตัว init แปลง root=UUID= เป็นชื่ออุปกรณ์ด้วยการเรียก blkid ถ้าไม่มีก็หา root ไม่เจอ ทั้งที่ดิสก์อยู่ตรงนั้น
/dev/consoleบรรทัดสุดท้ายของ initramfs ส่ง stdio ของ init ผ่านไฟล์นี้ ถ้าไม่มี kernel จะ panic ทันทีที่กำลังจะส่งมอบงาน ทั้งที่ทุกอย่างก่อนหน้าผ่านหมด

บรรทัด grub.cfg boots root=UUID= คือด่านสุดท้ายที่กันไว้ไม่ให้ได้ VM ที่บูตไม่ขึ้น ตอน update-grub รันอยู่ใน chroot มันมองเห็นแค่ loop device ที่ mount ไว้ ถ้ามันไปเขียน root=/dev/loop0p1 ลงไฟล์แทนที่จะเป็น UUID เครื่องจะไปตายที่หน้าจอ initramfs พร้อมข้อความว่าหา /dev/loop0p1 ไม่เจอ ซึ่งอ่านไม่ออกเลยว่าเกิดจากอะไร โปรแกรมจึงอ่าน grub.cfg ที่เพิ่งสร้างกลับมาเทียบกับ UUID จริง ไม่ตรงคือหยุดทันที ไม่ปล่อยผ่าน

รันซ้ำได้ตลอด ทุกขั้นเช็กผลของตัวเองก่อนทำ ถ้าค้างกลางทางเพราะเน็ตหลุด รันใหม่มันจะเดินต่อจากจุดที่ค้าง ไม่เริ่มใหม่หมด และถ้ารันบน image ที่เสร็จแล้ว ผลคือ initramfs, grub.cfg และ MBR ชุดใหม่ ซึ่งไม่เสียหายอะไร

ถ้ามันเลือก kernel ผิดตัว เช่นเป็น Ubuntu แต่ไปลง linux-image-amd64 ของ Debian มันจะพังตอน apt-get แล้วบอกเอง แก้ด้วยการใส่ชื่อที่ถูกเอง

$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas \
    --kernel linux-image-generic
4

ลอง boot จริง

ไม่ต้องถอดแผ่น ไม่ต้องแก้ boot order เพราะไม่เคยมีแผ่นตั้งแต่แรก

$ qm start 9140
$ qm terminal 9140

ออกจากหน้าจอนี้กด Ctrl + O ล็อกอินเข้าไปด้วยรหัส root ตัวเดิมของ CT แล้วเช็ก 3 อย่าง

uname -r
df -h /
ip -o link show

บรรทัดแรกต้องได้เลข kernel ตัวที่เฟส 2 เพิ่งลงไป บรรทัดที่สองต้องเห็น /dev/vda1 และต้องไม่ใช่ ro บรรทัดที่สามต้องเห็นแค่ lo เพราะยังไม่มีการ์ด

ยังไม่ต้องรีบทำอะไรต่อ VM ตัวนี้ยังไม่มีเน็ตโดยตั้งใจ จะได้ไม่ชนกับ CT ตัวเก่าที่ยังรันอยู่ ลองเปิดโปรแกรมในนั้นดูให้พอใจ แล้วสั่งดับ

$ qm shutdown 9140

ถ้าหน้า noVNC ดำแต่ qm terminal ใช้ได้ หรือกลับกัน ก็ยังถือว่าผ่าน สองอันนี้คนละจอกัน จอ noVNC คือ tty1 ส่วน qm terminal คือ ttyS0 เฟส 2 เปิดให้ทั้งคู่ แต่ถ้าอันใดอันหนึ่งไม่ขึ้น ดูหัวข้อในส่วนเจอปัญหา

5

ทดสอบด้วยไอพีอีกตัว

ขั้นนี้ข้ามได้ แต่ถ้าอยากลองใช้งานจริงก่อนสลับตัว ต้องทำตามลำดับนี้เท่านั้น — CT ตัวเก่ายังรันอยู่ตลอดเวลา ไม่ต้องดับ

ตัว CT ไม่เสี่ยงอะไรเลย เฟส 1 แค่อ่านข้อมูลออกมาจาก CT ที่กำลังรัน ตัวที่เสี่ยงคือ VM ที่ก๊อบมา เพราะพอเปิดขึ้นมามันเชื่อว่าตัวเองคือเครื่องจริง งานตามเวลา ตัวส่งเมล ตัวส่งค่าไปเครื่องมอนิเตอร์ ตัวสำรองข้อมูล จะเริ่มทำงานกับของจริงทันทีพร้อมกับเครื่องเก่า

ห้ามใส่การ์ดเน็ตแล้วค่อยเข้าไปแก้ทีหลัง ตั้งแต่กดเปิดจนกว่าคุณจะล็อกอินได้ เครื่องเปิดบริการทุกตัวไปแล้ว งานตามเวลาอาจยิงไปแล้ว เมลที่ค้างในคิวอาจส่งออกไปหาคนจริงแล้ว ต้องแก้ในไฟล์ก่อนเปิดเสมอ

หนึ่ง ดับ VM แล้วเปิดไฟล์ disk ออกมาแก้

ทำบน node ใหม่ ที่เดียวกับสองเฟสที่ผ่านมา

$ qm stop 9140
$ IMG=$(pvesm path tank-hdd-nas:9140/vm-9140-disk-0.raw)
$ LOOP=$(losetup -Pf --show "$IMG")
$ mkdir -p /mnt/c2v
$ mount "${LOOP}p1" /mnt/c2v

ขั้นนี้ห้าม chroot ถึงแม้ว่าเฟส 2 จะ chroot ได้ เฟส 2 mount /run เป็น tmpfs เปล่าให้ก่อนเสมอ ด้วยเหตุผลข้อเดียวคือ systemctl ที่รันใน chroot จะคุยกับ systemd ของตัว node ผ่าน socket ใน /run/systemd/private ถ้าไม่มีตัวกั้นนั้น การสั่งปิดบริการในนี้คือการปิดบริการของ hypervisor คำสั่งข้างล่างทั้งหมดจึงเป็นการอ่านกับแก้ไฟล์ล้วนๆ โดยตั้งใจ

สอง ดูว่ามีอะไรจะโทรออกบ้าง

$ ls -1 /mnt/c2v/etc/systemd/system/multi-user.target.wants/ | sed 's/\.service$//'
$ cat /mnt/c2v/var/spool/cron/crontabs/* 2>/dev/null
$ ls -1 /mnt/c2v/etc/cron.d/ 2>/dev/null
$ grep -Ev '^[[:space:]]*#' /mnt/c2v/etc/fstab | grep -E 'nfs|cifs|gluster'
$ ls -l /mnt/c2v/var/lib/mysql/master.info 2>/dev/null
บรรทัดที่ถ้าเจอแปลว่า
1รายชื่อบริการที่จะเปิดเองตอน boot ทั้งหมด
2, 3งานตามเวลา จะเริ่มยิงเองภายในไม่กี่นาทีหลังเปิด ที่เก็บ crontab ของ Debian อยู่ลึกกว่าของ CentOS หนึ่งชั้น
4มีการ mount ที่เก็บข้อมูลจากเครื่องอื่น สองตัวจะเขียนไฟล์เดียวกัน
5ถ้ามีไฟล์นี้ ฐานข้อมูลตัวนี้เป็นตัวลูก มันจะไปต่อตัวแม่ด้วยเลขประจำตัวซ้ำกับของจริง แล้วเตะกันไปมา

สาม ตัดของพวกนั้นทิ้ง

เอาชื่อที่ได้จากขั้นสองมาใส่ในรายการนี้ ที่ให้มาเป็นตัวที่เจอบ่อย ยังไม่ครบทุกเครื่อง ตัวที่ห้ามลืมที่สุดคือ cron กับ keepalived — ตัวหลังจะไปแย่งไอพีกลางมาจากเครื่องจริง

$ for s in cron postfix exim4 zabbix-agent nagios-nrpe-server snmpd collectd \
           bacula-fd bareos-fd keepalived puppet salt-minion filebeat; do
    rm -f /mnt/c2v/etc/systemd/system/multi-user.target.wants/$s.service
  done

ลบเฉพาะทางลัดใน multi-user.target.wants เท่านั้น ไม่ได้ลบตัวบริการ พอก๊อบรอบสุดท้ายมาทับ ทางลัดพวกนี้จะกลับมาเองทั้งหมด ไม่ต้องไปนั่งเปิดคืนทีละตัว

สี่ ใส่ไอพีทดสอบ

Ubuntu 20.04 ที่มาจาก CT ของ Proxmox ตั้งค่าเน็ตไว้ที่ /etc/network/interfaces ส่วนที่ติดตั้งมาแบบอื่นอาจใช้ netplan ดูก่อนว่ามีอันไหน

$ cat /mnt/c2v/etc/network/interfaces 2>/dev/null
$ ls -1 /mnt/c2v/etc/netplan/ 2>/dev/null

ถ้าเป็นแบบแรก แก้ไฟล์เดียวจบ เอาบรรทัดไอพีจริงออก ใส่ไอพีทดสอบแทน

$ cat > /mnt/c2v/etc/network/interfaces <<'EOF'
auto lo
iface lo inet loopback

auto eth0
iface eth0 inet static
    address 192.168.99.10/24
EOF

ไม่ต้องใส่ gateway เครื่องทดสอบไม่ควรออกไปไหนได้ นั่นคือครึ่งหนึ่งของความปลอดภัยที่ได้จากขั้นนี้ อีกครึ่งคือ vlan99 ที่ไม่ได้ต่อออกไปข้างนอกอยู่แล้ว

ถ้าเป็น netplan ให้ย้ายไฟล์เดิมออกไปก่อน แล้วเขียนไฟล์ใหม่ทับ

$ mv /mnt/c2v/etc/netplan/01-netcfg.yaml /mnt/c2v/etc/netplan/01-netcfg.yaml.real
$ cat > /mnt/c2v/etc/netplan/99-c2vtest.yaml <<'EOF'
network:
  version: 2
  ethernets:
    eth0:
      addresses: [192.168.99.10/24]
EOF

ไฟล์ netplan ที่ย้ายออกไปต้องย้ายกลับเอง ต่างจาก /etc/network/interfaces ที่การก๊อบรอบสุดท้ายทับกลับมาให้เอง เพราะไฟล์ที่ลงท้ายด้วย .real ไม่มีอยู่ในตัว CT ตัวก๊อบจึงลบมันทิ้งด้วย --delete ส่วนไฟล์ 99-c2vtest.yaml ก็โดนลบเหมือนกัน ผลรวมคือถูกต้อง แต่ให้เช็กด้วยตาอีกรอบก่อนเปิดเครื่องจริง

ห้า ปิด mount จากเครื่องอื่นไว้ก่อน

ใส่คำนำหน้าไว้เพื่อให้หาเจอทีหลัง คำนี้ไม่มีความหมายกับ mount มันคือ comment ธรรมดา

$ sed -i -E 's@^([^#].*[[:space:]](nfs|nfs4|cifs)[[:space:]])@#C2VTEST# \1@' \
    /mnt/c2v/etc/fstab
$ grep -n C2VTEST /mnt/c2v/etc/fstab

หก ปิด disk แล้วเปิดเครื่อง

$ umount /mnt/c2v && losetup -d "$LOOP"
$ qm set 9140 --net0 virtio,bridge=vmbr99,tag=99,mtu=9000
$ qm start 9140
$ qm terminal 9140

ค่า tag=99 กับ mtu=9000 มาจากฝั่ง OVS ของ node เอง เพราะ vlan99 ถูกตั้งไว้ด้วย ovs_options tag=99 และ ovs_mtu 9000 ถ้าใส่ไม่ครบสองตัวนี้ การ์ดจะขึ้นแต่คุยกับใครไม่รู้เรื่อง

ทดสอบเสร็จแล้วดับ แล้วถอดการ์ดออก อย่าทิ้งไว้

$ qm shutdown 9140
$ qm set 9140 --delete net0

ถ้าเปิดไปแล้วโดยยังไม่ได้ตัดอะไรเลย ยังกู้ได้ ดับทันทีแล้วเปิดใหม่แบบไม่ให้บริการไหนขึ้นเลย ที่เมนู boot กด e เลื่อนไปที่บรรทัดที่ขึ้นต้นด้วย linux พิมพ์ single ต่อท้ายบรรทัดนั้น แล้วกด Ctrl + X ปุ่ม Enter ไม่ใช่ปุ่มสั่งบูตในเมนูนี้ จะได้หน้าจอ root เปล่าๆ ที่ไม่มีเน็ตและไม่มีงานตามเวลา เข้าไปแก้แล้วค่อย systemctl isolate multi-user.target

6

ย้ายจริง

ถึงตรงนี้ VM boot ได้แล้ว เหลือแค่ก๊อบข้อมูลรอบสุดท้ายแล้วสลับตัว ช่วงนี้บริการจะดับ ยาวเท่ากับเวลาก๊อบส่วนที่เปลี่ยนบวกอีกไม่กี่นาที

หนึ่ง ดับ CT ตัวเก่า พิมพ์บนเครื่องเก่า

$ ssh root@10.100.1.11
$ pct shutdown 140
$ pct status 140

สอง กลับมาที่ node ใหม่ ก๊อบรอบสุดท้ายด้วย --stopped

$ qm stop 9140
$ ./tools/c2v-prepare.sh \
    --old-node 10.100.1.11 \
    --old-ctid 140 \
    --vmid 9140 \
    --storage tank-hdd-nas \
    --stopped

สาม รันเฟส 2 ซ้ำ ทุกครั้งที่รันเฟส 1 ไม่ใช่ทางเลือก การก๊อบรอบสุดท้ายเอา /etc จาก CT กลับมาทับทั้งชุด ของที่เฟส 2 เคยแก้ไว้ในนั้นหายไปหมด — /etc/default/grub กลับไปเป็นของ container, ttyS0 หลุดจาก /etc/securetty, ทางลัดของ getty โดนลบ, unit ที่ LXC ปิดตายไว้กลับมาถูกปิดใหม่ ผลคือหน้าจอดำและอาจถึงขั้นไม่มี /dev/vda1 ทั้งที่เมื่อวานทดสอบผ่านหมด

$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas

รอบนี้เร็วมาก เพราะ /boot กับ /lib/modules อยู่ในรายการที่ตัวก๊อบข้ามไว้ kernel กับ grub จึงยังอยู่ครบ apt-get ไม่มีอะไรต้องลง เหลือแค่เขียน /etc/default/grub ใหม่ สร้าง initramfs กับ grub.cfg แล้วแก้ของใน /etc คืน

ของที่ไม่โดนทับกลับมี /boot, /lib/modules, /etc/fstab, /etc/mtab, /etc/initramfs-tools, /etc/kernel, 70-persistent-net.rules และตัว boot loader ที่อยู่นอกระบบไฟล์ ที่เหลือใน /etc ทับหมด

ถ้าเฟส 1 ขึ้น WARN ว่า this image has a kernel in /boot but not: ... แปลว่าเป็น image ที่ถูกก๊อบทับด้วยสคริปต์รุ่นเก่าที่ยังไม่ได้กันของพวกนี้ไว้ ตัว kernel ใน /boot ยังอยู่ VM จึงยังบูตขึ้นและดูปกติ แต่ไม่มี module ให้โหลดและสร้าง initramfs ใหม่ไม่ได้ รันเฟส 2 ซ้ำแก้ได้เลย apt จะลงกลับให้เอง แค่ใช้เวลาเป็นนาทีแทนที่จะเป็นวินาที

สี่ เฉพาะคนที่ทำขั้น 5 มา แก้ /etc/fstab คืน ถ้าไม่ได้ทำขั้น 5 ให้ข้ามไปข้อห้า

$ LOOP=$(losetup -Pf --show "$(pvesm path tank-hdd-nas:9140/vm-9140-disk-0.raw)")
$ mkdir -p /mnt/c2v && mount "${LOOP}p1" /mnt/c2v
$ sed -i 's@^#C2VTEST# @@' /mnt/c2v/etc/fstab
$ grep -Ev '^[[:space:]]*#' /mnt/c2v/etc/fstab
$ ls -1 /mnt/c2v/etc/netplan/ 2>/dev/null
$ umount /mnt/c2v && losetup -d "$LOOP"

ไอพีทดสอบกับบริการที่ตัดไป ไม่ต้องแก้คืน ข้อสองทับกลับมาให้เองแล้ว แต่ /etc/fstab อยู่ในรายการที่ตัวก๊อบข้ามเสมอ มันจึงยังค้างเป็น #C2VTEST# อยู่ ลืมข้อนี้แล้วเครื่องจริงจะขึ้นมาโดยไม่มีที่เก็บข้อมูลจากเครื่องอื่น บรรทัดรองสุดท้ายมีไว้ดูว่าโฟลเดอร์ netplan กลับมาเหมือนของ CT แล้วจริงไหม

ห้า ใส่การ์ดเน็ตให้ VM แล้วเปิด ต้องใส่ให้ครบทุกใบที่ CT เคยมี เฟส 1 พิมพ์บรรทัดที่ถูกต้องไว้ให้แล้วตอนจบ ก๊อบมาจากตรงนั้นดีที่สุด อย่านึกเอง

$ qm set 9140 --net0 virtio,bridge=vmbr99,tag=99,mtu=9000
$ qm start 9140
$ qm terminal 9140

ขาดการ์ดไปใบหนึ่ง ไม่ได้แปลว่าเสียแค่ใบนั้น ไฟล์ตั้งค่าของใบที่หายยังอยู่ในเครื่อง บริการที่ผูกกับไอพีของใบนั้นจะพยายาม bind แล้วตายด้วยรหัส 99 ทั้งที่อีกใบทำงานปกติ อาการที่เห็นคือเว็บบางตัวขึ้นบางตัวไม่ขึ้น ซึ่งอ่านเหมือนปัญหาเส้นทางแต่ไม่ใช่ ค่า mtu กับ tag ก็ต้องตรงของเดิมด้วย

ping -c 3 10.100.1.1

เจอแบบนี้ทำยังไง

บูตแล้วไปค้างที่ initramfs ขึ้นว่าหา /dev/loop0p1 ไม่เจอ

แปลว่า grub.cfg ถูกเขียนด้วยชื่ออุปกรณ์ที่มีอยู่แค่บน node ตอนที่ chroot อยู่ ไม่ใช่ UUID ที่ติดไปกับดิสก์ ปกติเฟส 2 กันไว้แล้วและจะหยุดตัวเองก่อนถึงตรงนี้ ถ้ามาถึงหน้าจอนี้ได้แปลว่า image นี้ถูกทำโดยสคริปต์คนละรุ่น รันเฟส 2 รุ่นนี้ทับลงไปแก้ได้เลย

$ qm stop 9140
$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas

บูตแล้วขึ้น ALERT! UUID=... does not exist แล้วตกไปที่ initramfs shell

Gave up waiting for root file system device. ALERT! UUID=60e21d24-efbf-4b2d-ac32-dc3241bd7cc8 does not exist. Dropping to a shell! (initramfs)

ตรงนี้หลอกมาก เพราะถ้าพิมพ์ blkid ที่หน้าจอนั้นมันจะตอบ UUID ตัวเดียวกันเป๊ะ ดิสก์อยู่ครบ partition อยู่ครบ UUID ตรง แต่ initramfs หาไม่เจอ

สาเหตุคือใน initramfs ไม่มี blkid ตัวที่พิมพ์ได้คือของบนดิสก์จริง คนละตัวกัน ตัว init แปลง root=UUID= เป็นชื่ออุปกรณ์ด้วยการเรียก blkid ไม่ใช่ด้วยโค้ดของตัวเอง และคนที่ใส่ blkid เข้าไปใน initramfs คือ hook ของแพ็กเกจ udev ซึ่งเฟส 1 ข้ามทั้งโฟลเดอร์ /usr/share/initramfs-tools ไป และ apt ก็เอากลับมาให้ไม่ได้ เพราะฐานข้อมูล dpkg ที่ก๊อบมาบอกว่า udev ลงอยู่แล้ว mkinitramfs จึงสร้าง initramfs ที่หน้าตาปกติทุกอย่างแล้วจบด้วย exit 0

เฟส 2 ตั้งแต่รุ่น 2026-08-04a เขียน hook ของตัวเองไว้ที่ /etc/initramfs-tools/hooks/c2v ซึ่งอยู่ใต้ /etc ที่เฟส 1 ข้ามเหมือนกัน รันเฟส 1 ซ้ำกี่รอบก็ไม่หาย และหลัง update-initramfs มันจะแกะ initramfs ออกมาอ่านว่ามี blkid จริงไหม ไม่มีคือหยุด ไม่ปล่อยให้ไปเจอที่หน้าจอ ถ้าเจออาการนี้แปลว่า image ถูกทำด้วยรุ่นก่อนหน้านั้น รันเฟส 2 ทับได้เลย

$ qm stop 9140
$ ./tools/c2v-inside-deb.sh --vmid 9140 --storage tank-hdd-nas

อยากเช็กของจริงในดิสก์โดยไม่ต้องเปิดเครื่องก็ได้ ต้องเห็นบรรทัดที่ลงท้ายด้วย bin/blkid

$ LOOP=$(losetup -Pf --show "$(pvesm path tank-hdd-nas:9140/vm-9140-disk-0.raw)")
$ mkdir -p /mnt/c2v && mount "${LOOP}p1" /mnt/c2v
$ lsinitramfs /mnt/c2v/boot/initrd.img-* | grep blkid
$ umount /mnt/c2v && losetup -d "$LOOP"

บูตแล้ว panic ว่า Attempted to kill init! exitcode=0x00000100

Begin: Running /scripts/init-bottom ... done. Kernel panic - not syncing: Attempted to kill init! exitcode=0x00000100 /init: line 373: can't open /root/dev/console: no such file CPU: 4 PID: 1 Comm: sh Not tainted 5.4.0-216-generic

อาการนี้เกิดหลังจากทุกอย่างผ่านหมดแล้ว ถ้าเลื่อนขึ้นไปดูจะเห็นว่า fsck รันแล้วบอกว่าสะอาด และ EXT4-fs (vda1): mounted filesystem ก็ขึ้นเรียบร้อย ระบบไฟล์ไม่ได้มีปัญหาอะไรเลย

บรรทัดสุดท้ายของ /init คือ exec run-init ... <${rootmnt}/dev/console >${rootmnt}/dev/console และ shell จะเปิดไฟล์ที่จะ redirect ก่อน exec เสมอ พอไม่มี /root/dev/console การเปิดก็ล้มเหลว dash ตายด้วย exit 1 และ dash ตัวนั้นคือ pid 1 kernel เลยรายงานว่า exitcode=0x00000100 ซึ่งก็คือ 1 เลื่อนไป 8 บิต ส่วนคำว่า Comm: sh เป็นหลักฐานว่าตอนนั้น pid 1 ยังเป็น shell ของ initramfs อยู่ ยังไม่ทันได้เป็น systemd

ปกติมีสองอย่างที่กันไว้ไม่ให้ใครต้องรู้เรื่องนี้ อย่างแรกคือเครื่อง Debian ที่ลงเองมี /dev/console กับ /dev/null ติดดิสก์มาตั้งแต่ debootstrap อย่างที่สองคือ script init-bottom/udev ที่ย้าย /dev ตัวจริงไปวางให้ก่อนส่งมอบ ทาง CT ไม่มีทั้งสองอย่าง เพราะ /dev บนดิสก์ของ container ว่างเปล่า (ตัว runtime เอา tmpfs ครอบไว้) ตอนก๊อบจึงไม่มีอะไรให้ก๊อบตั้งแต่แรก และ init-bottom/udev ก็หายไปกับ /usr/share/initramfs-tools ชุดเดียวกับ hook ของ blkid ข้างบน

เฟส 2 ตั้งแต่รุ่น 2026-08-04b สร้าง device node พวกนี้ลงดิสก์ให้เอง แล้วอ่านกลับมาเช็กว่าเป็น character device จริง รันทับได้เลย
