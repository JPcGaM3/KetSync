What runs by itself, how to read the mail, adding a CT, and the habits of these commands

Everything on this page is typed on the storage node (10.100.1.17)
1

The rhythm — what runs by itself

The crontab -e form. In /etc/cron.d/ the sixth field must be the USER (*/10 * * * * root /root/...) or cron throws the whole file away - doctor checks that every run. The backup node runs one line of its own: ketsync watch, watching whether the master answers.

Never hand an engine -y. No engine has heard of it: it answers unknown argument: -y and exits 2, so the line has never run once - and with >/dev/null on the end, nothing says so. The rule: engine called directly = no -y; a WRITING verb through ketsync = -y; a read-only verb (watch, doctor, status) = none needed. doctor checks both directions.

crontab -l on a healthy master
*/15 * * * * /root/ketsync/engines/ct-replica.sh --storage tank-hdd-nas
*/15 * * * * /root/ketsync/engines/ct-replica.sh --storage tank-ssd-nas
*/10 * * * * /root/ketsync/ketsync watch
30 7 * * * /root/ketsync/ketsync watch --digest
2

Four kinds of mail

watch mails on change only: RAISED when a problem appears, CLEARED when it goes, silence in between.

mailmeansfirst move
[ketsync] INFRA ... the floor: backup node silent, PAUSE standing, or DR stand-ins live read the body; storage-related → open 05
[ketsync] NODE ... one machine: no ssh answer, or a storage an evacuate left off ssh into the machine it names
daily digestdoctor's full report, per-CT items included skim the non-ok sections; under a minute on a good day
INFRA: master-unreachable sent by the BACKUP node, not the master: the storage node missed three ssh probes, and nothing is watching the fleet right now open 05 - the DR is driven from the backup

Who watches whom. The master watches the fleet; the backup node watches one thing - does the master answer - because the machine that reports the fleet cannot report its own death. The scopes never overlap, so nothing arrives twice.

Silence is a signal too. If healthchecks.io says the ping stopped, the watcher itself is down or its mail is broken — worse than any mail it ever sent. Check ./ketsync watch --list on the master.

Adding a CT

two tables → sync → dry-run → real
# conf/fleet.tsv - the map (ct, home, dr, dst - tabs)
130	10.100.1.32	10.100.1.32	local-lvm
# inventory/inventory-replica.tsv - the work list
130	replica-hdd
# bump each file's "# generation:" line, then:
./ketsync sync
./ketsync replica --dry-run --ctid 130
./ketsync replica --ctid 130
5

sync always, and FORKED

Edit a table on the master, push it yourself — nothing is automatic, and a forgotten sync means the backup node holds last month's list with no warning. FORKED means two machines hold the same generation with different contents; sync stops and pushes nothing.

sync --diff → edit → sync --bump <file>
./ketsync sync --diff
$EDITOR conf/fleet.tsv
./ketsync sync --bump fleet.tsv     # one file at a time
6

Three habits of these commands

  • A bare verb refuses (exit 2) and prints its menu — four more characters (--all) is the record that you meant the fleet.
  • A writing command asks once, stating what it writes; cron lines need -y (doctor nags about missing ones - read-only verbs excepted).
  • Per-CT pause: touch engines/pause/<ctid>, remove to resume. engines/PAUSE stops everything and belongs to failback windows only.
