02 — Install from zero

Cluster, ssh, one storage name, the dead-end bridge, three files, first green copy, alert mail

Condensed mirror - the Thai edition carries the full detail (PBS setup included). Every step says which machine.
1

Cluster the compute + backup nodes

The storage node stays out of the cluster, on purpose.

pvecm create / add / qdevice
# first compute node
pvecm create tomato
# every other compute node, and the backup node
pvecm add 10.100.1.32
# a third vote on a machine that is NOT a member, then on every member:
apt install -y corosync-qnetd          # voter machine
apt install -y corosync-qdevice        # every member
pvecm qdevice setup 10.100.1.40

Verify: pvecm status says Quorate: Yes and lists every member.

2

Passwordless ssh from the storage node

ssh-keygen + ssh-copy-id to every machine
# on the storage node
ssh-keygen -t ed25519 -N "" -f /root/.ssh/id_ed25519
ssh-copy-id root@10.100.1.9     # backup - REQUIRED
ssh-copy-id root@10.100.1.32
ssh-copy-id root@10.100.1.33

Verify: every line prints OK:

for ip in ...; do ssh -o BatchMode=yes ...
for ip in 10.100.1.9 10.100.1.32 10.100.1.33; do
  printf '%s ' "$ip"; ssh -o BatchMode=yes root@$ip true && echo OK || echo FAIL
done
3

One storage name, two sides

Same id on both sides, different type — a CT's config remembers only the name.

pvesm add dir / nfs tank-hdd-nas
# storage node - the real files
pvesm add dir tank-hdd-nas --path /tank/hosting --is_mountpoint yes --content images,rootdir
# EVERY compute node - same id, over NFS
pvesm add nfs tank-hdd-nas --server 10.100.1.17 --export /tank/hosting --content images,rootdir

Verify: pvesm status | grep tank-hdd-nas says active on both sides.

4

The dead-end bridge, on backup and every compute node

Copies live on an island: a bridge with no uplink, so a copy started by mistake answers nobody.

vmbr99 into /etc/network/interfaces
cat >> /etc/network/interfaces <<'EOF'

auto vmbr99
iface vmbr99 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
EOF
ifup vmbr99

Verify: ls /sys/class/net/vmbr99/brif/ is EMPTY on every node. On an OVS node build an OVS bridge instead and check ovs-vsctl --timeout=5 list-ifaces vmbr99.

5

Install the tool, fill three files

git clone + copy the samples
# on the storage node AND the backup node - same path on purpose
git clone <this repo> /root/ketsync
cd /root/ketsync
cp conf/ketsync.conf.sample  conf/ketsync.conf
cp conf/nodes.tsv.sample     conf/nodes.tsv
cp conf/fleet.tsv.sample     conf/fleet.tsv
cp inventory/inventory-replica.sample.tsv inventory/inventory-replica.tsv
filewhat goes in
conf/ketsync.confKS_ROLE=master on storage, slave on backup; KS_MASTER_IP=10.100.1.17. Never scp this file between machines.
conf/nodes.tsvone line per machine: ip TAB role (storage / backup / compute). No name column, on purpose.
conf/fleet.tsvthe DR map: ct, home, dr, dst — every column required, no defaults
inventory/inventory-replica.tsvwhat to copy nightly: ct + dest pool, every row
TAB completion (optional, once per machine)
# ./ketsync repl<TAB> -> replica; flags and --ctid values complete too
echo 'source /root/ketsync/tools/ketsync-completion.bash' >> /root/.bashrc
source /root/.bashrc

7

Alert mail — the system speaks when nobody is looking

  1. Everything into conf/ketsync.conf - who gets told, and which relay carries it
    KS_MAIL_* + relay + optional dead-man
    KS_MAIL_FROM="ketsync@example.com"      # must be VERIFIED as a sender at the provider
KS_MAIL_INFRA="infra@example.com"
KS_MAIL_NODE="node@example.com"
KS_MAIL_DIGEST="admin@example.com"
KS_WATCH_HEALTHCHECK="https://hc-ping.com/<uuid>"   # optional
# the transport - changing provider = edit these three, re-run mail-setup
KS_MAIL_RELAY="[smtp-relay.brevo.com]:587"
KS_MAIL_USER="b5c6b3001@smtp-brevo.com" # the login the provider's SMTP page shows
KS_MAIL_KEYFILE="/root/.brevo.key"      # the PATH to the key, never the key

    KS_MAIL_USER is whatever the provider generates (SendGrid: the literal word apikey with relay smtp.sendgrid.net), and KS_MAIL_FROM must be an address the provider has VERIFIED as a sender - relays validate the envelope sender and reject one they have never heard of.

  2. Drop the key in place, then let ketsync point postfix at the relay
    ketsync mail-setup --test
    # on the storage node - and again on the backup node
apt-get install -y libsasl2-modules   # postfix cannot AUTH without these; PVE ships bare
echo 'xsmtpsib-your-key' > /root/.brevo.key && chmod 600 /root/.brevo.key
./ketsync mail-setup --test

    The test mail goes to KS_MAIL_INFRA from KS_MAIL_FROM - the exact path watch's own mail will take. It has to actually arrive before the next step. If nothing does: journalctl -u postfix -n 30 has the provider's answer (535 = wrong user/key, 550 sender = not verified). The script underneath is contrib/mail-satellite.sh, still runnable by hand with explicit flags.

  3. Rehearse, then cron
    watch --dry-run → watch → cron
    ./ketsync watch --dry-run
./ketsync watch
./ketsync watch --digest
# crontab - watch is read-only, no -y needed
*/10 * * * * /root/ketsync/ketsync watch
30 7 * * * /root/ketsync/ketsync watch --digest

    4. Two places, two formats. The lines above are the crontab -e form: five time fields, then the command. A file in /etc/cron.d/ is a SYSTEM crontab and needs a user as the sixth field - without it cron throws away the WHOLE file (bad username) and every job in it silently stops existing, visible only in systemctl status cron.

    /etc/cron.d/ketsync-watch (with the user field)
    PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
*/10 * * * * root /root/ketsync/ketsync watch
30 7 * * * root /root/ketsync/ketsync watch --digest

    ./ketsync doctor checks this every run: cron.d lines cron itself will not run.

  4. Do the same on the BACKUP node — the machine that reports the fleet cannot report its own death
    backup node: mail-setup + KS_MAIL_FROM/INFRA + cron
    # on the backup node
apt-get install -y libsasl2-modules
echo 'xsmtpsib-your-key' > /root/.brevo.key && chmod 600 /root/.brevo.key
# conf/ketsync.conf there: KS_ROLE=slave, KS_MASTER_IP=<storage ip>,
# plus KS_MAIL_FROM / KS_MAIL_INFRA / KS_MAIL_RELAY / KS_MAIL_USER / KS_MAIL_KEYFILE
./ketsync mail-setup --test
./ketsync watch --dry-run
*/10 * * * * /root/ketsync/ketsync watch

    The master watches the fleet; a slave watches ONE thing - does the master answer. When the storage node dies its watch dies with it, so the first mail you get comes from here. The scopes never overlap: the master never says "the master is gone" and the slave says nothing else. It asks ssh 3 times, 5s apart, before it believes it, so a blip is not a page. KS_MAIL_NODE is not needed on a slave - it mails INFRA only.

Only green runs ping the dead-man — a dead watch or a broken transport goes silent, and the silence is the alarm. Two layers that cover different holes: the slave says WHAT died within a cron tick; the dead-man catches both machines going quiet at once. How to read the mail: 03-daily.
