ketsync — the whole thing on one page

What it does, every command, and what to type in each situation. Five minutes.

The shortcut. Full detail lives in the contents.
1

What it does

Copies every container's disk to a second machine every 15 minutes, and when the machine holding those disks dies, runs the copies on a compute node so customers stay up.

machineexamplejob
storage10.100.1.17holds the real disks; the machine you drive from (master)
backup10.100.1.9holds the copies; the machine you drive from when storage is gone
compute10.100.1.32/.33actually runs the containers
numberwhat it is
300the real container. The only id anyone types
8300its copy on the backup node, always stopped = 300 + 8000
9300the temporary stand-in on a compute node = 300 + 9000
vmbr99a bridge with no uplink - where copies and cut-off containers sit

Two hard rules. Nothing here ever starts a container - you type that yourself - and nothing ever guesses a value you did not write down.

3

Situation 1 — the nightly copy (replica)

cron already does this. You only touch it when a container is added.

File to edit: inventory/inventory-replica.tsv. A container with no row here is never copied, and nothing complains.

  1. Add the row: id + destination pool (replica-hdd or replica-ssd)
    inventory/inventory-replica.tsv
    130	replica-hdd
  2. Push the tables
    ./ketsync sync
    ./ketsync sync
  3. Run the first round by hand and check it
    ./ketsync replica --ctid 130
    ./ketsync replica --ctid 130
./ketsync status

    It must end failed=0; cron takes it from there.

4

Situation 2 — the storage node died (distribute)

Every container is frozen. Goal: get the copies running on compute, fast. Type this on the backup node - the storage node is gone.

File that must be right: conf/fleet.tsv, every container, four columns ct / home / dr / dst. A row missing anything is refused rather than guessed. The usual mistake is dst: it must match pvesm status on the target machine exactly.

  1. See the plan first - writes nothing
    ./ketsync distribute --all --dry-run
    ./ketsync distribute --all --dry-run
  2. For real: it disables the dead storage, takes the old containers off the wire, then places the copies
    ./ketsync distribute --all
    ./ketsync distribute --all
  3. Start them yourself, one at a time - that decision has a customer on it
    ssh root@compute pct start 9xxx
    ssh root@10.100.1.32 pct config 9110
ssh root@10.100.1.32 pct start 9110

Re-running after a partial round? --no-prepare skips the first half, which is already done.

5

Situation 3 — the storage node is back (recover)

The way back is a seven-step checklist; recover is that checklist executed, and it is re-runnable - a step already done is skipped. Type this on the storage node.

File that must be right: conf/fleet.tsv again - this time the home column, so it knows which machine to fsck each disk on. A container with no row prints no row in fleet.tsv and is skipped.

  1. First, on the backup node: pull what the stand-ins served back into the copies
    ./ketsync recall --all --final
    ssh root@10.100.1.32 pct shutdown 9110
./ketsync recall --all --final
  2. See what is left - read-only
    ./ketsync recover --list
    ./ketsync recover --list
  3. For real: storages back on, fsck the damaged disks, copies written back, network restored, stand-ins put away
    ./ketsync recover --all
    ./ketsync recover --all
./ketsync recover --ctid 137
  4. Start the real containers yourself and check them
    ssh root@compute pct start 110
    ssh root@10.100.1.32 pct start 110
  5. Happy? Then the last sweep - remove the stand-ins and let replication resume
    ./ketsync recover --all --destroy
    ./ketsync recover --all --destroy

    Until --destroy, the nightly copy stays PAUSED on purpose, so nothing overwrites a copy that may still be the good one.

6

Situation 4 — a new container

Two files, then sync. Forget one and it stays quiet until the day it matters.

filerowif you forget
inventory/inventory-replica.tsv130 replica-hddnever copied
conf/fleet.tsv130 home dr dstcannot be recovered on the day
./ketsync sync && ./ketsync doctor
./ketsync sync
./ketsync doctor

The mail you get

Only on change: once when a problem appears, once when it clears, silence in between.

subjectmeans
