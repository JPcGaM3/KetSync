05 — Disaster day

The storage node is dead. Six stages, all the way home — condensed; the Thai edition carries the full reasoning

Type everything on the backup node (10.100.1.9) unless a step says otherwise
0

Before anything: is it really dead?

ping + ssh probe from the backup node
# on the BACKUP node
ping -c3 10.100.1.17
ssh -o ConnectTimeout=5 root@10.100.1.17 true; echo "rc=$?"
  • Still answers? Stop here and fix the real cause — the copies are all still there.
  • Half-alive? touch /root/ketsync/engines/PAUSE on it first, so the next cron tick cannot overwrite the copies you are about to lean on.

If a [ketsync] INFRA mail from watch brought you here: yes, this is the page. Copies are 15 minutes old at worst; work lost is bounded. Nothing here starts a container — every start is yours.

1

Get production out of the way

./ketsync evacuate — per node or the fleet
# on the BACKUP node
./ketsync evacuate --all --dry-run
./ketsync evacuate --node 10.100.1.32
./ketsync evacuate --all

Per node, in the only order that works: disable the dead storage, force the mount to fail, restart pvestatd, then stop the CTs on it — a CT that will not stop is moved onto vmbr99 (ISOLATED) instead, with its real bridge written down. E2 refuses a storage that still answers; healthy storages on the same node are never touched.

2

Place the stand-ins

./ketsync distribute — list, one, all
./ketsync distribute --list
./ketsync distribute --ctid 300 --dry-run
./ketsync distribute --ctid 300
./ketsync distribute --all

Copy 8300 → CT 9300 on the compute node fleet.tsv names, network taken from production's own config (or the isolate record). It prints the pct start 9300 for you to type, per CT, in your priority order.

3

Copy back while the stand-ins serve

./ketsync recall --all — repeatable
./ketsync recall --list
./ketsync recall --all      # 9300 -> 8300, run as often as you like

Do not skip this. From the moment 9300 serves, every customer write lives on one compute disk only. recall closes that hole; watch the changed= number shrink.

4

The storage node returns

PAUSE first, then narrow the gap
# on the STORAGE node, immediately after boot
touch /root/ketsync/engines/PAUSE
zpool status && pvesm status && ./ketsync doctor
# then, repeatedly, while customers keep working:
./ketsync recall --all        # on the backup node
./ketsync failback --all      # on the storage node

R13 already protects every copy that has a live 9xxx — PAUSE is the cheap second fence, and the one failback --final requires.

5

Cut over, per CT

shutdown 9300 → recall --final → failback --final → restore → start
pct shutdown 9300                          # on its compute node
./ketsync recall --ctid 300 --final        # backup node
./ketsync failback --ctid 300 --final      # storage node - snapshots first (B7)
./ketsync restore --ctid 300               # bridge + onboot from the record
pct start 300                              # a person decides this one

Downtime is the gap between the shutdown and the start — seconds, if stages 3-4 were run.

6

Clean up — or let recover do 4-6 in one command

./ketsync recover — the checklist, executed
# on the STORAGE node, once every 9xxx is stopped and recall --final ran
./ketsync recover --list
./ketsync recover --all              # keeps each 9xxx as a fallback
./ketsync recover --all --destroy    # the complete return: destroy, unpause, replicate

State-driven and re-runnable: what is already done is skipped and said. A kept 9xxx holds that CT out of replication (R13) until somebody destroys it. watch mails CLEARED when the records are truly gone — no CLEARED means something is left; ./ketsync watch --list names it.
