เครื่อง storage ตาย ทำยังไง

อ่านหน้านี้ตอนยังไม่เกิดเหตุ แล้วเปิดซ้ำตอนเกิด — ทุกขั้นเป็นคำสั่งที่พิมพ์ได้เลย

ทุกคำสั่งในหน้านี้พิมพ์บนเครื่อง backup (10.100.1.9) เว้นแต่จะเขียนบอกไว้

ตอนนี้ทำได้แค่ไหน — อ่านก่อน

พูดตรงๆ ว่ายังไม่ครบ จะได้ไม่ไปคาดหวังผิดตอนเกิดเหตุจริง

อยากทำตอนนี้
ปลุกสำเนาขึ้นมารันที่เครื่อง backupทำได้ ด้วยมือ ตามหน้านี้
เอาข้อมูลกลับเข้าตัวจริงตอน storage ฟื้นทำได้ ด้วย ketsync failback
กระจายสำเนาไปรันที่เครื่อง compute (9xxx)ทำได้ด้วยคำสั่ง — ketsync distribute ดูข้อ 3
ดึงข้อมูลจาก 9xxx กลับเข้าตัวจริงทำได้ด้วยมือ ตามข้อ 6ก — ketsync recall ยังไม่ได้สร้าง
ก๊อปข้อมูลต่อระหว่างที่รันอยู่ที่ computeยังทำไม่ได้ ช่วงนั้นไม่มีสำเนาสำรอง

แปลว่าเครื่อง backup คือที่เก็บของ ไม่ใช่ที่รันของ และไม่ใช่ที่รัน engine ด้วย — ตัว ct-replica.sh กับ ct-failback.sh อ่านและเขียนไฟล์ดิสก์ที่อยู่บนเครื่อง storage ทั้งคู่ พอเครื่องนั้นตาย ก็ไม่มีอะไรให้มันทำ ของต้องถูกก๊อปต่อไปที่เครื่อง compute แล้วรันที่นั่น ซึ่งตอนนี้มีคำสั่งทำให้แล้ว

ข้อจำกัดที่ต้องยอมรับ ต่อให้กระจายไปหลายเครื่องแล้ว ก็ยังไม่พอรัน CT ทุกตัวพร้อมกัน ต้องเลือกเฉพาะตัวสำคัญ เรียงลำดับไว้ล่วงหน้าดีกว่ามานั่งเลือกตอนตี 3

./ketsync failback --list

ยืนยันก่อนว่าตายจริง

อย่ารีบ ปลุกสำเนาขึ้นมาทั้งที่ตัวจริงยังรันอยู่ = มีสองเครื่องใช้ IP เดียวกัน ซึ่งพังหนักกว่าเดิมและแก้ยากกว่า

# on the BACKUP node
ping -c3 10.100.1.17
ssh -o ConnectTimeout=5 root@10.100.1.17 true; echo "rc=$?"

ถ้ายัง ping ติดหรือ ssh เข้าได้ อย่าเพิ่งทำต่อ เครื่องอาจแค่ช้าหรือ NFS ค้าง ให้ไปแก้ที่ต้นเหตุก่อน สำเนายังอยู่ครบ ไม่ได้หายไปไหน

ถ้าเครื่อง storage ยังพอมีชีวิต ให้ปิด cron ก่อนเป็นอย่างแรก ไม่งั้นรอบถัดไปมันจะพยายามก๊อปทับสำเนา ตอนที่คุณกำลังจะใช้สำเนานั้น

# on the STORAGE node, if you can still reach it
touch /root/ketsync/engines/tp/PAUSE

ย้ายสำเนาไปรันชั่วคราวที่เครื่อง compute

สำเนาอยู่ที่เครื่อง backup ก็จริง แต่ไม่ได้เอาไปรันที่นั่น เครื่อง backup มีหน้าที่เก็บของ ไม่ได้มีแรงพอจะรัน CT ทั้งฟลีต ของต้องถูกก๊อปต่ออีกทอดไปลงดิสก์ในตัวเครื่อง compute เอง ซึ่งเป็นที่เก็บของที่เดียวในตึกที่ไม่ได้พึ่งเครื่องที่เพิ่งตายไป

เลข CT บอกว่ากำลังดูอะไรอยู่

เลขคืออะไรอยู่ที่ไหน
300ตัวจริงดิสก์บนเครื่อง storage ผ่าน NFS
8300สำเนาที่ก๊อปทุกคืน ปิดอยู่เครื่อง backup
9300ตัวชั่วคราวตอนฉุกเฉินlocal-lvm ของเครื่อง compute

เห็นเลข 9 นำหน้าเมื่อไหร่ให้รู้ทันทีว่านี่คือของชั่วคราวที่ต้องเก็บกวาดทีหลัง ไม่ใช่ตัวจริง

มีคำสั่งทำให้แล้ว ไม่ต้องทำมือ ขั้นตอนที่เคยต้องพิมพ์ทีละบรรทัด ตอนนี้อยู่ใน ketsync distribute ครบ พร้อมด่านตรวจ 7 ด่าน ขั้นตอนแบบมือยังเก็บไว้ท้ายหัวข้อนี้ เผื่อวันที่ต้องแกะดูว่ามันทำอะไรอยู่

ขั้นที่ 1 — ดูก่อนว่ามันจะทำอะไร ยังไม่แตะอะไร

cd /root/ketsync
./ketsync distribute --list

มันจะพิมพ์ออกมาว่า CT ตัวไหนจะไปเครื่องไหน ลง storage อะไร ใช้เนื้อที่เท่าไหร่ ตัวไหนที่ไม่มีที่ไปมันจะบอกว่าไม่มีแถวใน fleet.tsv — ไม่เดาให้ ต้องบอกด้วย --to เอง

ขั้นที่ 2 — ซ้อมตัวเดียวก่อน

./ketsync distribute --ctid 300 --dry-run

เดินผ่านด่านตรวจครบทุกด่านเหมือนของจริง ต่างกันแค่ไม่จองเนื้อที่ ไม่ก๊อป ไม่เขียน config

ขั้นที่ 3 — ของจริง ทีละตัวตามลำดับความสำคัญ

./ketsync distribute --ctid 300
./ketsync distribute --ctid 300 --to 10.100.1.33          # override the placement
./ketsync distribute --ctid 300 --to 10.100.1.33 --dst local-zfs

มันจะจองเนื้อที่บนเครื่องปลายทาง ทำ filesystem ก๊อปข้อมูลจากเครื่อง backup แล้วเขียน config ให้ — แต่ไม่เปิดให้ มันจะพิมพ์คำสั่งเปิดออกมาให้คนกดเอง เหมือนทุกเครื่องมือในชุดนี้

[300] placed: CT 9300 on pve01, local-lvm:vm-9300-disk-0, rsync rc=0 in 412s [300] its network is still on the copy's bridge. Check it, then start it BY HAND: [300] ssh root@10.100.1.32 pct config 9300 [300] ssh root@10.100.1.32 pct set 9300 --net0 <the production bridge> [300] ssh root@10.100.1.32 pct start 9300

ขั้นที่ 4 — ทั้งฟลีตทีเดียว เมื่อซ้อมตัวแรกผ่านแล้ว

./ketsync distribute --all

ตัวไหนพลาดมันข้ามไปตัวถัดไป ไม่หยุดทั้งชุด แล้วสรุปตอนท้ายว่าตัวไหนไม่ผ่านเพราะอะไร

ด่านที่จะเจอบ่อยที่สุดคือ D1 — ถ้า CT ตัวจริงยังรันอยู่ มันจะไม่ยอมวางสำเนา เพราะสำเนาถือ IP กับ MAC เดียวกัน สองตัวตอบพร้อมกันแย่กว่าเหตุที่กำลังแก้อยู่ ให้ปิดตัวจริงก่อน แล้วค่อยสั่งใหม่

ทำมือ (ถ้าอยากรู้ว่าคำสั่งข้างบนทำอะไร)

สามขั้นล่างนี้คือสิ่งที่ ketsync distribute ทำให้ ไม่ต้องพิมพ์เองแล้ว เก็บไว้เผื่อต้องแกะปัญหา

ขั้นที่ 1 — จองเนื้อที่บนเครื่อง compute

ดูขนาดจาก config ของสำเนาก่อน แล้วจองเท่านั้น

# on the BACKUP node - read the size and keep the whole config
pct config 8300 | tee /tmp/8300.conf | grep rootfs
rootfs: replica-hdd:subvol-8300-disk-0,size=20G
# on the COMPUTE node that will run it
pvesm alloc local-lvm 9300 vm-9300-disk-0 20G
mkfs.ext4 -F /dev/pve/vm-9300-disk-0

ขั้นที่ 2 — ก๊อปข้อมูลจากเครื่อง backup มาลง

# on the COMPUTE node
mkdir -p /mnt/dr-9300
mount /dev/pve/vm-9300-disk-0 /mnt/dr-9300

rsync -aHAX --numeric-ids --sparse --info=progress2 \
  root@10.100.1.9:/replica-hdd/ct/subvol-8300-disk-0/ /mnt/dr-9300/

sync
umount /mnt/dr-9300

ถ้า rsync จบด้วยรหัส 0 หรือ 24 ถือว่าผ่าน (24 แปลว่ามีไฟล์หายไประหว่างก๊อป ซึ่งปกติ) รหัส 23 คือก๊อปได้ไม่ครบ ให้สั่งซ้ำอีกรอบก่อนไปต่อ

ขั้นที่ 3 — เขียน config ให้ตัวชั่วคราว

เอา config ของสำเนามาแก้สองบรรทัด: ชี้ rootfs ไปที่ดิสก์ที่เพิ่งทำ และย้าย net กลับเน็ตจริง

# on the COMPUTE node - $(hostname) is this node's own pmxcfs directory
sed -e 's|^rootfs:.*|rootfs: local-lvm:vm-9300-disk-0,size=20G|' \
    -e 's|bridge=vmbr99|bridge=vmbr0|' \
    /tmp/8300.conf > /etc/pve/nodes/$(hostname)/lxc/9300.conf

pct config 9300

ก๊อปไฟล์ /tmp/8300.conf จากเครื่อง backup มาก่อนด้วย scp เปลี่ยน vmbr0 เป็นชื่อ bridge จริงของเครื่อง compute ตัวนั้น อย่าแก้ hwaddr กับ ip เพราะระบบอื่นที่คุยกับ CT ตัวนี้จำค่าพวกนั้นอยู่ และตัวจริงตายไปแล้วจึงไม่ชนกัน

ขั้นที่ 4 — เปิด แล้วเช็ก

pct start 9300
pct status 9300
pct exec 9300 -- systemctl is-system-running

ผ่านแล้วค่อยทำตัวถัดไป

ทำไมต้อง local-lvm ไม่ใช่ NFS อีกอัน เพราะทั้งหมดนี้เกิดจากการที่ shared storage ตาย การไปพึ่ง shared storage อีกก้อนคือแก้ปัญหาด้วยของชนิดเดียวกับที่เพิ่งพัง ดิสก์ในตัวเครื่อง compute เป็นที่เดียวที่ไม่ขึ้นกับใคร

ถ้ามี CT แค่ตัวสองตัวและเร่งมาก ปลุกที่เครื่อง backup ตรงๆ ก็ได้ (pct set 8300 --net0 ...bridge=vmbr0... แล้ว pct start 8300) เร็วกว่าเพราะไม่ต้องก๊อป แต่เป็นทางลัดสำหรับกรณีเล็กเท่านั้น ไม่ใช่แผนหลัก และต้องจำไว้ว่าตอนเอากลับจะคนละเส้นทางกัน

4

ระหว่างที่รันอยู่บนเครื่อง backup

ข้อมูลใหม่ของลูกค้าตอนนี้อยู่บน local-lvm ของเครื่อง compute แต่ละเครื่อง กระจายกันอยู่ ไม่ได้รวมที่เดียว ตัวเลขที่ต้องเฝ้าคือเนื้อที่ของแต่ละเครื่อง

# on each COMPUTE node running a 9xxx container
free -h
lvs pve
df -h /

RAM ใกล้เต็มแปลว่าย้ายมาเพิ่มไม่ได้แล้ว เนื้อที่ pool ใกล้เต็มอันตรายกว่ามาก: thin pool ที่เต็มไม่ได้แค่เขียนไม่ได้ มันทำให้ทั้ง pool กลายเป็น read-only ซึ่งลาก CT ทุกตัวบนเครื่องนั้นลงไปด้วย เหลือน้อยกว่า 20% เมื่อไหร่ให้หยุดย้ายเพิ่มทันที

ช่วงนี้ไม่มีสำเนาสำรองเลย ตัว 9xxx ที่รันอยู่คือข้อมูลชุดเดียวที่ใหม่ที่สุด ตัว 8xxx ที่เครื่อง backup หยุดอยู่ที่ข้อมูลตอนก่อนเครื่องตาย และไม่มีอะไรก๊อป 9xxx ไปไหนอีก ถ้ามี PBS ให้สั่ง backup ตัวสำคัญไว้ระหว่างนี้ — นี่คือช่วงที่เปราะที่สุดของทั้งเหตุการณ์

5

เครื่อง storage กลับมา — จุดอันตรายที่สุดอยู่ตรงนี้

อ่านให้จบก่อนเปิดเครื่อง storage พอมันบูตขึ้นมา cron จะเริ่มทำงานภายใน 15 นาที แล้วมันจะเห็นว่า “ดิสก์ตัวจริงกลับมาแล้ว” จึงก๊อปทับสำเนาตามหน้าที่ของมัน — ทับข้อมูลใหม่ที่ลูกค้าเพิ่งใช้มาหลายชั่วโมงด้วยข้อมูลเก่าตอนก่อนเครื่องตาย และกู้กลับไม่ได้

มีด่านกันอยู่ชั้นหนึ่งคือ guard R2 — มันจะไม่ยอมเขียนทับสำเนาที่กำลังรันอยู่ แต่พอไหร่ที่คุณสั่งปิดสำเนาเพื่อเอาข้อมูลกลับ ด่านนั้นก็หมดผล ไฟล์ PAUSE คือด่านที่เหลืออยู่

ลำดับที่ปลอดภัย

  1. เปิดเครื่อง storage ขึ้นมา แต่อย่าเพิ่งให้ cron ทำงาน 
    # on the STORAGE node, immediately after boot
systemctl stop cron
touch /root/ketsync/engines/tp/PAUSE
  2. เช็กว่าดิสก์และ storage กลับมาครบ 
    zpool status
pvesm status
./ketsync doctor
  3. เปิด cron กลับได้ ตอนนี้ PAUSE กันไว้แล้ว 
    systemctl start cron

ถ้าเผลอปล่อยให้ cron ทำงานไปก่อนแล้ว ให้รีบสร้าง PAUSE ทันที แล้วเช็กจาก log ว่ามีตัวไหนถูกก๊อปทับไปหรือยัง

grep -l 'GUARD R2' /root/ketsync/engines/tp/logs/replica-*.log
grep 'ok=' /root/ketsync/engines/tp/logs/replica-$(date +%F).log | tail -3

บรรทัดที่ขึ้น GUARD R2 คือตัวที่รอดเพราะยังรันอยู่ ตัวที่ขึ้นว่า ok ในรอบนั้นคือตัวที่ถูกทับไปแล้ว

6

เอาข้อมูลกลับเข้าตัวจริง

ข้อมูลใหม่อยู่ที่ 9xxx บนเครื่อง compute ไม่ใช่ที่ 8xxx บนเครื่อง backup คำสั่ง ketsync failback ดึงจากเครื่อง backup เท่านั้น ถ้าคุณย้ายไปรันที่ compute ตามข้อ 3 มันจะดึงข้อมูลเก่ามาทับของใหม่ คำสั่งที่ควรจะดึงจาก compute คือ ketsync recall ซึ่งยังไม่ได้สร้าง ตอนนี้จึงต้องทำด้วยมือ ตามหัวข้อย่อยแรกข้างล่าง

ก. ถ้าย้ายไปรันที่เครื่อง compute (ตามข้อ 3) — ทำด้วยมือ

# on the COMPUTE node - stop it first, this is the cutover
pct shutdown 9300
mkdir -p /mnt/dr-9300
mount /dev/pve/vm-9300-disk-0 /mnt/dr-9300

# on the STORAGE node - mount the production image, then pull INTO it
losetup -f --show /tank/hosting/images/300/vm-300-disk-0.raw
mkdir -p /mnt/back-300
mount /dev/loop0 /mnt/back-300
rsync -aHAX --numeric-ids --delete --info=progress2 \
  root@10.100.1.32:/mnt/dr-9300/ /mnt/back-300/
sync; umount /mnt/back-300; losetup -d /dev/loop0

ทิศทางสำคัญมาก: compute → storage ถ้าสลับข้าง ข้อมูลหลายชั่วโมงที่ลูกค้าเพิ่งใช้หายทันที และกู้ไม่ได้ ก่อนกด Enter ให้อ่านบรรทัด rsync อีกรอบว่าต้นทางคือเครื่อง compute จริง

เสร็จแล้วเปิดตัวจริง แล้วข้ามไปข้อ 7 ได้เลย

# on the COMPUTE node that owns CT 300
pct start 300

ข. ถ้าปลุกที่เครื่อง backup ตรงๆ (ทางลัดกรณีเล็ก) — ใช้คำสั่งได้

ทำจากเครื่อง storage ตัวโปรแกรมจะดึงข้อมูลจากสำเนาที่ยังรันอยู่บนเครื่อง backup กลับเข้าไฟล์ดิสก์ของตัวจริง ทำซ้ำได้เรื่อยๆ ระหว่างที่ลูกค้ายังใช้งานอยู่

  1. ดูสถานะก่อน ไม่แตะอะไร 
    # on the STORAGE node
cd /root/ketsync
./ketsync failback --list
  2. ดึงรอบแรก — รอบนี้นานสุดเพราะดึงเกือบทั้งก้อน ลูกค้ายังใช้งานได้ตามปกติ 
    ./ketsync failback --all
  3. ดึงซ้ำอีกสองสามรอบ ดูตัวเลข changed= ของแต่ละ CT พอมันไม่ลดลงแล้ว แปลว่าพร้อมตัดจริง
  4. ตัดจริง — ปิดสำเนาที่เครื่อง backup ก่อน แล้วดึงรอบสุดท้าย 
    # on the BACKUP node
pct shutdown 8105

# on the STORAGE node - PAUSE must already exist
./ketsync failback --ctid 105 --final

    ถ้าลืมสร้าง PAUSE มันจะปฏิเสธไม่ยอมทำ และบอกคำสั่งที่ต้องพิมพ์ให้ อย่าไปหาทางข้าม — ด่านนั้นกันเรื่องในข้อ 5 อยู่

  5. เปิดตัวจริงขึ้นมา 
    # on the COMPUTE node that owns this CT
pct start 105
7

คืนสภาพให้พร้อมสำหรับครั้งหน้า

ข้อนี้คนลืมบ่อยที่สุด และถ้าลืมแปลว่าครั้งหน้าจะไม่มีสำเนาให้ใช้

  1. ย้ายสายของสำเนากลับไป bridge ปิดตาย ทุกตัวที่ปลุกไว้ 
    # on the BACKUP node
pct set 8105 --net0 name=eth0,bridge=vmbr99,hwaddr=BC:24:11:AA:BB:CC,ip=10.100.2.55/24,gw=10.100.2.1

    ถ้าลืม ตัวโปรแกรมจะเตือนทุกรอบว่า WARN R11 — อย่าปล่อยผ่าน สำเนาที่ปิดอยู่แต่ยังต่อเน็ตจริง คือระเบิดเวลาสำหรับวันที่มีคนเผลอเปิดมัน

  2. เก็บกวาดตัวชั่วคราวบนเครื่อง compute ให้หมด ไม่งั้นครั้งหน้าเลข 9xxx จะชนกัน และเนื้อที่ local-lvm จะหายไปเฉยๆ 
    # on each COMPUTE node - check it is stopped and already pulled back first
pct status 9300
pct destroy 9300
  3. ลบ PAUSE เพื่อให้เริ่มก๊อปตามปกติอีกครั้ง 
    # on the STORAGE node
rm /root/ketsync/engines/tp/PAUSE
  4. ดูรอบแรกหลังเปิดใหม่ว่าเขียวจริง 
    ./ketsync replica --ctid 105
./ketsync status

จบแล้วจดไว้หน่อย ว่าติดตรงไหน ใช้เวลาเท่าไหร่ อะไรที่หน้านี้ไม่ได้บอก ครั้งหน้าจะได้ไม่ต้องคิดใหม่ และเอามาเติมในหน้านี้ได้เลย
