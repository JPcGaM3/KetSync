setup มีเครื่องอะไรบ้าง เตรียมก่อนเริ่ม cluster ssh storage bridge PBS ลงตัวโปรแกรม กรอก 3 ไฟล์ ตรวจ ซ้อม ตั้งเวลา พังตรงไหนทำไง

ติดตั้งระบบตั้งแต่ศูนย์

ทำตามทีละข้อ ข้อละไม่กี่นาที ทุกข้อมีวิธีเช็กว่าผ่านแล้วจริง — ไม่ต้องเข้าใจ Proxmox ลึกก็ทำได้

คำสั่งทุกอันบอกไว้ว่าพิมพ์บนเครื่องไหน ถ้าไม่ได้บอก แปลว่าเครื่อง storage
0

มีเครื่องอะไรบ้าง แต่ละเครื่องทำอะไร

ทั้งระบบมีเครื่อง 3 ประเภท คิดง่ายๆ แบบนี้ — เครื่องหนึ่งเก็บของ เครื่องหนึ่งใช้ของ และอีกเครื่องเก็บสำเนาไว้เผื่อฉุกเฉิน ทั้งหมดใช้เวลาตั้งประมาณครึ่งวัน ทำตามลำดับ อย่าข้าม เพราะข้อหลังๆ ใช้ของที่ข้อก่อนหน้าสร้างไว้

เรียกว่าตัวอย่าง IPทำอะไรต้องลงโปรแกรมนี้มั้ย
storage10.100.1.17 เก็บไฟล์ดิสก์ของ CT ทุกตัว และเป็นเครื่องที่สั่งงานทุกอย่างใช่ ที่นี่ที่เดียว
compute10.100.1.32, .33 เอาดิสก์จาก storage มา mount แล้วรัน CT จริงๆไม่ต้อง
backup10.100.1.9 เก็บสำเนา CT ที่ปิดอยู่ ไว้ใช้ตอนฉุกเฉินไม่ต้อง
          writes            mounts over NFS
  storage  ---------->  compute      (CT runs here)
     |
     | nightly copy
     v
  backup                             (a stopped copy waits here)

เครื่อง storage ไม่ได้อยู่ใน cluster ของ Proxmox ตั้งใจให้เป็นแบบนั้น มันเลยไม่รู้จักชื่อเครื่องอื่นเลย ทุกอย่างในระบบนี้จึงคุยกันด้วย IP ล้วน

1

เตรียมให้ครบก่อนเริ่ม

ถ้าขาดข้อใดข้อหนึ่ง ให้หยุดแล้วหาให้ครบก่อน อย่าเพิ่งทำต่อ — ตอนหลังจะหาสาเหตุยากกว่ามาก

ต้องมีเอาไปทำอะไร
IP ของทุกเครื่อง กับรหัส rootใส่ในตารางเดียวของระบบ
เครื่อง storage มีเนื้อที่ว่างพอดิสก์ของ CT ทุกตัวอยู่ที่นี่
เครื่อง backup มี ZFS pool ว่างเก็บสำเนา
สิทธิ์แก้ network บนเครื่อง backupสร้าง bridge ปิดตายให้สำเนา (ข้อ 5)
CT หรือ VM เล็กๆ อีกตัว ที่ไม่ได้อยู่ใน clusterเป็นเสียงโหวตที่ 3 ของ cluster (ข้อ 2)
ZFS pool อีกก้อนที่เครื่อง backupที่เก็บของ PBS แยกจากที่เก็บสำเนา (ข้อ 6)

คำเตือนข้อเดียวที่สำคัญที่สุดในหน้านี้ สำเนาที่เก็บไว้ที่เครื่อง backup ใช้ IP และ MAC เดียวกับตัวจริงเป๊ะ ถ้ามันออกเน็ตได้เมื่อไหร่ = มีเครื่องสองตัวใช้ IP เดียวกันพร้อมกัน ระบบลูกค้าจะพังทันที ข้อ 3 คือการกันเรื่องนี้ และตัวโปรแกรมจะไม่ยอมทำงานเลยถ้ายังกันไม่เรียบร้อย

2

รวมเครื่อง compute กับ backup เป็น cluster

cluster คือการทำให้เครื่องหลายตัวมองเห็น config ของกันและกัน มันทำให้ย้าย CT ข้ามเครื่องได้ และทำให้เครื่องหนึ่งตอบแทนอีกเครื่องได้ ซึ่งเครื่องมือชุดนี้ใช้อยู่หลายที่

เครื่อง storage ไม่ join cluster ตั้งใจให้อยู่นอก เพราะมันเป็นที่เก็บดิสก์ของทุกเครื่อง ถ้ามันร่วมโหวตด้วยแล้วมันล่ม cluster จะเสียเสียงโหวตไปพร้อมกับดิสก์ ข้ามข้อนี้ไปสำหรับเครื่อง storage

สร้าง cluster ที่เครื่อง compute เครื่องแรก

# on the FIRST compute node
pvecm create tomato

เอาเครื่องที่เหลือเข้ามา

# on EVERY other compute node, and on the backup node
pvecm add 10.100.1.32

ใส่ IP ของเครื่องแรกที่สร้าง cluster ไว้ มันจะถามรหัส root ของเครื่องนั้น

ตัวช่วยโหวต — ข้อนี้อย่าข้าม

cluster ตัดสินใจด้วยเสียงข้างมาก ถ้ามีเครื่องเลขคู่แล้วขาดไปครึ่งหนึ่ง จะไม่มีใครได้เสียงข้างมาก ทุกเครื่องจะหยุดเขียน config พร้อมกัน ตัวช่วยโหวตคือเสียงที่ 3 ที่ทำให้ไม่เกิดเรื่องนั้น

# on a small CT or VM that is NOT a cluster member
apt install -y corosync-qnetd

# on EVERY cluster member - not one may be skipped
apt install -y corosync-qdevice

# back on one cluster member, pointing at the voter
pvecm qdevice setup 10.100.1.40

เช็กว่าผ่าน

pvecm status

ต้องเห็นคำว่า Quorate: Yes และเห็นชื่อเครื่องครบทุกตัวที่ join ไป ถ้าตั้งตัวช่วยโหวตแล้วต้องเห็น Qdevice ในรายการด้วย

ถ้า qnetd ไม่ยอมขึ้นหลังติดตั้ง มักเป็นเรื่องสิทธิ์ไฟล์ แก้ด้วยสองบรรทัดนี้ บนเครื่องที่ลง qnetd

chown -R coroqnetd:coroqnetd /etc/corosync/qnetd
systemctl reset-failed corosync-qnetd && systemctl restart corosync-qnetd
3

ให้เครื่อง storage เข้าเครื่องอื่นได้โดยไม่ต้องถามรหัส

ระบบทำงานอัตโนมัติตอนกลางคืน จะมานั่งใส่รหัสไม่ได้ ทำครั้งเดียวจบ

# on the storage node
ssh-keygen -t ed25519 -N "" -f /root/.ssh/id_ed25519   # skip if you have one

ssh-copy-id root@10.100.1.9     # backup  - REQUIRED
ssh-copy-id root@10.100.1.32    # compute - one per node
ssh-copy-id root@10.100.1.33

เช็กว่าผ่าน

for ip in 10.100.1.9 10.100.1.32 10.100.1.33; do
  printf '%s ' "$ip"; ssh -o BatchMode=yes root@$ip true && echo OK || echo FAIL
done

ต้องขึ้น OK ทุกบรรทัด ถ้ามีบรรทัดไหนขึ้น FAIL ให้ทำ ssh-copy-id เครื่องนั้นซ้ำ

เส้นที่ขาดไม่ได้จริงๆ มีเส้นเดียว คือ storage ไปเครื่อง backup เพราะทั้ง config ของ CT ทุกตัวและตัวข้อมูลจริงวิ่งผ่านเส้นนี้ ส่วนเส้นไป compute ใช้ตอบคำถามเดียวว่า “CT ตัวจริงปิดอยู่รึยัง” ตอนจะเอาข้อมูลกลับ ไม่มีก็ยังก๊อปได้ปกติ แต่จะเอากลับไม่ได้

4

ตั้งชื่อ storage ให้ตรงกันสองฝั่ง

ตรงนี้คนพลาดบ่อยที่สุด กติกาคือ ชื่อต้องเหมือนกันเป๊ะ แต่ประเภทต้องต่างกัน เพราะ config ของ CT จำแค่ชื่อ พอ CT ย้ายไปรันที่ compute มันจะหาจากชื่อเดิม แล้วเจอของที่ mount ผ่าน NFS ที่เครื่องนั้นเอง

# on the storage node - the real files live here
pvesm add dir tank-hdd-nas --path /tank/hosting --is_mountpoint yes \
  --content images,rootdir

# on EVERY compute node - same id, reached over NFS
pvesm add nfs tank-hdd-nas --server 10.100.1.17 --export /tank/hosting \
  --content images,rootdir

เช็กว่าผ่าน

# must say "active" on BOTH sides, with the SAME id
pvesm status | grep tank-hdd-nas
ssh root@10.100.1.32 "pvesm status | grep tank-hdd-nas"

ห้ามให้ pool ไปอยู่บน disk ระบบ ถ้า dataset ไม่ได้ mount อยู่จริง Linux จะเห็นเป็นแค่โฟลเดอร์ว่างธรรมดา เขียนลงไปได้เรื่อยๆ จนดิสก์ระบบเต็มแล้วเครื่องล่ม ตัวโปรแกรมเช็กให้ก่อนเขียนทุกครั้ง (guard G1) แต่ตอนตั้งค่าก็ควรรู้ไว้

5

สร้าง bridge ปิดตาย ที่เครื่อง backup

สำเนาที่เก็บไว้ต้องต่ออยู่กับ “เกาะร้าง” — เป็น bridge ที่ไม่มีสายออกไปไหนเลย ถ้าวันหนึ่งมีคนเผลอเปิดสำเนาขึ้นมา มันจะออกเน็ตไม่ได้ ไม่ไปชนกับตัวจริง

# on the BACKUP node
cat >> /etc/network/interfaces <<'EOF'

auto vmbr99
iface vmbr99 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
EOF

ifup vmbr99

เช็กว่าผ่าน

# on the BACKUP node - the second line must print NOTHING
ip -br link show vmbr99
ls /sys/class/net/vmbr99/brif/

บรรทัดแรกต้องเห็น vmbr99 บรรทัดที่สองต้องว่างเปล่า ถ้ามีชื่อการ์ดโผล่มาแปลว่ามีสายต่ออยู่ — ต้องเอาออกก่อน ไม่งั้นโปรแกรมจะปฏิเสธไม่ยอมทำงาน (guard R9) ซึ่งถูกแล้ว อย่าไปปิด guard

6

ลง PBS ที่เครื่อง backup

PBS (Proxmox Backup Server) เป็นคนละเรื่องกับสำเนาที่ ct-replica ทำ และต้องมีทั้งคู่

ct-replicaPBS
ตอบคำถามว่าเครื่องพังตอนนี้ กู้กลับมาได้เร็วแค่ไหนไฟล์ที่ลบไปเมื่อวันอังคาร เอากลับมาได้มั้ย
เก็บอะไรสำเนาล่าสุดชุดเดียว พร้อมเปิดใช้ย้อนหลังหลายเดือน เปิดใช้ทันทีไม่ได้
บ่อยแค่ไหนทุก 15 นาทีคืนละครั้ง

ของสองอย่างนี้อยู่คนละ pool กันบนเครื่องเดียวกัน ตั้งใจให้ไม่แย่งหัวอ่านดิสก์กัน

ติดตั้ง

# on the BACKUP node
echo "deb http://download.proxmox.com/debian/pbs bookworm pbs-no-subscription"   > /etc/apt/sources.list.d/pbs.list
apt update && apt install -y proxmox-backup-server

ทำที่เก็บ แล้วทำผู้ใช้ให้ PVE เอาไว้ยิงเข้ามา

zfs create pbsstore-sas/chunks
proxmox-backup-manager datastore create main /pbsstore-sas/chunks

proxmox-backup-manager user create svc-pve@pbs --password 'CHANGE-ME'
proxmox-backup-manager acl update /datastore/main DatastoreBackup   --auth-id svc-pve@pbs

ผู้ใช้ตัวนี้ได้สิทธิ์แค่ “ฝากของ” ไม่ได้สิทธิ์ลบ ตั้งใจให้เป็นแบบนั้น — ถ้าเครื่องใน cluster ถูกเจาะ คนที่เข้ามาจะลบ backup ย้อนหลังทิ้งไม่ได้

เอาลายนิ้วมือของ certificate ไว้

proxmox-backup-manager cert info | grep Fingerprint

ก๊อปค่าที่ได้ไว้ ใช้ตอนต่อ PVE เข้ามาในขั้นถัดไป

ตั้งงานประจำ 3 อย่าง

proxmox-backup-manager prune-job create daily-prune   --store main --schedule "daily 05:00"   --keep-daily 14 --keep-weekly 8 --keep-monthly 6

proxmox-backup-manager datastore update main --gc-schedule "sun 06:00"

proxmox-backup-manager verify-job create weekly-verify   --store main --schedule "wed 22:00"   --ignore-verified true --outdated-after 30

prune คือตัดรุ่นเก่าทิ้งตามกฎ, GC คือคืนเนื้อที่จริง (prune อย่างเดียวไม่คืนเนื้อที่), verify คืออ่านทุก chunk มาเทียบ checksum ว่ายังอ่านได้อยู่จริง เวลาที่ตั้งไว้เลี่ยงไม่ให้ทับกับ backup job ตอนตี 2 ครึ่ง

ต่อ PBS เข้า cluster แล้วตั้ง backup ทุกคืน

# on ANY cluster member
pvesm add pbs pbs-main   --server 10.100.1.9 --datastore main   --username svc-pve@pbs --password 'CHANGE-ME'   --fingerprint 'PASTE-THE-FINGERPRINT-HERE'

pvesh create /cluster/backup   --all 1 --storage pbs-main --schedule "02:30"   --mode snapshot --mailnotification failure   --notes-template '{{guestname}}'

--all 1 แปลว่า guest ที่สร้างทีหลังจะเข้า job นี้เองอัตโนมัติ ไม่ต้องมานั่งเพิ่มทีละตัว ซึ่งเป็นวิธีที่ CT ตัวใหม่มักจะหลุดไม่ได้ backup

เช็กว่าผ่าน

# on any cluster member
pvesm status | grep pbs-main

# on the BACKUP node, after the first night
proxmox-backup-manager task list | head

ต้องขึ้น active และคืนถัดมาต้องเห็น task ที่จบด้วย OK

สำเนาที่ ct-replica ทำ ไม่ได้เข้า PBS คนละระบบกัน ตัวสำเนาปิดอยู่และไม่ได้อยู่ใน backup job — ถ้าอยากให้เข้าด้วยต้องเพิ่มเอง แต่ปกติไม่ต้อง เพราะตัวจริงเข้าอยู่แล้ว และสำเนาก็คือตัวจริงเมื่อ 15 นาทีก่อน

ลงตัวโปรแกรม

ลงที่เครื่อง storage เครื่องเดียว clone ครั้งเดียวได้ครบ ไม่ต้อง clone ซ้ำที่ไหนอีก

# on the storage node
git clone <this repo> /root/ketsync
cd /root/ketsync

cp ketsync.conf.sample  ketsync.conf
cp nodes.tsv.sample     nodes.tsv
cp fleet.tsv.sample     fleet.tsv
cp engines/tp/inventory-replica.sample.tsv engines/tp/inventory-replica.tsv

ไฟล์ที่ลงท้าย .sample คือตัวอย่าง ก๊อปแล้วตัดคำว่า sample ออกถึงใช้จริง ตัวอย่างจะถูกอัปเดตตอน git pull ส่วนตัวจริงของคุณจะไม่ถูกทับ

8

กรอก 3 ไฟล์ แค่นี้พอ

ไฟล์ที่ 1 — ketsync.conf: เครื่องนี้เป็นตัวหลักรึเปล่า

KS_ROLE=master
KS_MASTER_IP=10.100.1.17

เครื่อง storage คือ master เครื่อง backup ใส่ slave ตัวหลักเท่านั้นที่แก้ตารางได้ เครื่องอื่นรับมาอย่างเดียว ระบบไม่สลับให้เอง — คนเปลี่ยนเองตอนจำเป็น ตั้งใจให้เป็นแบบนั้น

ไฟล์ที่ 2 — nodes.tsv: ทุกเครื่องที่ระบบจะคุยด้วย

# ip	role
10.100.1.17	storage
10.100.1.9	backup
10.100.1.32	compute
10.100.1.33	compute

คั่นด้วยปุ่ม Tab ไม่ใช่เว้นวรรค ไม่มีคอลัมน์ชื่อเครื่องนะ ตั้งใจตัดออก ชื่อ node ของ Proxmox ระบบจะไปถามมาเองแล้วเก็บไว้ที่ nodes.map ซึ่งห้ามแก้มือ

ไฟล์ที่ 3 — engines/tp/inventory-replica.tsv: จะก๊อป CT ตัวไหนบ้าง

# src_ctid  [tgt_ctid]  [storage-assert]  [dest]
105                                       ssd
113                                       hdd

คอลัมน์แรกคือเลข CT ที่จะก๊อป ส่วน ssd กับ hdd คือจะเก็บลง pool ไหนที่เครื่อง backup เริ่มจากใส่แค่ตัวเดียวก่อนก็ได้ แล้วค่อยเพิ่มทีหลัง

ไม่ต้องกรอก fleet.tsv ตอนนี้ มันใช้ตอนเครื่อง storage ล่มแล้วต้องกระจาย CT ไปรันที่ compute ซึ่งยังทำไม่เสร็จ ปล่อยเป็นตัวอย่างไว้ก่อนได้

9

สั่งตรวจ แล้วแก้จนเขียวหมด

คำสั่งนี้อ่านอย่างเดียว ไม่แตะข้อมูลอะไรเลย สั่งซ้ำได้ไม่จำกัด

cd /root/ketsync
./ketsync doctor

มันจะไล่บอกทีละบรรทัดว่าอะไรผ่านอะไรไม่ผ่าน อ่านจากบนลงล่างแล้วแก้ทีละอัน ที่ต้องผ่านให้ได้ก่อนคือ ssh ไปเครื่อง backup เพราะชื่อ node ทุกตัวมาจากเส้นนั้นเส้นเดียว

== the backup node, which everything else leans on 10.100.1.9 ok (node bkp02)

บรรทัดที่เขียนว่า no ssh (expected) ตรงเครื่อง compute ไม่ใช่ปัญหา เป็นสถานะปกติ ไม่ต้องไปแก้

ทำจนคำสั่งจบแล้วไม่มีบรรทัดที่เป็นตัวใหญ่ทั้งคำอย่าง SSH FAILS หรือ NOT EXECUTABLE เหลืออยู่

10

ซ้อมก่อนของจริง

เลือก CT ที่ไม่สำคัญมาตัวเดียว แล้วสั่งแบบซ้อม มันจะเดินผ่านด่านตรวจครบทุกด่านเหมือนของจริง ต่างกันแค่ไม่เขียนอะไรลงดิสก์เลยสักไบต์

./ketsync replica --dry-run --ctid 105

อ่านผลว่ามันบอกจะทำอะไรบ้าง ถ้าดูแล้วตรงกับที่คิด ค่อยสั่งของจริงตัวเดียวก่อน

./ketsync replica --ctid 105

รอบแรกจะนานหน่อยเพราะก๊อปทั้งก้อน รอบต่อไปจะเร็วมากเพราะก๊อปเฉพาะส่วนที่เปลี่ยน พอตัวแรกผ่านแล้วค่อยสั่งทั้ง lane

./ketsync replica --storage tank-hdd-nas
11

ตั้งให้ทำเองทุก 15 นาที

ใส่ทีละ lane อย่าใส่พร้อมกันสองอัน ดูสักรอบสองรอบว่า log ออกมาปกติก่อนค่อยใส่ตัวถัดไป

crontab -e
*/15 * * * * /root/ketsync/engines/tp/ct-replica.sh --storage tank-hdd-nas
*/15 * * * * /root/ketsync/engines/tp/ct-replica.sh --storage tank-ssd-nas

เช็กว่าทำงานอยู่จริง

./ketsync status
tail -f /root/ketsync/logs/replica-*-$(date +%F).log

ใน cron ต้องใส่ path เต็มเสมอ และเป็น path ของ engine ตรงๆ (engines/tp/ct-replica.sh) ไม่ใช่ ./ketsync — เพราะ cron ไม่รู้ว่าตอนนี้อยู่โฟลเดอร์ไหน

12

เจอแบบนี้ แปลว่าอะไร ทำไง

โปรแกรมนี้เลือกที่จะ “ปฏิเสธเสียงดัง” มากกว่า “ทำต่อเงียบๆ” เจอ error ส่วนใหญ่จึงแปลว่ามันกันไว้ให้แล้ว ไม่ใช่ว่าพัง

ขึ้นว่าแปลว่าทำ
GUARD R9 ... HAS AN UPLINKbridge ที่เครื่อง backup ยังมีสายออกเน็ตกลับไปข้อ 4 เอาการ์ดออกจาก bridge
GUARD R3 ... not mountedpool ปลายทางไม่ได้ mount อยู่สั่ง zfs mount ที่เครื่อง backup ก่อน
GUARD R4เลข CT ปลายทางมีเจ้าของอยู่แล้วเปลี่ยนเลขในไฟล์ inventory-replica.tsv
GUARD B1 ... cannot reachssh ไปเครื่อง compute ไม่ได้กลับไปข้อ 2 ทำ ssh-copy-id เครื่องนั้น
storage 'xxx' is not activeชื่อ storage สองฝั่งไม่ตรง หรือยังไม่ได้เพิ่มกลับไปข้อ 3
inventory not foundยังไม่ได้ก๊อปไฟล์ตัวอย่างอ่านบรรทัดถัดไป มันบอกคำสั่งไว้ให้แล้ว
another run active - skipรอบก่อนยังไม่จบปกติ ไม่ต้องทำอะไร

ถ้าติดตรงไหนนานกว่า 10 นาที ให้สั่ง ./ketsync doctor อีกรอบ แล้วอ่านจากบนลงล่าง เกือบทุกครั้งคำตอบอยู่ในนั้น

13

ตรวจครั้งสุดท้าย

ตอบว่าใช่ได้ครบทุกข้อ ถือว่าติดตั้งเสร็จ

ข้อเช็กยังไง
cluster ครบและมีเสียงข้างมากpvecm status
ssh ไป backup ได้โดยไม่ถามรหัสssh root@10.100.1.9 true
storage ชื่อตรงกันสองฝั่งpvesm status | grep tank-
bridge ที่ backup ไม่มีสายต่อls /sys/class/net/vmbr99/brif/
PBS ต่อเข้า cluster แล้วpvesm status | grep pbs-main
doctor ไม่มีคำตัวใหญ่เหลือ./ketsync doctor
ซ้อม 1 ตัวผ่าน./ketsync replica --dry-run --ctid 105
ของจริง 1 ตัวผ่าน./ketsync replica --ctid 105
cron ใส่แล้ว ทีละ lanecrontab -l
เห็นผลใน status./ketsync status

สิ่งที่ควรทำเดือนละครั้ง สั่ง ./ketsync failback --list ดูเฉยๆ ไม่แตะอะไร มันจะบอกว่าถ้าวันนี้ต้องกู้จริง จะติดตรงไหนบ้าง — รู้วันธรรมดาดีกว่ารู้ตอนเกิดเหตุ
