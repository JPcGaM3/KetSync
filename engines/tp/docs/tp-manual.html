tp คืออะไร

tp คือคำสั่งเดียวที่มีเครื่องยนต์อยู่ข้างหลัง 3 ตัว แต่ละตัวทำหน้าที่คนละอย่าง ไม่มีตัวไหนเปิดหรือปิด CT ให้เอง — งานเปิดปิดเป็นงานของคน ทำเองทุกครั้ง

คำสั่งทำอะไร
tp migrate ย้าย CT ที่ยังอยู่บนเครื่องเก่านอกระบบ เข้ามาเป็นไฟล์ image ที่เครื่องนี้ ทำจนขึ้นเครื่องใหม่แล้วจบ ไม่ต้องทำอีก
tp replica ก๊อป image ที่ใช้งานจริงอยู่ตอนนี้ ไปเป็นสำเนาที่ปิดไว้บนเครื่อง {backup_node} ทำตลอดไป ทุก 15 นาที
tp failback วันที่ของจริงพังจนต้องเปิดสำเนาใช้แทน คำสั่งนี้พาข้อมูลที่สำเนาทำไว้ระหว่างนั้น กลับเข้า image ตัวจริง
tp status อ่านอย่างเดียว ไม่แตะอะไรทั้งนั้น — รอบล่าสุดของ CT แต่ละตัวเป็นยังไง
tp doctor อ่านอย่างเดียว — ถามคำถามที่ไม่มีใครจำได้ว่าต้องถาม เช่น CT ตัวไหนขึ้นระบบใหม่แล้วแต่ยังไม่มีสำเนา

เริ่มทุกครั้งเหมือนกันหมด คือเข้าเครื่องแล้วเข้าโฟลเดอร์ก่อน ทุกอย่างอยู่ในโฟลเดอร์นี้โฟลเดอร์เดียว

$ ssh root@{nfs_node}
$ cd /root/tp
$ ./tp                    # no arguments = the list of subcommands
$ ./tp version

อยากอ่านรายละเอียดของเครื่องยนต์ตัวไหน ใส่ --help ต่อท้ายได้ทุกตัว มันจะพิมพ์หัวไฟล์ของตัวเองออกมา รวมถึงความหมายของ exit code

$ ./tp migrate --help
$ ./tp replica --help
$ ./tp failback --help
1

นิสัยเดียวที่ต้องติด: ลองด้วย --dry-run ก่อนเสมอ

ข้อเดียวในคู่มือนี้ที่ถ้าจำได้ข้อเดียว ให้จำข้อนี้

เครื่องยนต์ทั้งสามตัวรับ --dry-run เหมือนกันหมด ใส่แล้วด่านตรวจทุกด่านยังทำงานครบ แต่ไม่มีการเขียนอะไรลงที่ไหนเลย ทั้งเครื่องนี้และเครื่องปลายทาง สิ่งที่ได้คือรายการว่าถ้าทำจริงจะเกิดอะไรขึ้น นี่คือวิธีมองก่อนลงมือ และเป็นคำสั่งแรกของทุกหัวข้อในคู่มือนี้

$ ./tp migrate  --ctid 251 --dry-run
$ ./tp replica  --dry-run
$ ./tp failback --all --dry-run

บรรทัดสุดท้ายของรอบ dry-run จะบอกไว้เองว่าไม่ได้เขียนอะไร ถ้าอ่านแล้วรายการตรงกับที่คิด ค่อยรันซ้ำโดยตัด --dry-run ออก

dry-run only - nothing was written, here or on the backup node

ข้อยกเว้นเดียว --stopped ของ migrate ใช้ร่วมกับ --dry-run ไม่ได้ เพราะมันต้องไปสั่ง pct mount บนเครื่องเก่า ซึ่งเป็นการเขียนบนเครื่องคนอื่น โปรแกรมจะปฏิเสธและบอกให้ dry-run รอบธรรมดาแทน

tp migrate — ดึง CT จากเครื่องเก่าเข้ามา

ใช้ตอนย้ายเข้าระบบใหม่ ทำทีเดียวจบต่อ CT หนึ่งตัว จบแล้วไม่ต้องทำอีก

โปรแกรมก๊อปข้อมูลของ CT ที่ยังเปิดใช้งานอยู่บนเครื่องเก่า เข้ามาเป็นไฟล์ image ที่เครื่องนี้ ลูกค้าไม่รู้สึกอะไรเลย แล้วมันสร้าง config ของ CT ตัวใหม่ให้บนเครื่องปลายทาง โดยไม่ใส่เน็ตและไม่ให้เปิดเอง ตัวจริงกับตัวใหม่จึงไม่มีวันชนกันบนเน็ตเวิร์ก

ไฟล์ที่มันอ่าน

ไฟล์คืออะไร
inventory-migrate.tsvรายชื่อ CT ที่จะย้าย 5 ช่อง เว้นวรรคหรือ tab ก็ได้ · ต้นแบบอยู่ที่ inventory-migrate.sample.tsv
ctmig.confความเร็วและตัวเลขปรับจูน ไม่ต้องแตะถ้ายังไม่มีปัญหา
done/<new_ctid>.doneไฟล์เปล่าที่คนสร้างเอง แปลว่า CT ตัวนี้ปิดงานแล้ว รอบต่อไปจะข้ามถาวร

ห้าช่องใน inventory-migrate.tsv เรียงแบบนี้ ไม่มีช่องไหนมีค่าเริ่มต้น ขาดช่องไหนแถวนั้นถูกข้ามพร้อมขึ้น ERROR

# old_node     old_ctid  new_ctid  new_node       storage
10.100.1.11    100       251       10.100.1.31    tank-hdd-nas
10.100.1.23    998       99200     10.100.1.18    tank-ssd-nas

ลองก่อน

$ ./tp migrate --ctid 251 --dry-run

ทำจริง

ทีละตัวใช้ --ctid (ใส่เลขตัวใหม่ ช่องที่ 3) · ทั้ง storage ใช้ --storage · ไม่ใส่อะไรเลยคือทุกแถว

$ ./tp migrate --ctid 251
$ ./tp migrate --storage tank-hdd-nas
$ ./tp migrate

รันซ้ำได้ตลอดและควรรันซ้ำ รอบหลังๆ ก๊อปเฉพาะส่วนที่เปลี่ยน ยิ่งรันบ่อยรอบสุดท้ายวัน go-live ยิ่งสั้น

อ่านผลยังไง

############################################################################## [251] CT 100 on 10.100.1.11 -> CT 251 on 10.100.1.31, storage 'tank-hdd-nas' [251] stats: files=1240 changed=812.4MiB wire=190.2MiB of 12.0GiB time=96s [251] create CT config on 10.100.1.31 (no net, onboot=0, stopped) ############################################################################## lane 'all' finished: ok=1 skipped=0 frozen=2 failed=0

ดูสองอย่าง: changed= ของแต่ละตัวว่าลดลงเรื่อยๆ ไหม และบรรทัดสรุปท้ายรอบต้องได้ failed=0 · frozen= คือจำนวนตัวที่ปิดงานไปแล้ว เป็นเรื่องปกติ

วัน go-live — งานที่โปรแกรมไม่ทำให้

ห้ามสลับลำดับข้อ 1 กับ 2

  1. ปิด CT ตัวเก่าด้วยมือ แล้วรอจนดับสนิท 
    $ ssh root@10.100.1.11 pct shutdown 100
$ ssh root@10.100.1.11 pct status 100      # must say: status: stopped
  2. รอบสุดท้าย เก็บข้อมูลช่วงท้ายที่ยังไม่ได้ก๊อป ใช้กับทีละตัวเท่านั้น 
    $ ./tp migrate --ctid 251 --stopped
  3. ปิดงาน CT ตัวนี้ ไม่ทำข้อนี้ รอบถัดไปจะก๊อปทับตัวใหม่ที่กำลังใช้งานอยู่ 
    $ touch done/251.done
  4. เติมเน็ตแล้วค่อยสตาร์ท ไอพีข้างล่างเป็นตัวอย่าง แก้ให้ตรงของจริง 
    $ ssh root@10.100.1.31 pct set 251 -net0 name=eth0,bridge=vmbr0,ip=10.100.1.51/24,gw=10.100.1.1
$ ssh root@10.100.1.31 pct start 251
  5. เพิ่มตัวนี้เข้ารายชื่อสำเนา ขึ้นระบบใหม่แล้วแต่ยังไม่มีสำเนา คือช่องโหว่ที่ tp doctor ตามหาอยู่ (ข้อ 3)

เสร็จแล้วหน้าตาแบบนี้ รอบสุดท้ายได้ failed=0 · มีไฟล์ done/251.done · CT ตัวใหม่เปิดใช้งานอยู่ · รอบถัดๆ ไปตัวนี้ไปโผล่ที่ช่อง frozen แทน

ถ้าตัวใหม่มีปัญหา ตัวเก่ายังอยู่ครบทุกอย่าง โปรแกรมนี้อ่านอย่างเดียวไม่เคยแตะมัน เปิดกลับได้เลย แล้วลบ marker ทิ้งเพื่อให้ระบบกลับมา sync ตัวนี้ต่อ

$ ssh root@10.100.1.31 pct stop 251        # stop the new one first
$ ssh root@10.100.1.11 pct start 100       # the old CT was never touched
$ rm done/251.done
3

tp replica — สำเนากันพัง ทุก 15 นาที ตลอดไป

ตั้งครั้งเดียวแล้วปล่อยให้ cron ทำ ปกติไม่ต้องพิมพ์เองเลย

ทุก 15 นาที โปรแกรมก๊อปข้อมูลของ CT ที่อยู่ในรายชื่อ ไปเป็นสำเนาบนเครื่อง {backup_node} สำเนาทุกตัวปิดไว้ตลอด เลขของสำเนาคือเลขต้นทางบวก 8000 (เช่น CT 105 → สำเนา 8105) สำเนาถือ IP และ MAC ของตัวจริงไว้เป๊ะๆ แต่ไปนั่งอยู่บนสะพานลอยที่ไม่ต่อสายออกไปไหน จึงชนกับตัวจริงไม่ได้

ไฟล์ที่มันอ่าน

ไฟล์คืออะไร
inventory-replica.tsv รายชื่อ CT ที่จะทำสำเนา · คนละไฟล์กับของ migrate ช่องคนละความหมายกันเลย · ต้นแบบอยู่ที่ inventory-replica.sample.tsv
ctrep.confเครื่อง backup, pool ปลายทาง, ความเร็ว, ชื่อสะพานลอย
PAUSEถ้ามีไฟล์นี้ = หยุดทำสำเนาทั้งฟลีต ใช้ตอน failback เท่านั้น เสร็จแล้วต้องลบ

แถวหนึ่งบรรทัด ช่องแรกคือเลข CT ต้นทาง ช่องหลังใส่ได้ตามต้องการไม่สนลำดับ: ตัวเลข = เลขสำเนาที่อยากกำหนดเอง, hdd หรือ ssd = pool ปลายทาง, ที่เหลือ = ชื่อ storage ต้นทางไว้กันย้ายมั่ว

105   ssd
112   9112
113   8113   tank-ssd-nas   ssd
114                       # -> copy 8114, default pool

ลองก่อน

$ ./tp replica --dry-run
$ ./tp replica --ctid 105 --dry-run

ทำจริง

รันมือเฉพาะตอนเพิ่ม CT ใหม่เข้ารายชื่อ หรือตอนตามแก้ตัวที่ค้าง นอกนั้นปล่อย cron

$ ./tp replica --ctid 105
$ ./tp replica --storage tank-hdd-nas
$ ./tp replica

cron หนึ่งบรรทัดต่อหนึ่ง storage

แยกไฟล์ตาม storage ต้นทาง เพื่อให้สองสายวิ่งพร้อมกันได้โดยไม่แย่งแบนด์วิดท์กัน ตัว CT ไม่ได้เลือกสายเอง — มันถูกจัดสายตาม storage ที่ข้อมูลมันนอนอยู่จริง

$ echo '*/15 * * * * root /root/tp/tp replica --storage tank-hdd-nas >/dev/null 2>&1' > /etc/cron.d/ct-replica-hdd
$ echo '*/15 * * * * root /root/tp/tp replica --storage tank-ssd-nas >/dev/null 2>&1' > /etc/cron.d/ct-replica-ssd

ตั้ง 2 สายแล้วต้องบอกมันด้วย เปิด ctrep.conf แล้วตั้ง LANES=2 เพดานความเร็วรวมจะได้ยังคุมอยู่ · ถ้าไฟล์ cron เดิมชี้ไปที่ /root/tp/ct-replica.sh ก็ถูกเหมือนกัน tp replica ส่งต่อไปให้ไฟล์นั้นตรงๆ ไม่ต่างกันเลย

อ่านผลยังไง

R9: vmbr99 ok on {backup_node} (no uplink) [105] stats: files=318 changed=214.6MiB wire=61.2MiB time=44s avg=1.3MiB/s [105] OK -> 8105 (rc=0) ############################################################################## === lane 'tank-hdd-nas' finished: ok=6 skipped=0 failed=0 ===

เสร็จแล้วหน้าตาแบบนี้ ทุกรอบจบด้วย failed=0 · สำเนาทุกตัวยังปิดอยู่ · tp doctor ไม่บ่นว่ามี CT ไหนไม่มีสำเนา และไม่มี PAUSE ค้าง

4

tp failback — พาข้อมูลกลับหลังวันที่พัง

ใช้เฉพาะตอนที่สำเนาถูกเปิดขึ้นมารับงานแทนตัวจริงไปแล้ว และตอนนี้ข้อมูลใหม่ที่สุดอยู่ที่สำเนา

มันคือ replica ที่วิ่งย้อนทาง ดึงข้อมูลจากสำเนาบนเครื่อง {backup_node} กลับเข้า image ตัวจริงที่เครื่องนี้ และเป็นทางเดียวที่ความผิดพลาดจะทำลายข้อมูลของตัวจริง ไม่ใช่สำเนา ด่านตรวจของมันจึงปฏิเสธอย่างเดียว ไม่มีเตือนแล้วทำต่อ มันอ่าน inventory-replica.tsv กับ ctrep.conf ชุดเดียวกับ replica ไม่ต้องตั้งค่าซ้ำ

ข้อ 0 ทำวันธรรมดา ไม่ใช่วันเกิดเหตุ

--list อ่านอย่างเดียว มันไล่ถามทุกเครื่องว่า CT ตัวจริงอยู่ไหนและดับหรือยัง — ถามผ่าน ssh ด้วยชื่อเครื่อง เครื่องนี้ตั้งใจให้อยู่นอกคลัสเตอร์ มันจึงไม่ได้ชื่อและกุญแจมาเองฟรีๆ วันที่รู้ว่า ssh ไม่เคยถูกตั้ง ต้องไม่ใช่วันที่สำเนากำลังรับลูกค้าอยู่

$ ./tp failback --list
CT COPY DEST PROD-NODE PROD COPY-STATE IMAGE 105 8105 hdd pve-a stopped running /tank/hosting/images/105/vm-105-disk-0.raw 112 9112 ssd pve-b stopped running /tank/fast/images/112/vm-112-disk-0.raw

ลองก่อน

$ ./tp failback --all --dry-run

ขั้นที่ 1 — presync ตอนสำเนายังรับงานอยู่

รันได้บ่อยเท่าที่อยากรัน ระหว่างที่ลูกค้ายังใช้สำเนาอยู่ตามปกติ แต่ละรอบขนเฉพาะส่วนที่เปลี่ยน ดูเลข changed= ของแต่ละตัว รันซ้ำจนมันไม่ลดแล้ว นั่นคือพร้อมตัดจริง

$ ./tp failback --all
$ ./tp failback --ctid 105
$ ./tp failback --all --dest ssd           # only copies on that backup pool
[105] stats: files=44 changed=18.2MiB wire=6.1MiB time=7s [105] OK <= 8105 (rc=0) ############################################################################## === failback finished: ok=6 skipped=0 failed=0 === presync done. run it again until 'changed=' stops shrinking, then cut over:

ขั้นนี้สำเนาต้องเปิดอยู่ ตราบใดที่สำเนายังรัน ตัวทำสำเนาจะข้ามมันเอง ข้อมูลใหม่จึงปลอดภัย ถ้าปิดสำเนาไปแล้วโดยยังไม่ได้ตั้ง PAUSE โปรแกรมจะปฏิเสธและบอกให้ไปใช้ --final แทน

ขั้นที่ 2 — รอบสุดท้าย ต้องมี PAUSE ก่อน

ทำสามข้อนี้ตามลำดับ ห้ามข้ามข้อแรก ไฟล์ PAUSE คือสิ่งเดียวที่กันไม่ให้ cron รอบถัดไปเอาข้อมูลเก่าทับสำเนา ทันทีที่สำเนาถูกปิด

  1. หยุดการทำสำเนาทั้งฟลีตก่อน 
    $ touch /root/tp/PAUSE
  2. ปิดสำเนาทุกตัวที่กำลังรับงานอยู่ ใส่เลขสำเนา ไม่ใช่เลขตัวจริง 
    $ ssh root@{backup_node} pct shutdown 8105
$ ssh root@{backup_node} pct status 8105   # must say: status: stopped
  3. รอบสุดท้าย 
    $ ./tp failback --all --final

ก่อนเขียนทับ image ตัวจริง มันถ่ายรูปเก็บไว้ให้เองหนึ่งรูป ชื่อขึ้นต้นด้วย ctback- ในบรรทัด safety net: ของ log · ถ้าจะย้อน ให้ก๊อปไฟล์ออกมาจากรูปนั้น ห้ามสั่งย้อนทั้ง dataset เพราะจะลากทุก CT ที่อยู่ด้วยกันย้อนไปหมด

ขั้นที่ 3 — งานที่โปรแกรมไม่ยอมทำให้

พอรอบ --final จบ มันจะพิมพ์รายการนี้ออกมาเองพร้อมเลข CT จริง สี่ข้อนี้เป็นงานคนล้วนๆ ตั้งใจให้เป็นแบบนั้น

next, by hand, for: 105 112 1) start each production CT: ssh root@<its node> pct start <ctid> 2) put each copy's network back on the mock bridge (ct-replica R11 nags until you do) 3) rm /root/tp/PAUSE 4) /root/tp/ct-replica.sh # first round back, must end failed=0
$ ssh root@pve-a pct start 105
$ rm /root/tp/PAUSE
$ ./tp replica

เสร็จแล้วหน้าตาแบบนี้ CT ตัวจริงเปิดรับงานอยู่ · สำเนากลับไปปิดและกลับไปอยู่บนสะพานลอยตามเดิม · ไฟล์ PAUSE หายไปแล้ว · tp replica รอบแรกหลังกลับมาจบด้วย failed=0

ลืมลบ PAUSE คือความเงียบที่แพงที่สุดในระบบนี้ สำเนาทุกตัวจะหยุดอัปเดตโดยไม่มีอะไรร้อง รู้ตัวอีกทีคือวันที่ต้องใช้มัน · tp doctor ถามข้อนี้ให้ทุกครั้งที่รัน

อ่านผลการรันหนึ่งรอบ

ทุกเครื่องยนต์จบด้วยบรรทัดสรุปหน้าตาเดียวกัน อ่านบรรทัดเดียวนี้ก่อนเสมอ

=== lane 'tank-hdd-nas' finished: ok=6 skipped=1 failed=0 ===
คำแปลว่า
ok=สำเร็จกี่ตัว ข้อมูลถึงปลายทางครบ
skipped=ข้ามกี่ตัว — ด่านตรวจปฏิเสธไว้ ไม่ใช่ความเสียหาย แต่แปลว่าตัวนั้นยังไม่ได้ก๊อป ต้องไปดูว่าทำไม
failed=พังกี่ตัว ต้องมี 0 เสมอ ไม่เป็น 0 คือมีงานให้ทำ
frozen=เฉพาะ migrate — ปิดงานไปแล้วกี่ตัว (มีไฟล์ใน done/) เป็นเรื่องปกติ

ถ้ามีตัวพัง บรรทัดถัดมาจะบอกเลขตัวที่ต้องไปดู ตามด้วยเลขนั้นไปหาใน log

NEEDS ATTENTION -> CT: 112 118

log ของสายนั้นอยู่ไหน

อยู่ในโฟลเดอร์ logs/ ข้างๆ โปรแกรม แยกไฟล์ตามสายและตามวัน ชื่อสายคือชื่อ storage ที่ใส่หลัง --storage หรือคำว่า all ถ้าไม่ได้ใส่

เครื่องยนต์ไฟล์ log
tp migratelogs/ctmig-<lane>-<date>.log
tp replicalogs/replica-<lane>-<date>.log
tp failbacklogs/failback-<date>.log
$ ls -lt logs/ | head
$ grep -n '\[112\]' logs/replica-tank-hdd-nas-2026-08-11.log
$ tail -f logs/replica-all-2026-08-11.log

แถวคั่นยาวๆ ในไฟล์ log ไม่ใช่ error มันคือเส้นแบ่งระหว่าง CT ตัวหนึ่งกับตัวถัดไป มีไว้ให้กวาดตาหาตัวที่พังเจอเร็วๆ ตอนตีสอง

ตัวเลข rc ท้ายบรรทัด

คือรหัสของ rsync ตัวขนข้อมูล จำสี่ตัวนี้พอ

rcแปลว่าทำยังไงต่อ
0สำเร็จไม่ต้องทำอะไร
24สำเร็จเหมือนกัน — มีไฟล์หายไประหว่างก๊อป ซึ่งเป็นเรื่องปกติมากของ CT ที่ยังเปิดใช้งานอยู่ไม่ต้องทำอะไร
23ก๊อปได้ไม่ครบเจอครั้งแรก ปกติเป็นอาการชั่วคราวจากการอ่านแบบไม่แตะต้นฉบับ ปล่อยให้รอบหน้าเก็บ · เจอสองรอบติดกันที่ CT ตัวเดิม ไม่ใช่เรื่องชั่วคราวแล้ว ไฟล์ image น่าจะเสีย ให้ปิด CT ตัวนั้นก่อน แล้วตรวจแบบอ่านอย่างเดียว
11พื้นที่ใน image เต็มโปรแกรมขยาย image ให้เอง 5% แล้วลองใหม่ สามครั้ง ถ้ายังไม่พอมันจะบอกดังๆ · ขยายแล้วเลขขนาดใน config ของ CT จะไม่ตรง ต้องไปแก้บรรทัด rootfs เองตอนว่าง

คำสั่งตรวจ image ตอนเจอ 23 สองรอบติด — CT ต้องดับก่อน เท่านั้น ชื่อไฟล์ image เอามาจากบรรทัด ERROR ใน log ได้ตรงๆ

$ pvesm path tank-hdd-nas:105/vm-105-disk-0.raw    # where the image really is
$ e2fsck -fn /tank/hosting/images/105/vm-105-disk-0.raw   # look only, changes nothing

คำปฏิเสธที่จะได้เจอจริงๆ และวิธีแก้

โปรแกรมปฏิเสธเพราะมันเห็นอะไรบางอย่างที่ผิด ไม่ใช่เพราะมันเสีย อ่านคำที่มันพิมพ์ แล้วแก้ตามนี้

GUARD B1: cannot reach <node>

[105] GUARD B1: cannot reach pve-a to check the CT - 'unverified' is not 'stopped'

failback ต้องถามเครื่องปลายทางให้ได้ว่า CT ตัวจริงดับแล้วจริงไหม ถามไม่ได้ = ไม่นับว่าดับ = ไม่ยอมเขียน เพราะถ้ามันยังรันอยู่ การเขียนลงไปจะทำลาย CT ของลูกค้าตัวเป็นๆ · เครื่องนี้ต้อง ssh เป็น root ไปทุกเครื่องที่รัน CT ได้ โดยเรียกด้วยชื่อเครื่อง · ตรวจวันนี้เลย อย่ารอวันเกิดเหตุ

$ ./tp failback --list                      # it names every node it could not reach
$ ssh -o BatchMode=yes root@pve-a true      # must print nothing and exit 0

ถ้ามันบอกว่าหาชื่อเครื่องไม่เจอ ให้เพิ่มชื่อกับ IP ลงใน /etc/hosts ของเครื่องนี้ · ถ้ามันถามรหัสผ่าน แปลว่ายังไม่ได้ส่งกุญแจไป

$ ssh-copy-id root@pve-a

ไม่มีไฟล์รายชื่อ

ERROR: no inventory at /root/tp/inventory-replica.tsv - NOTHING was run this file is NOT ct-migrate's inventory-migrate.tsv; the columns differ

สองไฟล์นี้คนละไฟล์กัน ช่องคนละความหมาย ห้ามเอามาใช้แทนกันเด็ดขาด เริ่มจากไฟล์ต้นแบบ

$ cp inventory-replica.sample.tsv inventory-replica.tsv    # replica + failback
$ cp inventory-migrate.sample.tsv inventory-migrate.tsv                    # migrate only

ใส่ตัวกรองแล้วไม่ตรงกับใครเลย

ERROR: no CT matched --storage tank-sdd-nas - nothing was replicated

พิมพ์ชื่อผิดหนึ่งตัวอักษร งานเลยไม่ถูกทำเลยแม้แต่ตัวเดียว โปรแกรมจงใจให้จบแบบไม่สำเร็จ เพราะถ้าจบแบบสำเร็จทั้งที่ไม่ได้ทำอะไร cron จะดูเขียวสนิทได้เป็นเดือนโดยไม่มีสำเนาเลยสักตัว · เทียบชื่อกับไฟล์รายชื่อ

$ awk '$1!~/^#/ && NF>=5 {print $3, $5}' inventory-migrate.tsv
$ pvesm status

GUARD B7: could not snapshot

[110] GUARD B7: could not snapshot tank/hosting - NOTHING was written for CT 110

รอบ --final เขียนทับ image ตัวจริง รูปที่ถ่ายไว้ก่อนเขียนคือทางกลับทางเดียวที่มี ถ่ายไม่ได้ = ไม่ยอมเขียน สาเหตุปกติคือ pool เต็ม

$ zpool list
$ zfs list -t snapshot tank/hosting

แก้ไม่ได้จริงๆ และยอมรับความเสี่ยงว่าจะไม่มีทางย้อนกลับ ต้องพิมพ์ประโยคนี้เองด้วยมือ ไม่มีทางไปโดนเข้าโดยบังเอิญ

$ ./tp failback --ctid 110 --final --no-snapshot

GUARD R9: สะพานลอยมีสายต่อออก

GUARD R9: vmbr99 on {backup_node} HAS AN UPLINK - NOTHING was run port 'eno2' is a physical NIC or a bond ANY COPY ALREADY RUNNING ON IT MAY BE COLLIDING WITH PRODUCTION NOW.

สำเนาถือ IP และ MAC ของตัวจริง สิ่งเดียวที่ทำให้เรื่องนี้ปลอดภัยคือสะพาน vmbr99 บนเครื่อง {backup_node} ต่อไปไหนไม่ได้เลย วินาทีที่มีคนเสียบสายจริงเข้าไป สำเนาทุกตัวบนนั้นกลายเป็นเครื่องปลอมที่ชนกับของจริงทันที มันจึงหยุดทั้งรอบ ไม่ทำอะไรต่อ · นี่คืออันเดียวในหน้านี้ที่ต้องรีบภายในนาทีนี้ ไปดูว่ามีสำเนาตัวไหนเปิดอยู่บนนั้นแล้วหรือยัง

$ ssh root@{backup_node} 'pct list'
$ ssh root@{backup_node} 'ls /sys/class/net/vmbr99/brif/'

อีกแบบคือมันบอกว่าไม่มีสะพานนี้อยู่เลย แปลว่ายังไม่ได้สร้าง ดูวิธีสร้างใน ct-replica-setup.html
