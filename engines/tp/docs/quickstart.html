Quickstart: ย้าย CT เข้า NFS
ตั้งแต่ศูนย์จนขึ้นเครื่องใหม่

คู่มือฉบับทำตามได้เลยสำหรับคนเพิ่งเริ่มใช้ — ติดตั้ง, ตั้งค่า, sync, และวันย้ายจริง · รายละเอียดลึกกว่านี้อยู่ใน manual.html

รันบน: storage-node เวลา setup: ~15 นาที downtime ตอน sync: 0
00

มันคืออะไร ทำงานยังไง

โปรแกรมตัวเดียวรันบน storage-node ทำ 2 อย่างต่อ CT หนึ่งตัว

  1. ก๊อปข้อมูล: ดึง rootfs ของ CT ที่กำลังรันบนเครื่องเก่า (ผ่าน ssh) มาเก็บเป็นไฟล์ raw บน storage ของเครื่องนี้ — ตัวเก่ายังทำงานต่อ ไม่มี downtime และรันซ้ำได้เรื่อยๆ รอบถัดไปส่งแค่ส่วนที่เปลี่ยน
  2. เตรียม CT ปลายทาง: เขียน config บนเครื่องใหม่ให้เหมือนตัวเก่า แต่ ไม่มี network + onboot=0 + ไม่สั่งสตาร์ท — วัน go-live เราค่อยเติมเน็ตแล้วกดสตาร์ทเอง

คำสั่งที่ใช้จริงคือ ./tp migrate ตัวเดียว ส่วน ./ct-migrate.sh คือโปรแกรมข้างในที่ tp เรียกให้ พิมพ์แบบไหนก็ได้ผลเหมือนกันเป๊ะ ทั้งคู่รับ option ชุดเดียวกัน

cd /root/tp
./tp migrate            # the normal way to run it
./ct-migrate.sh         # the same run: tp only hands the arguments to the engine
ภาพรวม: เครื่องเก่า (CT รันอยู่) —ssh/rsync→ storage-node (ไฟล์ raw บน ZFS, export NFS) —NFS→ เครื่องใหม่ (boot CT จาก NFS)
โปรแกรมไม่เคยเปิดหรือปิด CT ให้เอง การปิดตัวเก่า เติมเน็ต และกดสตาร์ทตัวใหม่ เราทำเองด้วยมือทั้งหมด ตั้งใจให้เป็นแบบนั้น
01

ติดตั้ง — โฟลเดอร์เดียวจบ (บน storage-node)

ทุกอย่างอยู่ในโฟลเดอร์เดียวกัน และโปรแกรมหาไฟล์ของตัวเองจากตำแหน่งที่สคริปต์วางอยู่ ไม่มี path แบบตายตัวในไฟล์เลย ย้ายโฟลเดอร์ไปไหน ทุกอย่างตามไปด้วย

git clone <repo> /root/tp && cd /root/tp
cp inventory.sample.tsv inventory.tsv
./tp doctor             # says what is not wired up yet
สิ่งที่อยู่ในโฟลเดอร์: tp (คำสั่งหน้าบ้าน) · ct-migrate.sh (ตัวโปรแกรม ห้ามแก้) · ctmig.conf (ตั้งความเร็ว ข้อ 05) · inventory.tsv (รายชื่อ CT ข้อ 04) · logs/ state/ done/ (โปรแกรมสร้างเอง)
02

SSH key ไปทุกเครื่อง (ครั้งเดียว)

โปรแกรม ssh แบบไม่ถามรหัส (จำเป็นสำหรับ cron) — ทำ key จาก storage-node ไปทุกเครื่องเก่าและเครื่องใหม่

# create a key once (skip if you already have one)
[ -f /root/.ssh/id_ed25519 ] || ssh-keygen -t ed25519 -N '' -f /root/.ssh/id_ed25519

# push it to every node (enter the password one last time per node)
for h in 10.100.1.11 10.100.1.12 10.100.1.31 10.100.1.32 ; do ssh-copy-id root@$h ; done

# TEST: each must print a hostname WITHOUT asking for a password
for h in 10.100.1.11 10.100.1.12 10.100.1.31 10.100.1.32 ; do ssh -o BatchMode=yes root@$h hostname ; done
ถ้าข้าม step นี้: log จะขึ้น SSH to <ip> FAILED (key not set up / host down) แล้ว CT ตัวนั้นถูกข้าม

เสริมความปลอดภัย (แนะนำ)

บนเครื่องปลายทางแต่ละตัว จำกัดให้ key นี้ใช้ได้จาก storage-node เท่านั้น — เติมข้างหน้าบรรทัด key ใน /root/.ssh/authorized_keys

from="10.100.1.20" ssh-ed25519 AAAA... root@pve-r740xd
03

เช็ค storage ทั้งสองฝั่ง

ชื่อ storage ต้องมีอยู่ทั้งสองฝั่ง และต้องชื่อเดียวกัน แต่คนละชนิด ฝั่งนี้เป็น dir ฝั่งเครื่องใหม่เป็น nfs

บน storage-node — dir storage ชี้ dataset จริง

pvesm add dir tank-hdd-nas --path /tank/hosting --is_mountpoint yes --content images,rootdir
pvesm status --storage tank-hdd-nas        # must be active

ตัวเลือก --is_mountpoint yes สำคัญ ถ้า dataset ยังไม่ถูก mount แล้วเราไม่ได้บอกไว้ ข้อมูลจะไหลลงดิสก์ระบบของเครื่องจนเต็มโดยไม่มีอะไรฟ้อง โปรแกรมเช็คข้อนี้ให้ก่อนเสมอ และถ้าผิดจะขึ้น GUARD G1 แล้วไม่ยอมเขียนอะไรเลย

บนเครื่องใหม่ (ทุกตัวที่จะ boot CT) — mount ตัวเดียวกันผ่าน NFS

pvesm add nfs tank-hdd-nas --server 10.100.1.20 --export /tank/hosting --content images,rootdir
pvesm status --storage tank-hdd-nas        # active on this node too
ชื่อไม่ตรงกัน = CT start ไม่ขึ้น เพราะ config ของ CT ชี้ storage ด้วยชื่อ ถ้าฝั่งเครื่องใหม่ไม่มีชื่อนี้ โปรแกรมจะข้าม CT ตัวนั้นพร้อมบอกว่า storage ... is not active
04

เขียน inventory.tsv

ไฟล์บอกว่า "ย้ายตัวไหน ไปไหน" — 1 บรรทัดต่อ 1 CT, 5 ช่องครบทุกบรรทัด คั่นด้วย space หรือ tab ก็ได้

# old_node    old_ctid  new_ctid  new_node      storage
10.100.1.11   100       251       10.100.1.31   tank-hdd-nas
10.100.1.12   100       253       10.100.1.32   tank-ssd-nas
# one line per CT; a line starting with # is ignored
ช่องความหมายตัวอย่างเช็คยังไง
1old_node10.100.1.11ไอพีเครื่องเก่า — ssh ถึงได้ (ข้อ 02)
2old_ctid100เลข CT บนเครื่องเก่า ต้อง running — pct list
3new_ctid251เลข CT ที่จะใช้บนเครื่องใหม่ ต้องว่าง — pct list
4new_node10.100.1.31ไอพีเครื่องใหม่ที่จะ boot ตัวนี้
5storagetank-hdd-nasชื่อ storage ที่ทำไว้ในข้อ 03
ช่อง 4 และช่อง 5 ไม่มีค่าเริ่มต้น โปรแกรมจะไม่เดาให้เด็ดขาด บรรทัดที่ขาดช่องใดช่องหนึ่งจะขึ้น ERROR: row is incomplete แล้วข้ามบรรทัดนั้น (บรรทัดอื่นยังทำงานปกติ) การเดาแปลว่า CT อาจไปโผล่ผิดเครื่องหรือผิด pool
เลขช่องที่ 3 ห้ามซ้ำกันเด็ดขาด ถ้าซ้ำ โปรแกรมจะไม่ทำอะไรเลยทั้งไฟล์ แล้วบอกว่าซ้ำที่บรรทัดไหน ส่วนเลขช่องที่ 2 ซ้ำได้ถ้าอยู่คนละเครื่อง เป็นเรื่องปกติเพราะทุกเครื่องเก่าเริ่มนับที่ 100 เหมือนกัน

ไม่ต้องใส่ขนาดดิสก์และไม่ต้องใส่ไอพีของ CT ขนาดคำนวณจากตัวเก่าให้อัตโนมัติ ส่วน network จะไม่ถูกเขียนลง config เลย ไปเติมเองวัน go-live (ข้อ 08)

ถ้ามีไฟล์เก่าที่ยังเป็น 4 ช่อง เติมช่องที่ 5 ให้ทั้งไฟล์ได้ด้วยคำสั่งนี้ (มันจะให้ดูผลก่อนแล้วถามยืนยัน และเก็บไฟล์เดิมเป็น .bak ให้)

tools/add-storage-column.sh tank-hdd-nas
05

ตั้งความเร็วใน ctmig.conf

การตั้งค่าทั้งหมดอยู่ใน ctmig.conf ซึ่งแยกออกมาจากตัวโปรแกรม เพื่อให้ส่งตัวโปรแกรมเวอร์ชันใหม่มาทับได้โดยค่าที่จูนไว้ไม่หาย อย่าย้ายค่าพวกนี้กลับเข้าไปในสคริปต์

ที่ต้องดูจริงๆ มีสองบรรทัด

BW_TOTAL_MB=230
LANES=1
  • BW_TOTAL_MB คือเพดานความเร็วรวมของทั้งเครื่องมือ หน่วยเป็น MB ต่อวินาที นับรวมทุกสายที่รันอยู่
  • LANES คือจะให้รันพร้อมกันได้กี่สาย เพดานข้างบนจะถูกหารด้วยจำนวนสายแบบตายตัว เช่น 230 กับ 2 สาย ได้สายละ 115 และสายที่รันอยู่คนเดียวก็ไม่ยืมโควตาของอีกสาย ตั้งใจให้คาดเดาได้ ดีกว่าเร็วสุด ถ้ารันทีละคำสั่งอยู่แล้วให้เป็น 1

แก้แล้วมีผลกับรอบถัดไปทันที ไม่ต้องรีสตาร์ทอะไร

06

รันครั้งแรก + อ่านผล

แนะนำรันใน tmux เพราะรอบแรกก๊อปทั้งก้อน อาจใช้เวลาหลายชั่วโมง (ปิด ssh กลับบ้านได้ งานยังวิ่งต่อ)

apt install -y tmux
tmux new -s mig
cd /root/tp && ./tp migrate
# detach: press Ctrl-b then d   |   come back later: tmux attach -t mig

บรรทัดสุดท้ายคือบรรทัดที่ต้องดูทุกครั้ง อ่านง่ายๆ ดังนี้

./tp migrate --ctid 251
tail -f logs/ctmig-all-$(date +%F).log
07

ตั้ง cron ให้ sync เอง — แยกสายตาม storage

พอรอบแรกผ่านแล้ว ให้ cron ทำ resync ไปเรื่อยๆ ตัวปลายทางจะสดใกล้ตัวจริงตลอด

--storage คือการสั่งให้ทำเฉพาะ CT ที่อยู่บน storage นั้น และเป็นวิธีแบ่งสายของ cron แต่ละสายมี lock ของตัวเอง จึงรันพร้อมกันได้โดยไม่ต้องรอกัน และเขียน log รายวันแยกไฟล์กัน (logs/ctmig-<lane>-<date>.log)

crontab -e
# one line per storage; each line is its own lane, lock and daily log
*/30 * * * * /root/tp/tp migrate --storage tank-hdd-nas >/dev/null 2>&1
*/30 * * * * /root/tp/tp migrate --storage tank-ssd-nas >/dev/null 2>&1

ถ้าตั้งสองสายแบบข้างบน ให้ตั้ง LANES=2 ใน ctmig.conf ด้วย เพดานความเร็วรวมจะได้ยังคุมอยู่

พิมพ์ชื่อ storage ผิด = โปรแกรมจบด้วย error ทันที ตั้งใจให้เป็นแบบนั้น เพราะถ้ามันจบเงียบๆ แบบสำเร็จทั้งที่ไม่ได้ทำอะไรเลย ใต้ cron จะดูเหมือนคืนที่ทุกอย่างปกติ ทั้งที่ไม่มี CT ไหนถูกย้ายเลยเป็นเดือน · --ctid ที่ไม่ตรงกับบรรทัดไหนเลยก็เหมือนกัน
เช็คว่า cron ทำงานจริง: ls -lt logs/ | head ดูว่ามีไฟล์ log ของวันนี้ · ใกล้วันย้ายจะปรับเป็นทุก 15 นาทีก็ได้ เพื่อให้รอบสุดท้ายเหลือข้อมูลน้อยที่สุด
08

วัน go-live (ทีละ CT)

ขั้นตอนนี้ทำด้วยมือทั้งหมด โปรแกรมไม่ปิดและไม่เปิด CT ให้เอง ห้ามสลับลำดับข้อ 2 กับ 3

  1. รันรอบธรรมดาไปเรื่อยๆ จนข้อมูลที่ส่งแต่ละรอบเหลือน้อย ขณะที่ตัวเก่ายังรันอยู่ 
    ./tp migrate --ctid 251
  2. ปิด CT ตัวเก่าด้วยมือ แล้วรอจนดับสนิทจริงๆ 
    ssh root@10.100.1.11 pct shutdown 100
ssh root@10.100.1.11 pct status 100      # must say: status: stopped
  3. รอบสุดท้าย เก็บข้อมูลช่วงท้ายที่ยังไม่ได้ก๊อป 
    ./tp migrate --ctid 251 --stopped
  4. ปิดงาน CT ตัวนี้ ใส่เลขช่องที่ 3 หลังจากนี้ทุกรอบจะข้ามตัวนี้ถาวร และไปโผล่ที่ช่อง frozen แทน 
    touch done/251.done
  5. เติม net0 แล้วค่อยสตาร์ท ไอพีข้างล่างเป็นแค่ตัวอย่าง แก้ให้ตรงของจริง 
    ssh root@10.100.1.31 pct set 251 -net0 name=eth0,bridge=vmbr0,ip=10.100.1.51/24,gw=10.100.1.1
ssh root@10.100.1.31 pct start 251
  6. ชี้ traffic เข้าเครื่องใหม่ (DNS / reverse-proxy) — ตัวเก่าปล่อย stop ทิ้งไว้ก่อน เผื่อ rollback
ทำไมรอบสุดท้ายต้องทำหลังปิดตัวเก่า ตราบใดที่ CT เก่ายังทำงาน ข้อมูลมันเปลี่ยนตลอดเวลา โดยเฉพาะฐานข้อมูล รอบสุดท้ายจึงต้องทำตอนมันหยุดนิ่งแล้วเท่านั้น ข้อมูลถึงจะครบจริง · --stopped ใช้กับ --ctid ทีละตัวเท่านั้น และถ้าตัวเก่ายังไม่ดับ โปรแกรมจะไม่ยอมทำให้ พร้อมบอกว่าให้ไปปิดเองก่อน

Rollback (ถ้าตัวใหม่มีปัญหา)

ตัวเก่ายังอยู่ครบทุกอย่าง ไม่เคยถูกแตะ — เปิดกลับได้เลย แล้วลบ marker ทิ้งเพื่อให้ cron กลับมา sync ตัวนี้ต่อ

ssh root@10.100.1.31 pct stop 251        # stop the new one first
ssh root@10.100.1.11 pct start 100       # the old CT is still intact
rm done/251.done                         # let the lane sync it again
09

ดูสถานะ / อ่าน log / แก้ error ที่เจอบ่อย

tp status สรุปผลรอบล่าสุดของ CT ทุกตัวในตารางเดียว ส่วน tp doctor ไล่เช็คคำถามที่มักไม่มีใครถาม เช่น CT ที่ขึ้นเครื่องใหม่แล้วแต่ยังไม่มีสำเนาสำรอง หรือ image ที่โตเกินกว่าที่ config บอกไว้

กฎห้ามพลาด

  • รอบสุดท้ายต้องทำหลังปิดตัวเก่าเสมอ โดยเฉพาะ CT ที่มีฐานข้อมูล ไม่งั้นข้อมูลไม่ครบ
  • ห้าม start CT ใหม่ที่ sync ยังไม่จบ ถ้ารอบไหนไม่ได้ rc=0 หรือ rc=24 โปรแกรมจะไม่สร้าง config ให้อยู่แล้ว แต่ถ้า config มีอยู่ก่อนแล้วก็อย่าเพิ่งกดสตาร์ท
  • ห้ามไป mount หรือ rsync ไฟล์ image เองด้วยมือ ถ้าไฟล์เดียวกันถูก mount สองที่พร้อมกัน ข้อมูลพังทันที โปรแกรมกันให้แล้วทุกทาง อย่าเดินอ้อม
  • ย้ายเสร็จแล้วต้อง touch done/<new_ctid>.done เสมอ ถ้าลืม รอบถัดไปจะก๊อปทับ CT ตัวใหม่ที่กำลังใช้งานอยู่
  • CT ที่มี mountpoint เพิ่ม (mp0…) ต้องก๊อปข้อมูลก้อนนั้นเองก่อน go-live
  • ห้ามแก้ ct-migrate.sh อยากปรับอะไรให้ปรับใน ctmig.conf เท่านั้น
  • ตัวเก่าอย่าเพิ่งลบ ปิดทิ้งไว้จนตัวใหม่รันนิ่งหลายวันค่อยเก็บกวาด
